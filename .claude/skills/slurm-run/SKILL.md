# Slurm に流す

r995 の Slurm の待ち行列に、重い計算を 1 本ずつ流す。投げるツールは `~/.claude/scripts/slurm-run.sh` だけで、`sbatch` は
直接使わない（hook が止める。名前、ログ、見積もり、区分と目的、連絡先が抜けるため）。

## 現在の待ち行列

!`~/.claude/scripts/slurm-queue.sh`

ジョブは走る順（パーティション `timed`、`main` の順。その中は走っているもの、止められたもの、待っているものの優先度の順）に
並び、1 行目はジョブ番号、状態、パーティション（既定の `main` か、時間を記録する `timed`）、優先度、区分、見積もり、開始の見込み、
名前、参照、2 行目は目的（結果が何を決めるか）、3 行目は連絡先（git のブランチ、投げた場所、`claude=` セッション、排他で
なければ `shared-cpus=`）。区分が `-` のジョブは、`slurm-run.sh` の外から投げたもので、区分と目的が無い。状態の
`（動かせない）` は、保留（優先度が 1 以下）か配列の親ジョブで、`scontrol top` で並べ直せない。経過と CPU 数は `squeue` で読む。
状態が `SUSPENDED` のジョブは、`timed` のジョブに止められた `main` のもので、それが終わると続きから再開する。
連絡先が自分のブランチでないジョブは、ほかのエージェントのもの。取り消さない（自分のジョブの取り消しは下の「順番」）。順番を変えるのは下の「順番」の `slurm-run.sh` の
並べ直しと `--top`、`ORDER:` の行の `scontrol top`、時間を記録するジョブの `--timed` だけ。

## 流すかどうか

資源で決める。時間の長さだけでは決めない。次のどれかに当たれば流す。迷ったら流す（待つだけで、誤りにはならない）。

- 多くのコア（目安で半分以上）を 5 分以上使い続ける
- メモリを大きく使う（目安で搭載量の半分以上）
- 時間を記録する測定（短くても。区分 `timed` で投げる）

1 コアの処理（テスト、lint、比べるツール）と数分のビルドは、時間がかかっても手元で実行する。待ち行列に入れると、
ほかのセッションの長い計算の後ろで待たされる。
ただし排他のジョブが走っている間は、`taskset` で 1 コアに限る（hook が止める）。

## 投げ方

```bash
~/.claude/scripts/slurm-run.sh --class <区分> --ref '<参照>' --purpose '<目的>' -t <見積もり> <名前> '<コマンド>'
```

例:

```bash
~/.claude/scripts/slurm-run.sh --class decision --ref '#0200' --purpose '平衡キセノンで軸方向の振動が消えるかで、#0200 の修正方法を決める' \
  -t 150 xlc-small-core-equilibrium 'dvc repro examples/small-core/dvc.yaml'
```

Bash ツールの `run_in_background=true` で実行する（ジョブが終わるまで戻らないので、フォアグラウンドは hook が止める）。
下の例の `<区分と目的>` は `--class <区分> --ref '<参照>' --purpose '<目的>'` を表す。

区分 `timed` のほかのジョブは、パーティション `main` に入り、`timed` のジョブに止められうる（止められても続きから再開し、
結果は変わらず、終わりが遅れるだけ）。時間を記録するジョブは、下の「時間を記録するジョブ（--timed）」のとおり区分 `timed` で投げる。

### 区分と目的

`--class`、`--ref`、`--purpose` は必須で、無いか形が違えば投げずにエラーで止まる。待っているジョブのどれを先に流すかを、
誰が見ても同じに待ち行列から確かめるため（次の「順番」）。3 つはジョブのコメントの先頭に `<区分> | <参照> | <目的> | <連絡先>`
の形で入り、`TIME:` 行の末尾にも `class= ref= purpose=` で出る。

- `--class` は次の 4 つで、上ほど先に流す
  - `timed`: 時間を記録する測定（検証の記録に書く時間、高速化の測定）。`--timed` を付けなくてもパーティション `timed` に投げる
  - `record`: 記録に載せる本番（検証の記録の数値、本番の燃焼、ライブラリの作り直し、参照解）
  - `decision`: 決定に要る確認（方式を選ぶ、原因を確かめる、issue を閉じるかを決める計算）
  - `trial`: 検討（結論を変えない試行、開発中の確認）
- `--ref` は、きっかけの issue か ADR の番号（`#0200`、`ADR-0175`、複数は `#0200,ADR-0175`）。`#` から後ろはシェルの注釈になるので、
  `--ref '#0200'` と引用符で囲む。無いときは `- <理由>`
  （`'- nixfiles の実機の確認で、記録の番号が無い'`）
- `--purpose` は、結果が何を決めるかの 1 文（「〜かで、〜を決める」）。何を計算するかでなく、結果を見て何を選ぶかを書く。
  改行と `|` は使えない（コメントの区切り）
- 区分は結果の使い道で選ぶ。迷ったら下の区分にする（上に書くと、ほかのセッションの本番を後ろに回す）

- `-t` は**分の数**（`-t 90`）か `H:MM:SS`。`25m` や `1h` は sbatch が受け付けない。上限ではなく、待ち行列の
  開始の見込みに使う見積もりで、超えても止まらない（OverTimeLimit は UNLIMITED）。外れると、後ろのジョブの見込みが狂う
- 見積もりは過去の実績から決める。`~/.claude/scripts/slurm-history.sh --by-name` が、ジョブ名ごとの見積もり、実績、比
  （`RATIO`、`MAX_RATIO`）を出す（`--timed` のジョブと、割り込みを入れる前に終わったジョブだけ。`main` のジョブは下の
  sacct で読む）。実績の 1.3 倍ほどを書く。実績のない計算は、小さい入力で測って見積もる。
  種類ごとに 1 段階（1 状態）を測ってから本数を掛ける。2026-10-14 に格子 104 状態の見積もり 2 時間が 3 時間超になった
  （反射体つきの格子を、集合体と同じ時間で見積もった）
- `slurm-history.sh --by-name` の表は名前でしか結ばない。名前の似たジョブが同じ仕事をしたとは限らず、割り込みの前の
  ジョブには、`-shared` を付け忘れた排他でないジョブも混ざる。実績に取るジョブは、コマンドと中身が同じ排他のジョブかを sacct で確かめる:

  ```bash
  sacct -S <日付> -X -P -n -o JobID,JobName,State,Elapsed,SubmitLine | grep -F -- '<コマンドの一部>'
  ```

  欄は JobID、JobName、State、Elapsed、SubmitLine の順。比べるのは、State が COMPLETED で、SubmitLine の sbatch の直後が
  `--exclusive` のジョブ（`slurm-run.sh` は排他のときだけそこに置く。`-c` のジョブは `--cpus-per-task=N` で、その時間は同じ仕事
  なら上限としてだけ使う。`AllocCPUS` は `-c 32` でも 32 なので排他の識別に使わない）。コマンドは SubmitLine の `--wrap` の後に
  ある。改行を含むコマンドは 2 行目以降が別の行に出る。コマンドが同じでも、中で走る仕事（ビルドの有無、作り直す出力の数）が
  違えば時間は数倍変わるので、ログ（下の「ログと時間」）の進みの行を数えて比べる。sacct はジョブ 126 より前を持たない
  （その前の排他かどうかの扱いは nixfiles の issue #452）。2026-10-22 に、名前の似た、中身の違う
  排他でないジョブ（`-c 8`、27 分）から 45 分と見積もり、2 時間 5 分かかった。sacct を読んで排他と中身を出す仕組みは
  nixfiles の issue #452
- 名前は `<ツール>-<題材>`（`openmc-2K`、`xlc-2K-swap-water`、`vera-reference-stages`）。使える文字は英数字と `.` `_` `-`。
  ログのファイル名に使い、`squeue` でも見分けるので、題材が分かる名前にする
- コマンドは投げたときのディレクトリで、`--export=ALL`（今の環境変数、nix の開発シェルの PATH を含む）で走る。
  r995 以外のホストでは `/mnt/r995/github`（r995 の `~/github` の NFS）の下で投げる
- ジョブの中のプログラムの時間とメモリは、`slurm-run.sh` の `TIME:` 行と `sacct -j <番号>.batch -o Elapsed,MaxRSS`
  （MaxRSS は `.batch` の行にだけ入る）で取り、コマンドを `/usr/bin/time` で包まない。r995 は NixOS で `/usr/bin/time` が
  無く、ジョブは 0 秒で失敗する（shell の「command not found」は 127 だが、`... || exit 1` でつないでいると 1 になる。
  標準エラーを自分のファイルに向けていると、Slurm のログには `TIME:` 行しか残らない。2026-10-24 に担当の 3 本が 0 秒で
  FAILED になり、投げ直した）。どうしてもプログラムだけの時間が要るときは、ジョブの PATH に GNU time があることを
  `type -P time`（`command -v time` は予約語の `time` を返すので使えない）で確かめてから
  `command time -o <ファイル> -f "%e s %M KB" <コマンド>` と書く（bash の予約語 `time` は `-o` と `-f` を受けないので
  `command` が要る）
- `slurm-run.sh` は必ず `cd <作業ディレクトリ> && ~/.claude/scripts/slurm-run.sh ...` で呼ぶ。ジョブは呼んだときの `$PWD` で
  走り、連絡先にもその `$PWD` が入る。`cd ... &` のように `&` で切ると cd が別のサブシェルになり、ジョブは呼んだ場所
  （main の作業ツリーなど）で走る。2026-10-14 に `dvc repro` が main の作業ツリーで走り、dvc.lock と出力を書き換えた。
  クォートしたコマンドの中の `cd` は連絡先に反映されない
- 投げた直後に `squeue` の連絡先のパスが、意図した worktree であることを確かめる
- 出力は `JOB:`、`LOG:`、ログの末尾 20 行、`EXIT:`。終了コードはジョブのもの

## 順番

パーティション `main` の待っているジョブは、区分の順（`timed` > `record` > `decision` > `trial`）に流す。`slurm-run.sh` は
`main` に投げるたびに、待っているジョブを区分の順（同じ区分は今の順。投げたジョブは自分の区分の末尾、`--top` なら先頭）に
並べ直す（`slurm-queue.sh --order` の列を `scontrol top` に渡す。投げる側は何もしなくてよい）。パーティション `timed` は
区分で並べず、投げた順に走る（時間の記録と、走っているジョブの終わりを待てない数分の計算。区分で並べると、急ぐ計算が長い
測定の後ろに回る）。

- 動かせないジョブ（保留と配列の親ジョブ）と区分の無いジョブは並べ直さず、並べ直したジョブの後ろに回る（区分の無いジョブが前で
  待っていれば、それだけで並べ直す）。`scontrol top` は走り始めたジョブや取り消したジョブを含む列も拒まない（終了コード 0）ので、
  並べ直した後も待ち行列を読み直し、区分の順になるまで繰り返す（同時に投げたジョブが列を上書きしても直る。3 回まで）
- `slurm-run.sh` の外で順が崩れたとき（区分の無いジョブ、`scontrol top` を手で実行したなど）は、`slurm-queue.sh` が
  `ORDER: main: <番号>（<区分>）が <番号>（<区分>）の後ろで待っている。scontrol top <番号>,<番号>,…` の行を出す。その
  `scontrol top` をそのまま 1 回で実行する。1 本ずつ分けて実行しない（`scontrol top` は渡したジョブをその順に先頭へ出すので、
  最後に出したジョブが先頭になり、1 本だけ出すと、その前にいた上の区分のジョブも追い越す）。ほかのセッションのジョブでも、
  区分の順に並べ直すだけなので実行してよい
- ほかのエージェントの走っているジョブは、下の区分でも止めない（区分は待っているジョブの順だけを決める）
- 区分と目的が見えるので、本数の上限は置かない。依頼の本数の上限は、待ち行列が混む（ほかのセッションのジョブが待っている）
  ときだけ

優先度は「10000 + 待った分 − nice」（r995 の Slurm 設定の `PriorityWeightPartition=10000` と `PriorityWeightAge=10080`。待った 1 分が優先度 1。7 日を超えて待つと頭打ちになる）で、並べ替えのない限り投げた順に走る。

- 急ぐ短いジョブは `--top` で投げる。`main` では自分の区分の先頭に出し、上の区分のジョブは追い越さない。`timed` では待っている
  ジョブすべての前に出す。区分の順を越えて 1 本を先に出す仕組みは無い
- 走っているジョブの終わりを待てない数分の計算は、区分を変えずに `--timed` で投げる（下の「時間を記録するジョブ（--timed）」）
- `--top` は、待っているほかのセッションのジョブも後ろに回す（エージェントはみな同じ利用者で投げるので、`scontrol top` は
  その全部の nice を上げる）。見積もりが数分のジョブに限って使う
- 待ち行列の順は `squeue` の PRIORITY（大きい順。同じならジョブ番号の順）で読める
- `scontrol hold` と `release` で並べ替えない。ほかのエージェントが、held のジョブを自分のものでないと誤解して取り消した
  ことがある
- 優先度は同じパーティションの中の順で、`timed` の待っているジョブは `main` の待っているジョブより先に走る
  （パーティションの `PriorityTier`）。並べ直しと `--top` も同じパーティションの中で並べ替える
- ほかのジョブは止めない。`scontrol suspend` で止めず、`main` のジョブを止めるのは `--timed` のジョブだけ（ほかのジョブと待ち行列の順を乱さないため）
- 自分のジョブで目的が無くなったもの（見込みが外れた、入力の誤りに気づいた、など）は、理由を報告に書いて `scancel <番号>` で取り消す。
  auto mode の分類器に `scancel` を拒まれたら、番号と理由を親（委任した側）に送り、親が取り消す

## 時間を記録するジョブ（--timed）

```bash
~/.claude/scripts/slurm-run.sh --class timed --ref '<参照>' --purpose '<目的>' -t <見積もり> <名前> '<コマンド>'   # 時間を記録する
~/.claude/scripts/slurm-run.sh --class decision --ref '<参照>' --purpose '<目的>' --timed -t <見積もり> <名前> '<コマンド>'   # 数分の急ぐ計算
```

時間を記録するジョブ（検証の記録に書く時間、本番の燃焼、ライブラリの作り直し、高速化の測定）は区分 `timed` で投げる。
数分の急ぐ計算は、区分をそのままにして `--timed` を付ける（どちらもパーティション `timed` に入る）。
パーティション `timed` に排他で投げ、待っている `main` のジョブより先に走り、走っている `main` のジョブをすべて止めて
（SUSPEND）実行する。自分は止められない。止められた `main` のジョブは `squeue` で `SUSPENDED` になり、`timed` のジョブが
終わると続きから再開する（計算は失われない）。

- 区分 `timed` も `--timed` も付け忘れると、時間を記録するつもりのジョブが `main` に入り、止められうる。TIME 行に
  `preemptible:` の印が付くので、その時間は記録に使わず、区分 `timed` で投げ直す
- 時間を記録せず、数分で終わらないジョブ（テーブル作成、精度の記録、確認の計算、参照解）には区分 `timed` も `--timed` も付けない。`timed` は待っている `main` のジョブを
  追い越すので、付けると `main` のジョブが待ち続ける
- `timed` のジョブどうしは止め合わず、投げた順に走る。長い `timed` のジョブ（本番の燃焼など）が走っている間は、測定も
  急ぐ計算も待つ。待っている `timed` のジョブの中で先に出すのは `--timed --top`（`timed` は区分で並べ直さない）
- 区分 `timed` と `--timed` は `-c` と組めない（エラー）。排他でない時間は記録に使えず、急ぐ計算は数分なので、`main` のジョブをすべて止めても損は小さい
- 止められたジョブはメモリに残る（Slurm はメモリを数えない）。走っているジョブのメモリ（`sstat -j <番号>.batch -o MaxRSS`。`.batch` を付けないと、`--wrap` のジョブには出る行が無い）と、
  投げる計算のメモリの合計が搭載量（RealMemory 86000 MB）に収まることを確かめる。超えると OOM killer がどちらかを殺す
- 止めるのはジョブのプロセスだけで、ジョブが頼んだ外のデーモンの仕事（nix-daemon のビルドなど）は止まらない。ジョブの
  プロセスは親をたどって見つける（`proctrack/linuxproc`）ので、親から外れたプロセス（デーモン化、二重 fork）も止まらない
  （nixfiles の issue #456）。測定の間にそれらが走り続けると、時間を乱しうる
- 止められたジョブは、持っているロック（cargo のビルドディレクトリ、DVC の `.dvc/tmp/lock`、flock）を持ったまま止まる。
  同じロックを取る計算を `--timed` で投げると、止められたジョブは `timed` のジョブが終わるまで再開しないので、どちらも
  進まない（DVC はすぐ失敗する）。走っている `main` のジョブの連絡先の worktree と同じ worktree、target ディレクトリ、
  DVC のリポジトリでは投げない。worktree によらないロック（cargo の `$CARGO_HOME` のパッケージのキャッシュ、nix の
  評価のキャッシュ）でも同じことが起きうる。`timed` のジョブがロックを待って進まなければ（ログに `Blocking waiting for file lock`
  など）、自分の `timed` のジョブを取り消し、止められたジョブが終わってから投げ直す

## 複数のジョブを待つ

関係するジョブは、まとめて 1 つの background のコマンドで投げて待ち、すべて終わってから報告する:

```bash
cd <作業ディレクトリ> && { ~/.claude/scripts/slurm-run.sh <区分と目的> -t 30 a '…' & ~/.claude/scripts/slurm-run.sh <区分と目的> -t 30 b '…' & wait; }   # 依存が無いとき。同時に投げ、待ち行列に任せる
cd <作業ディレクトリ> && ~/.claude/scripts/slurm-run.sh <区分と目的> -t 30 a '…' && ~/.claude/scripts/slurm-run.sh <区分と目的> -t 30 b '…'   # b が a の出力を使うときだけ。a が失敗したら b は投げない
```

後ろのジョブが前のジョブの出力を使うときだけ `&&`。独立なら `&` と `wait`（排他のジョブは待ち行列が 1 本ずつ実行する）。`cd` は `{ }` の前に置く（`cd d && a & b` は a だけが d で走る）。`wait` だけの終了コードは常に 0 なので、成否は `JOB:` の番号ごとに `sacct -j <番号> -o State,ExitCode` で見る（出力が混ざり、`EXIT:` の行にはジョブの名前が無い）。`&&` でつなぐと後のジョブは前の終わりまで squeue に出ず、親が取り消せない。打ち切りの指示が届く前に投げられる（2026-10-24 に 7 本を `&&` でつなぎ、最後の 2 時間のジョブが投げられて scancel した）。

background の `slurm-run.sh` は終わると通知が届くので、Monitor や until のループで重ねて待たない（2026-10-22 に担当が Monitor を 9 回張り、30 分で切れるたびに張り直してトークンを無駄にした。通知は届く）。

`slurm-run.sh` の出力は、そのまま受ける（`| tail` などにつなぐと終了コードと `TIME:` の行が消える。2026-10-15 に 2 回、ジョブの時間を記録できなかった）。同じ background のコマンドの `slurm-run.sh` や `wait` の後ろに `;` や `&&` で表示のコマンド（`tail`、`grep`、`cat`）をつなぐと、終了コードは表示のコマンドのものになり、ジョブの成否を表さない（1 本の `slurm-run.sh` では `;` でジョブの終了コードが失われ、`&&` では表示のコマンドが失敗すると成功したジョブが失敗に見える。`wait` の後ろでは、もともと 0 の終了コードが偽の失敗になる）。表示はつながず、ジョブが書いた出力のファイルは通知の後に別の呼び出しで読む。1 本なら `slurm-run.sh` の終了コードと `EXIT:` で、`wait` で待った複数なら上のとおり `sacct` で成否を見る。`tail -3 a.txt b.txt` の古い `-N` の形は GNU tail が 2 つ以上のファイルで拒むので、`tail -n 3` と書く（2026-10-26 に、2 本とも COMPLETED のジョブを待つコマンドが後ろのこの形で 1 で終わり、原因を追った）。

## 排他のジョブが走っている間

手元の全コアの計算は排他のジョブの時間の記録を乱す（hook が止める）。`run-checks.sh` は自分で
排他のジョブを見つけ、1 コアに限って遅く実行する。

排他のジョブ中の手元の試行の時間は、測定に使わない。手元のビルドや 1 コアの計算、Slurm 外のプロセス（nix-daemon のビルドなど）との
重なりは、数 % のブレとして受け入れ、追加の隔離の仕組み（測定から物理コアを外す、手元の計算を止める hook）は作らない（`--timed` の一時停止は別で、一時停止は経過時間を壊すので残す）。hook で手元を 1 コアに
限っても、その論理 CPU の片割れでは測定のスレッドが走りうるので完全には隔離できず、ユーザーの判断で「厳密な時間計測は要らない」として
nixfiles #460 を対応せずに閉じた（2026-10-24）。測定の時間を比べるときは、同じ時間帯の手元の計算と Slurm 外のプロセスを差の原因の候補に
先に挙げ、高速化の判断は同じジョブの中の A/B、`seconds` の内訳、反復や自己遮蔽の回数で比べる。

## ログと時間

ログは r995 の `~/github/slurm-logs/<名前>-<ジョブ番号>.out`（`slurm-run.sh` が `LOG:` に出す）。終わった直後に、末尾へ
`TIME: job=<番号> elapsed=<実際> estimate=<見積もり> <印> class=<区分> ref=<参照> purpose=<目的>` が足される（印は下の段落）。全ジョブの履歴は `sacct` で、名前や期間で絞り、
メモリの最大値も読める:

```bash
sacct -S <日付> --name=<名前> -o JobID,JobName,Partition,Elapsed,TimeLimit,State,MaxRSS,Suspended
```

番号の分かったジョブの時間（見積もりや依頼の前提に使う値）は、番号と時間が同じ行にある形で読む。`sacct -j <番号>[,<番号>…] -X
-o JobID,JobName,Partition,Elapsed,Suspended,State` か、`TIME:` 行の `job=`（この欄を足す前のログには無い）。記録に書けるかは
次の段落で決める。何本かのログを 1 回の `grep` で
読むときは `-H`（または `-h` を付けない）でファイル名を行に残し、行の順をファイルや引数の順と仮定しない。Claude Code の Bash の
`grep` は ugrep を呼ぶ関数で、出力の順は引数の順と限らず、実行ごとに変わりうる。2026-10-28 に、`grep -h '^TIME' *-536.out *-534.out`
の 1 行目（534 の 17 分 15 秒）を 536（sacct で 7 分 20 秒）と読み、担当への依頼の見積もりに書いた。

記録に書く時間は、パーティション `timed` のジョブ（区分 `timed` か `--timed`）の `elapsed` だけを使う（TIME 行に印が無い）。`timed` で走らなかったジョブの TIME 行には、
止められなかったときも `preemptible: 割り込まれうるので時間は記録に使わない（記録するなら排他の --timed）` が付く。その時間
（`elapsed` も、プログラムが自分で測った時間も）は記録に使わない。実際に止められていれば、さらに
`suspended: 止められていたので時間は当てにならない` が付く（止められていた時間は `sacct` の `Suspended` で読める）。

`slurm-history.sh` の表は、`timed` のジョブと、割り込みを反映する前（2026-10-23 21:40 より前）に終わったジョブだけから作り、
ほかの件数を `UNTIMED:` の行に出す。`main` のジョブの見積もりの実績は、上の「投げ方」の `sacct` で読む（`Elapsed` は
止められていた時間を除く）。

## 排他でない投げ方（-c）

```bash
~/.claude/scripts/slurm-run.sh <区分と目的> -c <コア数> -t <見積もり> <名前> '<コマンド>'
```

`--exclusive` を付けず、`<コア数>` の CPU だけを取る。時間を記録しない長い計算（何時間もの参照解、開発中の
試行）向け。

- コア数は Slurm の CPU（ハードウェアスレッド）で数える。OpenMC を 16 スレッドで実行するなら `-c 16`（物理コア 8）
- r995（Ryzen 9 9950X）は 16 物理コア × SMT で論理 32。Slurm はスレッドを CPU に束縛しない（TaskPlugin なし）ので、共有ジョブは
  どの分け方でも物理コアを SMT で共有する。SMT の片割れの伸びは小さい（OpenMC は 16 → 32 スレッドで 1.45 倍。2026-10-12 の xlc での観測）ので、
  `-c 24` + `-c 8` のように偏ると、少ない側が極端に遅くなる（`-c 8` の格子計算が 3 時間以上になった。多い側の伸びは測っていない）。長い共有ジョブと
  開発の共有ジョブを重ねるときは `-c 16` + `-c 16` を基本にする。時間を記録する測定は排他の区分 `timed` で流す
- ログの TIME 行の末尾に `shared (-c N): 時間は当てにならない` が付く。その時間を検証の記録に書かない
- `main` の排他のジョブは、ノードにほかのジョブが走っている間は始まらない。排他でないジョブが走っている間は、あとから投げた
  `main` の排他のジョブが待つ。排他でないジョブどうしは重なる。`main` の排他の短いジョブとは重ならない
  （sbatch の `--exclusive` は、ほかのジョブとノードを共有しない）。`--timed` のジョブは待たず、走っている排他でないジョブも
  止めて始まり、止めたジョブとメモリを分け合う
- メモリは Slurm が数えない（`CR_Core`）。排他でないジョブを複数流すときは、メモリの合計が搭載量（RealMemory 86000 MB）を
  超えないよう自分で数える。超えると OOM killer が長い計算を殺す
- 名前の末尾に `-shared` を付ける（`openmc-2K-shared`）。`sacct` で実績を読むとき、排他のジョブと見分けるため
- 連絡先に `shared-cpus=N` が付くので、`squeue` で待たされている理由が読める
