# 頼む側（親のセッション）の書き方

委任するかは、費用で決める。担当 1 本は数万〜数十万トークンを使い、依頼と報告の往復で細部が落ちる。数回のツール呼び出しで済む
ことと、行き先の分かっている確認は、親が自分で行う。担当に回すのは、独立して進められるブランチ作業、親の文脈を埋める長い
読み込みや試行、親の見方に引きずられない読みが要るレビュー。

手順と報告の形はこのスキルにあるので、依頼には作業ごとに変わることだけを書く:

```text
最初に /delegate を呼び、その手順に従って進める。

リポジトリ: <path>
ブランチ: <branch>
何をするか: <目的と範囲。決定済みの内容（ADR、issue、ユーザーとの合意。ユーザーの言葉は下の項の形で）と、判断が要るときの軸。ユーザーの案は「案（決定ではない）」と親の評価。評価が使う事実を含め、事実は「前提」に書き、本文で要るときは前提の行の語をそのまま書いて指す。ADR を書かせるか実装させるときは、マージでの status を結果ごとの条件で 1 行（下の「ADR を書かせるか」の項）>
前提: <事実として使う値と前提を 1 行に 1 つ。各行に出典か「確かめていない」。書き方は下の「前提」の項。事実を使わなければ「なし」>
完成の形: <何ができれば終わりか。テストや確認で示す振る舞い。実機の試験や計算があれば目的と区分>
変える範囲: <変えてよいファイルやディレクトリと、issue の置き場（docs/issues/ か GitHub の issue）>
```

- 6 つの欄は、行頭に欄の名前を置き、直後に `:` か `（…）:` を続けた見出しで書く（`前提:`、`前提（確かめていない）:`。`（…）` の
  中に出典の括弧を 1 段まで入れてよい。箇条書きの中の語は見出しに数えない）。依頼をファイルに置くときは、prompt の 1 行目に
  「依頼文は <絶対パス> にある」と書く。空でない最初の行に「/delegate を呼び、」（「呼ぶ。」「呼んで、」など、句読点か行末が
  続く形）がある Agent の prompt（またはそれが指すファイル）に欠けた欄があれば、PreToolUse の hook（claude-hooks の
  delegate-request-fields）が止める。判定の規則と修正方法は、その拒否の文言にある
- 「変える範囲」には、issue の作成と追記を含めると書く（欄に `issue` の語が無ければ delegate-request-fields が止める。理由は拒否の
  文言にある）
- 追加の指示を送るときは、報告の催促でなければ「報告の催促ではない」と書く
- モデルは依頼文ではなく、Agent の `model` で渡す
- trailer を依頼に書くときは、`Co-Authored-By:` のモデル名を `<自分のモデル名>` と書き、`Claude-Session:` だけ親の値をコピーする
  （親の行をそのままコピーすると親のモデル名になり、担当の system-reminder と食い違う）
- Agent の `description` の先頭にモデル名を書く（例: `Opus: 履歴の書き換えツールの PR`。ユーザーが実行中の一覧で見分けるため）。
  `subagent_type: "fork"` は `model` を無視して親のモデルで走るので親のモデル名を書き、/code-review などスキルが起動するものは
  description を選べないので、起動を伝える文にモデルを書く。ユーザーへの報告でも、担当に触れるたびにモデルを添える
- 依頼は 1 時間を超える待ち（「作業中の規則」の待ちの項で担当が待たないもの）で切る（例:「実装して計算の
  コマンドを書くまで」と「記録とレビュー対応」）。担当はその待ちの前で報告して終わるので、待ちの後の作業まで 1 つの依頼に入れると
  毎回やり残しになる。待ちの後に同じ担当を起こして続けさせない（理由は「作業中の規則」の 1 時間を超える待ちの項）
  - 計算: 報告の「続きの作業」のコマンドを、報告の行ごとに 1 本の `run_in_background=true` の Bash で、そのまま実行する（依存の
    無いジョブは 1 行 1 本、`a && b` の行はそのまま。出力の `EXIT:` が行のジョブの順に並び、続きの担当が成否をジョブに対応づけ
    られる）。投げる直前に、担当の項と同じく `base-moved.sh` で比較元を fetch してから `git -C <worktree> rev-list --count HEAD..<base>`
    を見て、結果を変える変更（コード、入力、環境）が既定ブランチに入っていれば、投げずに続きの担当に rebase を先に頼む。すべての
    background の終わりの通知を待ってから、すべての出力のファイルのパスだけを続きの依頼の前提の欄に書き（ジョブの番号、ログ、成否は続きの
    担当が読む）、前の報告の「続きの作業」を何をするかと完成の形にコピーして、新しい担当に同じブランチの続きとして頼む。親が出力の
    ファイルから読むのは、成否の行（`EXIT:`）と末尾の数行まで（成否を知るためだけに担当を増やさない）。ログの中身は続きの担当が
    読む（親の費用は文脈の大きさで決まり、読んだログはその後の毎回の読み出しと書き直しに残るため）。通知が来るまで、そのジョブの worktree を変える続きの依頼は出さない（ジョブは走りながら worktree の入力を読み、出力を
    書くので、途中で変えると記録と違う版で走る）
  - PR の自動レビュー: 担当が待ちを打ち切って報告したときは、止まった担当には通知が来ないので、親が /gh-pr-review の手順のとおり
    background で待つ（担当が再レビューの依頼を済ませていなければ
    `~/.claude/skills/gh-pr-review/scripts/request-rereview.sh <PR の URL>`（依頼の後そのまま待つ）、ほかは `gh-wait-review.sh <PR の URL>`。終了コードの扱いは /gh-pr-review に従う）。計算と両方を待つ報告は、自動レビューの続きを計算の
    続きと同じ担当に、計算の後で頼む
- ADR を書かせるか実装させる依頼と、そうする追加の指示には、その ADR をマージでどの status にするかを、/git-merge の「proposed の
  ADR」の節の分け方（全部を実装、一部を実装、試して採らない、試しただけ、決定だけ）ごとに、accepted、proposed、rejected（実装を
  ブランチから外す）のどれかで書く（担当の扱いは手順 4。担当の周の後に親が accept を指示すると、直した ADR にもう 1 周が要る）
- 追加の指示でレビューの周を頼むときは、「<base>（手順 2 の比較元。最後の周の HEAD ではない）より後の差分に周を回す」と書き、
  報告の時点で最後の周の後に挙動を変えるコミットがあれば、回さなかった理由を書くことを求める。周の終わりと周の数（「差分に
  1 周」）は書かず、手順 7 の「どちらも」の項に任せる（書き直した文は規則が変わっても残り、周の数は上限と読まれる）
- 実機の試験や計算には、目的（結果が何を決めるか、きっかけの issue か ADR の番号）と区分（/slurm-run の `timed`、`record`、
  `decision`、`trial`）を完成の形に書く。本数の上限は、待ち行列が混む（ほかのセッションのジョブが待っている）ときだけ書く（上限は
  読み方で守ったかが変わり、外れた方式の損を限らない。見積もりと再実行の理由は担当が報告に書く）
- 決定済みの内容は、どこで決まったか（ADR などの記録の場所、ユーザーの言葉）を添える（担当の文脈に親の会話は無く、ユーザーの
  言葉は依頼に書いたものしか届かない）。ADR などの決定は、言い換えずに要る部分の文をコピーする（省いたところに「…」）か、番号と
  節だけで指す（言い換えると、どの項や量に掛かるか（主語、否定、条件）がずれ、担当はそれを決定として設計する）
- ユーザーの言葉（判断、承認、案）を「」で括って引用するときは、会話の記録の `.jsonl` のパスとその発言の `timestamp` を添え、
  記録からそのままコピーする（語尾や後半を変えない。長ければ要る部分だけを、文の区切り（「。」「？」「！」、改行、発言の端）で
  切って引用し、省いたところと、文の途中で切った端に「…」を付ける。受ける側は両端がこれに当たらない引用を要約に落とす）。記録は
  `~/.claude/projects/` の下の、会話を始めたディレクトリ（worktree を含む）ごとのディレクトリにあり（ファイル名の ID は
  `Claude-Session:` の ID と別）、パスと `timestamp` は受ける側と同じ `~/.claude/scripts/quote-in-transcript.sh` に `~/.claude/projects/*/*.jsonl` を渡して引く。
  記録からコピーしない言葉は括らず、`<要約>（ユーザー <日付> の判断の要約）` と書く（日付は JST。言い換えを括ると、受ける側が
  ユーザーの発言として ADR にコピーする）
- 前提: 依頼が事実として使う値と前提は、「前提」の欄に 1 行に 1 つ書き、「何をするか」の本文には書かない（両方に書くと片方だけ
  直ってずれる。1 行ずつなのは、行ごとに出典を開いたかを両方が見返せるため）。各行は出典で確かめて出典を添えるか、「確かめて
  いない」と添える（前提が誤ると、担当はそれを土台に設計する。確かめるのは受ける側の作業になる。欄の無い追加の指示の事実も同じ）。決定の出典（ADR、ユーザーの言葉）は
  「何をするか」に添える
  - 出典の種類: 外部の値（ツールの既定値、仕様の数値と表の番号、体系の構成）は版と、ファイルの行か文書のページや節。対象の
    リポジトリの事実（何を出力し、何を残すか、入力の中身）はファイルと、関数、型、入力の項目などの名前（行は main が進むとずれる）。
    出力について書くときは、書き出す箇所と、それを切り替える入力の項目と設定も読む。出典は依頼を書く時点で開いた文書の場所か、
    実行したコマンドとその出力にする（前に見た値は、その後に変わっていることがある）。前に終わった計算の結果は、保存された
    ログや記録を開き直せばよく、計算をやり直さない
  - 比を掛けた見込み（計算の時間の倍率など）は、「確かめていない」と添える行でも、比の元の測定（ジョブやログ。割り込まれず
    CPU を共有しないジョブか）と、何と何の比かを添える。分子が見込む計算と同じ条件で、分母が比を掛ける測定と同じ条件の比だけを
    使う（分母が違う比を掛けると、別の量の見込みになる）
  - 記録の値（検証の記録、比較の JSON、担当の報告の数値）は手でコピーせず、出典（JSON のパスとキー、記録の節の名前）で指すか、
    その時点に出典から値を出したコマンドと出力を貼る（手でコピーすると、開いた出典が正しくても写し間違える）。範囲（a〜b）は列の min と max を計算して書く（列は単調とは限らない）。担当の
    報告の値は、報告が拠った記録か JSON を開いて取る（報告の後に書き直されているか、別の点の集まりを比べていることがある）
  - 原因の見方（どの量が差を生むか）を依頼の理由に使うときも 1 行で書き、その量の語で open の issue と ADR の「候補」「確かめて
    いない」の行を検索して、既存の分析と食い違わないことを確かめ、拠った issue か ADR の節を出典に添える（食い違う見方を書くと、
    担当は既存の分析と照らすところから始める）
- ユーザーの案を依頼に入れるときは、先に親が評価し、その結果（賛否と理由、成り立つ条件、反例を探した範囲。測らないと決められ
  なければその旨と、測る計算の目的と区分を「完成の形」に）を添えて、「何をするか」の中で「案（決定ではない）」と明示する（決定と
  区別せずに書くと、担当は検討せずに作る）。成り立たないか、より良い代案があると判断した案は、理由と代案をユーザーに返し、依頼には
  入れない
- 時間や精度の目標を書くときは、分かっている内訳のうち、その依頼で手を付けない部分の合計を先に出し、目標がその合計以下なら、
  その部分も範囲に入れるか目標を上げる。内訳は「前提」の欄に書き、分からなければ、先に測るか「内訳は確かめていない」と書く
- 依頼の範囲から外す部分（「〜は変えない」）は、外してよい理由（目標の精度や速度を満たしている、など）を「前提」の欄に出典か
  「確かめていない」を添えて書く。精度の目標は、変える関数とそれから求める関数の定義域の全体（負の側、区間の境界、±∞、NaN）を、
  実装の前に多倍長などの参照と比べる形で「完成の形」に書く
- 呼び出しの形（スクリプトの引数、出力の行の形、ファイルの形式、スキルの名前）を変える依頼では、「変える範囲」を書く前に、その形を
  書くか読む（照合する、解析する）リポジトリの中の場所（スクリプト、hook の拒否の文言と照合、スキル、CLAUDE.md、README、ADR、
  テスト、モジュールのコメント）を、スクリプト名、行の見出し、ファイル名、スキルの名前（`/` を付けない形。名前を変えるときは古い
  名前）で grep し、ヒットごとに新しい形かを見て、古い形のものを範囲に入れる（必須の引数を足す変更では、古い形は新しい引数が
  無いことでしか見分けられない）。ADR のヒットは、直してよい所を /adr の「確定後の運用」で決め、直さない凍結する部分は外す場所に
  数えない。ほかに外す場所は、上の項のとおり理由を「前提」の欄に、誰がいつ合わせるかを「何をするか」に書く（リポジトリの外の
  呼び出しは、親がマージの後に合わせると書けばよい）。古い形が残ると、担当は範囲の外として直さず、続きの依頼が増える
- 規則（対象のリポジトリの CLAUDE.md、ADR、delegate 以外のスキル）の解釈や例外を依頼や追加の指示に書くときは、先にその規則の
  原文を読み、場所を添える。規則と食い違う例外は書かず、要るならユーザーに聞くか、先に規則を直す（受ける側は取り込まずに報告する）
- レビューの (c)（/git-merge の「直す指摘の基準」）を担当に直させる依頼と追加の指示には、指摘ごとに、何が引いた先と食い違うかと、
  どの出典で直すかだけを書き、直した後の文と値は書かない（担当がそのまま入れると、親の誤りが次の周の (c) になる）
- hook のエスケープの付け方や「〜なら付けてよい」は依頼に書かない（担当はエスケープを手順の一部として使う）
- 委任の前に、対象のリポジトリで `git -C <リポジトリ> fetch` のあと、同じものを直している PR・ブランチ・worktree が無いかを
  確かめる（`gh pr list`（リモートがあれば）、`git -C <リポジトリ> branch -a`、`git -C <リポジトリ> worktree list`）。別のセッションの
  ものがあれば、委任せずその PR に任せるか、マージを待つ。自分のセッションが作ったブランチ（コミットの `Claude-Session:` で
  分かる）への続きの委任は、そのブランチで進める
- 依頼の方式に関わる採用中の ADR を、対象のリポジトリの docs/adr/ で確かめ（`design-records` か `grep -l <語> <リポジトリ>/docs/adr/*.md`。
  status が採用中のものに絞る）、依頼にその番号と「この ADR に従う」か「この ADR を置き換える」を書く。ADR の「検討した案」で採らな
  かった方式は頼まない
- 1 つの成果物（例: 辞書の追加とその調査の結果）は 1 つの PR にまとめて頼む
- 使うツールが追跡されていない場所（`references/`、手元のスクリプト）にあれば、それを昇格させる作業を本作業より先に別の依頼で
  頼み、マージしてから本作業を頼む（受ける側の手順 1 の止まる条件は ADR とコードの食い違いの安全網で、重複する PR や未追跡の
  ツールは拾えないので、ここまでの確認は頼む前に行う）
- 報告は確かめる前の暫定として扱う。マージの前に、報告のコミットと確認の結果を自分で確かめる。担当が ADR と issue に書いた「」で
  括ったユーザーの言葉は、受ける側と同じ `~/.claude/scripts/quote-in-transcript.sh` を `~/.claude/projects/*/*.jsonl` に掛けて同じ文があるかと、両端が文の
  区切りか「…」に当たるかを見て、満たさなければマージの前に要約の形に直す
