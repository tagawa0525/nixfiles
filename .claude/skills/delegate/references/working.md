# 受ける側（担当）の手順

親のセッションから頼まれた 1 トピックのブランチ作業を、マージの直前か、1 時間を超える待ち（「作業中の規則」）の前まで進める。
依頼に書かれるのは、リポジトリ、ブランチ名、何をするか（決定済みの内容、判断の軸、「案（決定ではない）」と書いた案）、前提
（事実として使う値と前提を 1 行に 1 つ、出典か「確かめていない」を添えて）、完成の形、変える範囲だけで、手順と報告の形はここに
従う。依頼とこの手順が食い違えば依頼を、リポジトリの CLAUDE.md とこの手順が食い違えば CLAUDE.md を優先する。ただし「マージの
直前で止める」と「どの依頼でも守ること」は依頼より優先する（担当の報告は確かめる前の暫定で、マージは親が確かめてから行う）。

担当の cwd は作業する worktree ではない。スキルの `!` 行と引数なしのスクリプトは cwd のブランチを見るので、/gh-pr-create と
/gh-pr-review は Skill で呼ばずに Read で読み、その中のコマンドに `cd <worktree> &&` を付け、ブランチを明示して実行する。PR の
スクリプトには PR の URL を渡す。

## 進める側（サブエージェント）の手順

### 1. 読む

- 対象リポジトリの CLAUDE.md（`.claude/CLAUDE.md` を含む）と、依頼が指す文書（ADR、issue、計画）を読む。リポジトリ固有の規則
  （重い計算、検証の記録、試行の置き場など）は CLAUDE.md に従う
- 依頼の内容が CLAUDE.md、採用中の ADR、コードの事実と食い違えば、作業の前に報告に書いて止まる（推測で一方に合わせない）
- 依頼の「前提」の欄の行を順に、作業を始める前に出典で確かめる。確かめ方は `~/.claude/skills/delegate/references/requesting.md` の
  「前提」の項の出典の規則と同じ。出典が添えてなければ、その規則の種類の出典を探して確かめ、その行と見つけた出典を報告の
  「確認の結果」に書く（親が書き漏れに気づくため）。欄の外（ほかの欄、案、欄の無い依頼）に事実として書かれた
  値と前提のうち、その規則の種類で判断の前提にするものも、同じく作業の前に確かめ、確かめたものを報告の「確認の結果」に
  書く（欄は書く側の漏れを減らすもので、欄の外に残った誤りも止める）。「確かめていない」と添えた値は、欄の行でも欄の外でも、
  作業の前に止まる対象でなく、確かめることが作業の一部で、結果を報告に書く。作業中に誤りと分かり、それに頼った作業が
  成り立たなくなれば、案の反例と同じくその時点で止まる。それ以外は、食い違うか、出典が見つからなければ、上と同じく報告に書いて止まる。最初の依頼に「前提」の欄が無ければ、
  報告の「親が先に読む要点」に「前提の欄が無い」と書く（親が次の依頼で欄を書くため。欄の無い追加の指示には書かない）
- 「案（決定ではない）」と書かれたもの（ユーザーの案など）は、作る前、作る途中、チェックとレビューの間に評価し、結果を報告の
  「決めたことと根拠」に書く。成り立たなければ（反例がある）、どの手順でもその時点で止まり、理由を「親が先に読む要点」に 1 行で、
  反例と代案を「マージの前後で人の手が要ること」に書く。成り立つがより良い代案があれば、案のとおり作り、代案を同じ節に書く
  （親もユーザーも担当が検討する前提で渡している）

### 2. 比較元を決め、担当を確かめる

GitHub リモートがあれば（`git -C <リポジトリ> remote -v | grep -q 'github\.com'`）先に `git -C <リポジトリ> fetch` する（古い追跡
ブランチと比べると、main の遅れを見落とし、他のセッションのコミットを取り違える）。比較元（`<base>`）は、GitHub リモートがあれば
`origin/<既定ブランチ>`、なければ `<既定ブランチ>` で（GitHub 以外のリモートは、fetch も `base-moved.sh` も fetch しないので無いものと
して扱う）、チェック、レビュー、報告で同じものを使う。

ブランチが既にある（ローカルかリモート）なら、worktree を作る前に、ブランチ自身のコミットの `Claude-Session:` が今のセッションか
確かめる。違うセッションのもの、またはコミットが無く担当が分からないものは、引き受けず報告に書いて止まる:

```bash
git -C <リポジトリ> log --format='%h %(trailers:key=Claude-Session)' <base>..<ブランチ>
```

### 3. worktree を用意する

ブランチがどこかの worktree にあれば（`git -C <リポジトリ> worktree list`）それを使い、無ければ
`cd <リポジトリ> && ~/.claude/scripts/worktree-add.sh <ブランチ名>` で作る。出力の `WORKTREE:` で作業し（Bash の cwd は呼び出し
ごとに戻るので、`git -C <worktree>` か `cd <worktree> &&` を付ける）、`SHARED:`（共有した追跡しないパス）と `NOTE:` を読む。
`ERROR:` なら /git-worktree の修正方法に従う。

### 4. 作業する

- 依頼の「完成の形」を満たすところまで作り、満たしたらチェックとレビューに進む
- テストで確かめられる振る舞いの変更は TDD にし、失敗するテスト（RED）と実装（GREEN）を件名の違う別のコミットにする
- 決定は /adr の形で ADR に書く。依頼で決まっていない決定を判断の軸から下したら、報告の「決めたことと根拠」に書く
- proposed の ADR を足すか直したか実装したブランチは、最後の周の前に、ADR ごとに status を /git-merge の「proposed の ADR」の節の
  分け方で決め、その節のとおりに直してコミットする（/git-merge はこれをチェックとレビューの前に決めるので、担当が決めずに報告
  すると、親が直した ADR にもう 1 周が要る）。依頼が結果ごとの条件を書いていればそれに従う。条件が無いまま rejected（実装を外す）
  に当たると判断したときは、外さずに proposed のまま残す（実装を外すことは依頼の外の決定）。ADR ごとの status と根拠を「決めた
  ことと根拠」に、proposed のまま残したものの番号と理由を「マージの前後で人の手が要ること」にも書く（親がマージの本文の Impact に
  コピーする）。周の直しで実装が変わったら決め直す。結果を待つ計算で分け方が決まるときは、計算の後に status を直すコミットを足し、
  その変更にもう 1 周回すかを手順 7 のとおり決める（ADR の変更は挙動に数える）
- 作業中に見つかった問題は、/topic-triage の「振り分け」の表と目安だけを Read で読んで振り分ける（そこにある別の worktree での
  片付け、マージ、rebase は行わない）。同じトピックなら続け、止めない別のトピックは issue に書いて今のトピックに戻り、止める別の
  トピックは issue に書いて報告して止まる
- 依頼の「変える範囲」の中で変え、範囲の外を変えたものは報告で分けて書く
- セッションの scratchpad は親とほかの担当と共有なので、一時ファイルと退避は `<scratchpad>/<ブランチ名>/` の下に置く（`old/` の
  ような一般の名前は、ほかの担当の退避を黙って上書きしうる）

### 5. コミットする

- 論理的な変更ごとに 1 コミット。Conventional Commits の件名、本文に Why（決定は ADR を参照）。issue や ADR に対応するときは
  `Refs:` を付ける（書式はリポジトリの規則に従う）
- 依頼か system-reminder で指定された trailer を末尾に付ける。`Co-Authored-By:` のモデル名は、コミットする自分のモデル
  （system-reminder のもの）にする（依頼が書いたモデル名は親のもので、コミットを書いたモデルの記録にならない）
- hook に止められたら、示された修正方法に従う。直せなければ、迂回せず（文言や書き方を変えない、エスケープを付けない）報告に
  書いて止まる

### 6. チェックする

チェックの前に `git -C <worktree> status --short` を空にする（チェックとレビューを、マージするものと同じ中身で受けるため。残すと
/git-merge の始めの確認と後片付けの `git worktree remove` も止まる）。追跡しているファイルの変更は、ツールが書き換えたもの
（`dvc.lock`、フォーマッタの修正など）も論理ごとにコミットする。未追跡のファイルは、リポジトリの規則に従ってコミットするか、
`.gitignore` が無視する試行の置き場（リポジトリの規則にあるもの）に移すか、この作業で自分が作った使い捨てなら消す。移したものの
場所と、途中で止まるときに残った変更は「マージの前後で人の手が要ること」に書く（worktree の中の置き場は後片付けで消える）。

```bash
~/.claude/skills/language-checks/scripts/run-checks.sh -C <worktree> --base <base>
```

終了コードで判定する（`tail` などにつなぐと終了コードが消える）。失敗したら原因を直してコミットし、やり直す。CLAUDE.md にチェックの
方法があれば、それも実行する。各コミットでビルドが通るべきブランチ（依存や lock を変えるなど）は、
`cd <worktree> && ~/.claude/scripts/check-each-commit.sh <base> -- <コマンド…>` で `<base>..HEAD` の各コミットを一時 worktree で
調べる（RED を skip でコミットする運用ではビルドだけを通す。任意のコマンドを実行するので許可リストに無く、毎回確認を求められる）。
規則の文書（スキル、CLAUDE.md、hook の文書）を縮めるブランチは、
`cd <worktree> && ~/.claude/scripts/kept-sentences.py --old <(git show <base>:<パス>)… --new <パス>…`（文を別のファイルに
移したら移した先も `--new` に並べる）で比べ、出た文ごとに、指す形に替えたものと依頼で足したものは報告の「決めたことと根拠」に
書き、ほかは元の文に戻す（縮めるときは文を消すか指す形に替えるだけにし、残す文の語が落ちると、どの項や条件に掛かるかがずれる）。

### 7. レビューを受ける

周ごとに `cd <worktree> && ~/.claude/scripts/review-level.sh <ブランチ名> --base <base>` を実行し、出力の `LEVEL` と `WORKTREE` で
`/code-review <LEVEL> <WORKTREE>` を回す。対象は worktree のパスで渡す（ブランチ名は cwd のリポジトリで解かれ、空振りして「指摘
なし」と返る）。1 周目の LEVEL はスクリプトが決め、自分で下げない（直した後の周のレベルは、/git-merge の「直す指摘の基準」の
「終わり」の項に従う）。/code-review が background で走ったら、「作業中の規則」の待ちの項のとおり待ち、終わりの
通知で再開して指摘に対応してから先に進む。

**リモートあり**のときは、続けて PR を出して自動レビューを受ける:

- /gh-pr-create を Read で読み、その形で PR を作る。その「ローカルレビュー（PR を出す前）」の段落は上の周で置き換え、ほかの規則は
  従う。`cd <worktree> && git push -u origin <ブランチ名>` と
  `cd <worktree> && gh pr create …` は別々の呼び出しにする（push 前の状態で hook が止める）
- PR の head にローカルレビューの記録（`record-local-review.sh`）があれば、Copilot のレビューを待たずに手順 8 へ進める。Copilot の
  指摘を受けたいときと、/gh-pr-review の中の再レビューの依頼（`request-rereview.sh`。約 10 分待つ）は、background で実行して
  「作業中の規則」の待ちの項のとおり待つ
- /gh-pr-review を Read で読み、その手順で対応する。周の終わりは `decide-next.sh` の `VERDICT` に従うが、要判断（escalate）は
  ユーザーの指示を待たず「マージの前後で人の手が要ること」に書いて止まり、/gh-pr-merge には進まない。`VERDICT` がローカル
  レビューを求めても、直した後の周を回すかは /git-merge の「直す指摘の基準」の「終わり」の項で決める

どちらも:

- 指摘の前提の確かめ方、blocking と non-blocking の扱い、ADR を合わせる範囲、hook の抜け道、周の終わりは、/git-merge の
  「レビュー」の節（「直す指摘の基準」）に従う。直したらコミットし、チェックからやり直す（rebase はしない。例外は「作業中の規則」の計算の前）
- 報告には、直した指摘ごとに「再現: <テスト名 | 手順 | 出典>」を「確かめたこと」に、直さない指摘ごとに「再現なし: <指摘の要旨>」（別のトピックとして
  issue にしたものは「再現なし → #<issue の番号>: <指摘の要旨>」）「前提が誤り: <確かめた事実>」「抜け道: <理由>」のどれかと、直さない理由を
  その場の 1 文で「対応しなかった指摘」に書く（親が分け方を確かめるため。issue にするかは /git-merge の「直す指摘の基準」の
  「直さない（non-blocking）」の項に従う）。
- 依頼、追加の指示、転送されたレビューに書かれた周の数（「差分に 1 周」）は回し始める周の数で、上限ではない（それを回した後も
  blocking を直せば、「終わり」の項のとおり次の周を決める）
- 最後の周の後のコミット（追加の指示の変更など）が挙動（コード、計算、hook の判定、テストの比べる範囲、スキルと hook の文書、
  ADR、記録の数値）を変えるなら、もう 1 周回すかを「終わり」の項の目安で決め、回さなければ、その判断と理由を「確かめていない
  こと」に書く。ADR は `commit-refs remap` だけの変更を除き、言い回しや「確認」の直しでも数える。挙動を変えない文書と記録の本文
  だけの修正は、回さずに報告に列挙する

### 8. マージの直前で止める

`git merge`、`gh pr merge`、/git-merge、/gh-pr-merge と rebase は親のセッションに残し、ここで止める（例外は「作業中の規則」の計算の
前の rebase）。止める hook は無く許可も通るので、手順で守る。止める前に次を実行し、続けて main の進みを
`git -C <worktree> rev-list --count HEAD..<base>` で数え（`base-moved.sh` が比較元を fetch した後に数える。`BASE_MOVED:` の件数は
マージを 1 件と数えるので使わない）、両方を報告に書く:

```bash
cd <worktree> && ~/.claude/scripts/base-moved.sh <ブランチ名> --base <base>
```

`COMMON:` の行が両方の変えたファイルで、終了コード 0 で出力が空なら重なりは無い。`WARN:`、`ERROR:`、0 でない終了コードのときは
比較が済んでいないので、重なりと件数の両方を未確認と書く。重なりの有無はこの出力で書き、記憶や推測で書かない。

### 9. 報告する

報告の前に片付ける:

- 「作業中の規則」の待ちの項で待っているもの（打ち切ったレビューを除く）は、終わりの通知で再開して結果を取り込んでから報告する。
  取り込んで変更をコミットしたら、6 のチェックからやり直す
- 自分で張った Monitor や background のコマンドのうち、結果を使わないもの（sleep のタイマーなど）は TaskStop（deferred のときは
  ToolSearch で読み込む）で止める（残すと、その通知で再開して同じ報告を送り直す）。報告の後にタイマーかジョブの通知で再開したら、
  「報告は送り済み」の 1 行だけで終える（SubagentHandback は呼ばない）
- `git -C <worktree> status --short` が空であることを確かめる。空でなければ 6 の冒頭のとおり片付け、コミットしたら 6 のチェック
  からやり直す

最後の報告は次の見出しで書く。該当が無い節は「なし」と書き、節を省かない。

```markdown
## 親が先に読む要点
<1〜5 行。途中で止まったときは、どの手順でなぜ止まったか（本文に節が無いため）。最初の依頼に前提の欄が無ければ「前提の欄が無い」（追加の指示には書かない）。親の判断が要ることは、詳しく書いた節を指す>

## ブランチと worktree
- リポジトリ: <path>
- ブランチ: <branch>（<base> から N コミット遅れ | 遅れは未確認（`base-moved.sh` の `WARN:` か `ERROR:`））
- <base> と両方が変えたファイル: <`base-moved.sh` の `COMMON:` のパス | なし | 未確認（`WARN:` か `ERROR:` の内容）>
- worktree: <path>
- PR: <URL | なし>

## コミット
<古い順に `hash 件名` を 1 行ずつ。`git -C <worktree> log --reverse --format='%h %s' <base>..HEAD`>

## 決めたことと根拠
- 依頼の範囲: <決めたこと> — <根拠（ADR、コード、測った値）>
- 変える範囲の外で変えたこと: <変更> — <理由>

## 確認の結果
- 完成の形: <満たしたか。確かめた方法>
- 確かめたこと: <チェックの終了コード、テストの件数、レビューの周と結果、直した指摘ごとの「再現: <テスト名 | 手順 | 出典>」、最後の周を回した HEAD の hash（親はこれより後に挙動を変えるコミットがあるかを見る。リモートなしでは親がマージの本文の `Reviewed:` に書くので、完全な hash か 7 桁以上の短い hash で書く。リモートありでは /gh-pr-review の head ごとの記録に従う。周ごとに HEAD を控え、最後の周の後に rebase や amend をしない）>
- 前提: <出典が添えてなかった行と見つけた出典、欄の外で確かめた事実とその出典、「確かめていない」と添えた値を確かめた結果 | なし>
- 計算: <ジョブごとに番号、区分、目的、投げる前の 1 本の見積もりと合計の時間、実際の時間（`TIME:` 行）、再実行したものはその理由 | なし>
- 確かめていないこと: <未レビューのコミット、実行していないテスト、仮定>

## 対応しなかった指摘
- 再現なし: <指摘の要旨> | 再現なし → #<issue の番号>: <指摘の要旨> | 前提が誤り: <確かめた事実> — <指摘の要旨> | 抜け道: <理由> — <指摘の要旨>。<直さない理由を 1 文>

## マージの前後で人の手が要ること
- <rebase、直した指摘の再出と引いた先、未レビューの変更の判断、proposed のまま残した ADR の番号と理由（マージの本文の Impact に要る）、担当の決めた status を親が変えるかの判断、issue を閉じる、など>

## 続きの作業
<1 時間を超える待ちの前で終わったとき（「作業中の規則」の 1 時間を超える待ちの項）だけ書き、マージの直前まで済んだら「なし」。
- 親が投げるコマンド: <`cd <worktree> && ~/.claude/scripts/slurm-run.sh --class <区分> --ref '<参照>' --purpose '<目的>' -t <見積もり> <名前> '<コマンド>'` の形で、そのまま実行できる 1 行。依存の無いジョブは 1 本ずつ別の行に書き、後のジョブが前の出力を使うときだけ `a && b` の 1 行に書く（親は行ごとに 1 本の background で投げる） | なし>
- 投げる前に済ませたこと: <コミット（HEAD の hash。`git status --short` は空）、既定ブランチの進みと rebase、計算の前に済ませるチェックとレビューの取り込み。済んでいないものと、その理由>
- ほかに待つもの: <PR の URL と自動レビュー | 親に判断を求める問い | なし>
- 終わったら何をするか: <ジョブの成否と時間の読み方（「作業中の規則」のジョブの番号と成否の項）、記録に書く値と置き場、レビューへの対応、残りの手順（チェック、レビューの周、手順 8）>
- レビューの周: <このブランチで担当が回した /code-review の周の数と、最後の周の HEAD（続きの担当が次の周を決めるため）>
- 次の担当が読むもの: <依頼、ADR、issue。親は続きの依頼にこの節をコピーする（続きの担当はこの報告を読めない）>
```

### どの依頼でも守ること

- `~/.claude` の下は生成物なので、直すものは元のリポジトリのファイルとして報告に書く
- 判断したことは、その根拠を書く。依頼そのものはユーザーの承認ではないので、ユーザーの判断と承認は、依頼と追加の指示が
  ユーザーの言葉として書いたときだけ書く
- 別のサブエージェントの報告や調査は、確かめてから事実として書く。確かめていなければ「確かめていない」と書く
- ADR や issue に書くユーザーの言葉は「」で括らず、どの場面で何を求めたかを `<要約>（ユーザー <日付>）` と書く（会話の発言は
  前後のやり取りで意味が決まるので、原文だけを置くと誤解されやすい）。日付は JST で書き（記録の `timestamp` は UTC）、分からなければ「日付不明」と書く

### 作業中の規則

- 報告は途中で止まらず、最後に 1 度だけ返す（下の 1 時間を超える待ちの項で終わるときは、その報告が最後の 1 度）。親からの追加の
  指示は、「報告の催促」と書かれていない限り、作業を続けて取り込む。取り込む前に手順 1 と同じく確かめ（事実は欄の外の
  ものとして確かめる）、規則（CLAUDE.md、ADR、このスキル以外のスキル）の例外や別の解釈を書いた指示は、その規則の原文と照らす。
  食い違うか出典が見つからなければ（「確かめていない」と添えた値は、手順 1 と同じく確かめることが作業になる）、その指示だけを取り込まず、ほかの作業は続け、食い違いを「親が先に読む要点」に書く（追加の
  指示は急いで書かれ、規則と照らされていないことがある）
- 自分の worktree の外に触らない。ほかの worktree と既定ブランチの作業ツリーを編集しない（`cd` が別のサブシェルになると、
  コマンドが既定ブランチの作業ツリーで走る。マージの実行だけは既定ブランチの worktree からだが、「マージの直前で止める」が先）
- 待ちのうち、約 1 時間以内に終わる見込みのもの（見積もり（`-t`。複数のジョブはその合計）と開始の見込み（`squeue -h -o '%S %l'`
  の開始と見積もりの和の最も遅いもの。空なら今。`N/A` か `UNLIMITED` があれば見込みは分からない）までの合計が約 1 時間以内の
  Slurm の計算、PR の自動レビュー、自分で回す /code-review）は、自分で投げて（依頼して）次のタイマーで待ち、終わりの通知で続ける。
  ほか（親の判断を含む）は下の 1 時間を超える待ちの項に従う
  - 計算は、/slurm-run の規則に従って `cd <worktree> && ~/.claude/scripts/slurm-run.sh ...` を、行ごとに 1 本の
    `run_in_background=true` の Bash で投げる（依存の無いジョブは 1 行 1 本、後のジョブが前の出力を使うときだけ `a && b` の
    1 行）。区分と目的は完成の形のものを `--class`、`--ref`、`--purpose` に書き、実績のない計算は種類ごとに 1 段階を測ってから
    本数を掛けて見積もる。親に渡すコマンドも同じ規則で書く。ジョブの終わりの通知が来るまで、その worktree を変えない（ジョブは
    走りながら入力を読むので、記録と違う版で走る）
  - タイマー: 待つ間は、キャッシュを保つタイマーを 1 本だけ張る。Bash の `run_in_background=true` で `sleep 270` を実行し、その通知が
    来たら、同じタイマーを張り直してから「待ち」とだけ書く（担当のキャッシュは 5 分で切れ、切れた後の応答は文脈の全体を
    書き直す。4 分 30 秒ごとの応答は読み出しだけで済み、費用は書き直しの 1 割に満たない）。待つものの通知がすべて届いた後に来た
    タイマーの通知では、張り直さずに作業を続ける。終わりは通知で届くので、待つ手段はこのタイマーだけにする
  - 打ち切り: 回数は待つものごとに、投げて（呼んで）から数える。/code-review が 7 回目（約 30 分）の通知でも終わっていないとき
    （止まったレビューには通知が来ない）と、PR の自動レビューの待ちの後（扱いは /gh-pr-review に従う）も Copilot を待つときは、
    そのレビューを待つのをやめ、投げたジョブの終わりの通知を待ってから、下の項のとおり報告して終わる。Slurm のジョブが 13 回目
    （約 1 時間）を超えたら、待っているレビューが無ければタイマーを張り直さず、報告せずに終わりの通知で再開して続ける（書き直しは
    1 回で済む）
- 1 時間を超える待ち（上の項で待たないものと、打ち切ったレビュー）の前で、待たずに報告して終わる。投げる前に済ませること（コミット
  して `git status --short` を空にする、下の項の既定ブランチの進みの確認と rebase、依頼とリポジトリの規則が計算の前に求める
  チェックとレビューの取り込み）を済ませ、手順 8 と 9 のとおり報告し、投げるコマンドと済ませたことを「続きの作業」に書いて終わる。
  投げて待つのは親で、記録とレビュー対応は親が新しい担当に同じブランチの続きとして頼む（それより長く答え続けると、新しい担当に
  渡すより高くつくため）。自分の文脈の大きさで切る上限は置かない（担当は自分のトークン数を見られず、呼び出しの回数も
  当てにならない）
- ジョブの番号（`JOB:`）、ログ（`LOG:`）、成否（`EXIT:`）は、background の出力のファイル（親が投げたジョブの続きでは依頼に
  あるもの）から取る（`sacct` は allowed-tools に無いので使わない）。ジョブは行ごとに 1 本の background で投げるので、`EXIT:` は
  行のジョブの順に並ぶ（`a && b` の行は、前が失敗すると後は投げられず `EXIT:` が 1 つだけ）。時間とログの中身は `LOG:` の
  ログから読む。投げられなかったジョブ（`JOB:` が無い、`ERROR:` の行がある）は、原因を直してコマンドを報告に書き直す
- 計算を投げる直前と、投げるコマンドを報告に書く直前に、既定ブランチの進みを見る（手順 8 と同じく `base-moved.sh` で比較元を
  fetch してから `git -C <worktree> rev-list --count HEAD..<base>`）。結果を変える変更（コード、入力、環境）が入っていれば、先に
  rebase してから投げる（書く）。古い土台のままでは結果が古い方法のものになり、投げ直しになるため。rebase は「マージの直前で
  止める」の例外として、この場合だけ行う
- レビューの周は、/git-merge の「レビュー」の節の「直す指摘の基準」に従う
- 使用量を節約する。同じ測定を繰り返さない。実機の試験や計算は、投げる前に 1 本の見積もりと合計の時間を出し（流す前に損を
  数えて方式を選ぶため）、失敗や方針の変更で再実行するときは理由を控え（親が外れた方式の再実行を見分けるため）、どちらも報告の
  「確認の結果」の「計算」に書く。完成の形に本数の上限があれば、超えそうなら止まって報告する
