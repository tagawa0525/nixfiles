# Delegate

親のセッションから頼まれた 1 トピックのブランチ作業を、マージの直前まで進める。依頼に書かれるのは
リポジトリ、ブランチ名、何をするか（決定済みの内容、判断の軸、「案（決定ではない）」と書いた案）、前提（事実として使う値と
前提を 1 行に 1 つ、出典か「確かめていない」を添えて）、完成の形、変える範囲だけで、手順と報告の形は
ここに従う。
依頼とこの手順が食い違えば依頼を、リポジトリの CLAUDE.md とこの手順が食い違えば CLAUDE.md を優先する。
ただし「マージの直前で止める」と「どの依頼でも守ること」は、依頼より優先する（サブエージェントの報告は
確かめる前の暫定で、確かめずにマージすると誤った結論が main に入る。マージは親が報告を確かめてから行う）。

サブエージェントの cwd は作業する worktree ではない。スキルの `!` 行と引数なしのスクリプトは cwd の
ブランチを見るので、/gh-pr-create と /gh-pr-review は Skill で呼ばずに Read で読み、
その中のコマンドを `cd <worktree> &&` を付け、ブランチを明示して実行する。PR のスクリプトには PR の URL を渡す。

## 進める側（サブエージェント）の手順

### 1. 読む

- 対象リポジトリの CLAUDE.md（`.claude/CLAUDE.md` を含む）と、依頼が指す文書（ADR、issue、計画）を読む
- 重い計算、検証の記録、試行の置き場など、リポジトリ固有の規則は CLAUDE.md に従う
- 依頼の内容が CLAUDE.md、採用中の ADR、コードの事実と食い違えば、作業を始める前に報告に書いて止まる
  （推測で一方に合わせない）
- 依頼の「前提」の欄の行を順に、作業を始める前に出典で確かめる。確かめ方は「頼む側（親のセッション）の書き方」の
  「前提」の項の出典の規則と同じ。出典が添えてなければ、その規則の種類の出典を探して確かめ、その行と見つけた出典を報告の
  「確認の結果」に書く（親が書き漏れに気づくため）。欄の外（ほかの欄、案、欄の無い依頼）に事実として書かれた
  値と前提のうち、その規則の種類で判断の前提にするものも、同じく作業の前に確かめ、確かめたものを報告の「確認の結果」に
  書く（欄は書く側の漏れを減らすもので、欄の外に残った誤りも止める）。「確かめていない」と添えた値は、欄の行でも欄の外でも、
  作業の前に止まる対象でなく、確かめることが作業の一部で、結果を報告に書く。作業中に誤りと分かり、それに頼った作業が
  成り立たなくなれば、案の反例と同じくその時点で止まる。それ以外は、食い違うか、出典が見つからなければ、上と同じく報告に書いて止まる。最初の依頼に「前提」の欄が無ければ、
  報告の「親が先に読む要点」に「前提の欄が無い」と書く（親が次の依頼で欄を書くため。欄の無い追加の指示には書かない）
- 依頼が「案（決定ではない）」と書いたもの（ユーザーの案など）は、作る前、作る途中、チェックとレビューの間に評価し、
  評価の結果を報告の「決めたことと根拠」に書く（案に含まれる出典で確かめられる前提は、上の項目で確かめる）。技術的に
  成り立たなければ（反例がある）、どの手順でもその時点で止まり、ほかの途中で止まるときと同じく報告する。止まった理由を「親が先に読む要点」に 1 行で、反例と代案を「マージの前後で
  人の手が要ること」に書く。
  成り立つが、より良い代案があるときは、案のとおり作り、代案を「マージの前後で人の手が要ること」に書く（親もユーザーも、案を担当が検討する前提で
  渡している。検討せずに作ると、成り立たない案がそのままブランチに入る）

### 2. 比較元を決め、担当を確かめる

GitHub リモートがあれば（`git -C <リポジトリ> remote -v | grep -q 'github\.com'`）先に fetch する。古い追跡
ブランチと比べると、main の遅れを見落とし、他のセッションのコミットをブランチのものと取り違える:

```bash
git -C <リポジトリ> fetch
```

比較元（`<base>`）は、GitHub リモートがあれば `origin/<既定ブランチ>`、なければ `<既定ブランチ>`（GitHub 以外の
リモートは無いものとして扱う。上の fetch も `base-moved.sh` もそれを fetch しないので、追跡ブランチは古いまま残る）。チェック、レビュー、
報告で同じものを使う。

ブランチが既にある（ローカルかリモート）なら、worktree を作る前に、ブランチ自身のコミットの
`Claude-Session:` が今のセッションか確かめる:

```bash
git -C <リポジトリ> log --format='%h %(trailers:key=Claude-Session)' <base>..<ブランチ>
```

違うセッションのもの、またはコミットが無く担当が分からないものは、引き受けず報告に書いて止まる。

### 3. worktree を用意する

ブランチがもうどこかの worktree にあれば（`git -C <リポジトリ> worktree list`）、その worktree を使う。
無ければ作る:

```bash
cd <リポジトリ> && ~/.claude/scripts/worktree-add.sh <ブランチ名>
```

- 出力の `WORKTREE:` 以降はそこで作業する。Bash の cwd は呼び出しごとに戻るので、`git -C <worktree>` か
  `cd <worktree> &&` を付ける
- `SHARED:`（共有した git で追跡しないパス）と `NOTE:`（メイン worktree に無いパス、複数の GitHub リモート）を
  読む。`ERROR:` なら /git-worktree の修正方法に従う

### 4. 作業する

- 依頼の「完成の形」を満たすところまで作り、満たしたらチェックとレビューに進む。「案（決定ではない）」が作る途中や
  チェックとレビューの間に成り立たないと分かったら、手順 1 のとおり止まる
- テストで確かめられる振る舞いの変更は TDD にする。失敗するテスト（RED）と実装（GREEN）を別のコミットにし、
  件名も別にする
- 決定が要るものは /adr の形で ADR に書く。依頼で決まっていない決定を、依頼の判断の軸から下したときは、
  報告の「決めたことと根拠」に書く
- 作業中に見つかった問題は、/topic-triage の「振り分け」の表と目安だけを Read で読んで振り分ける（そこにある
  別の worktree での片付けとマージ、rebase は行わない）。同じトピックなら続け、止めない別のトピックは issue に
  書いて今のトピックに戻り、止める別のトピックは issue に書いて報告に書いて止まる
- 依頼の「変える範囲」の中で変える。範囲の外を変えたものは、報告で分けて書く

### 5. コミットする

- 論理的な変更ごとに 1 コミット。Conventional Commits の件名、本文に Why（決定は ADR を参照）
- issue や ADR に対応するときは `Refs:` を付ける（書式はリポジトリの規則に従う）
- 依頼か system-reminder で指定された trailer（`Co-Authored-By:`、`Claude-Session:` など）を末尾に付ける。`Co-Authored-By:` の
  モデル名は、コミットする自分のモデル（system-reminder のもの）にする。依頼が別のモデル名を書いていても、それは親のモデルで、
  コミットを書いたモデルの記録にならない
- hook に止められたら、示された修正方法に従う。直せなければ、迂回せず（文言や書き方を変えない、エスケープを
  付けない）報告に書いて止まる

### 6. チェックする

チェックの前に `git -C <worktree> status --short` を空にする（チェックとレビューを、マージするものと同じ中身で受けるため）。
追跡しているファイルの変更は、ツールが書き換えたもの（`dvc.lock`、フォーマッタの修正など）も含めて、論理ごとにコミットする。
未追跡のファイルは、リポジトリの規則（試行の置き場など）に従ってコミットするか、`.gitignore` が無視する試行の置き場（リポジトリの規則にあるもの）に
移すか、この作業で自分が作った使い捨てのものなら消す。移したものは、場所を報告の「マージの前後で人の手が要ること」に書く
（worktree の中の置き場は、マージの後の後片付けで worktree ごと消えるので、要るものは親が移す）。残すと、/git-merge の始めの
確認（リモートの無いリポジトリの `git-merge-state.sh`）と、後片付けの `git worktree remove` が止まる（2026-10-22 に、
`examples/` へ移した試行の入力の隣に、その出力 34 個が未追跡で残った）。途中で止まって報告するときは、残った変更を報告の「マージの前後で人の手が要ること」に書く。

```bash
~/.claude/skills/language-checks/scripts/run-checks.sh -C <worktree> --base <base>
```

終了コードで判定する（出力を `tail` などにつなぐと終了コードが消える）。失敗したら原因を直してコミットし、やり直す。CLAUDE.md に
チェックの方法が書かれていれば、それも実行する。

依存や lock を変えるブランチなど、各コミットでビルドが通るべきときは、`<base>..HEAD` の各コミットを一時 worktree で
調べる（検査コマンドは呼び出し側が決める。RED を skip でコミットする運用では、全テストでなくビルドだけを通す）:

```bash
cd <worktree> && ~/.claude/scripts/check-each-commit.sh <base> -- <コマンド…>
```

任意のコマンドを実行するので許可リストには入れていない。実行のたびに確認を求められる。

### 7. レビューを受ける

ローカルのレビューは、どちらの場合も先に回す:

```bash
cd <worktree> && ~/.claude/scripts/review-level.sh <ブランチ名> --base <base>
```

出力の `LEVEL` と `WORKTREE` で `/code-review <LEVEL> <WORKTREE>` を回す。対象はブランチ名でなく worktree の
パスで渡す。/code-review は cwd のリポジトリでブランチ名を解くので、cwd が別のリポジトリだと空振りして
「指摘なし」と返る（2026-10-12 に 2 回起きた）。/code-review は、結果をその場で返すか、background で走って終わりに
通知を届ける。background のときは終わりの通知だけで待ち（Monitor、sleep、until のループは足さない）、通知で再開して指摘に対応してから先に進む。

2 周目からも、周ごとに上の `cd <worktree> && ~/.claude/scripts/review-level.sh <ブランチ名> --base <base>` を実行し、出力の `LEVEL` で回す。
LEVEL はスクリプトが決める（`docs/` の外のファイルが 1 つでもあれば high）。前の周の直しが小さくても、自分で medium に下げない
（2026-10-29 に xlc の担当が、Python の修正を含む 3 周目を、スクリプトを通さずに medium で回した）。

**リモートあり**のときは、続けて PR を出して自動レビューを受ける:

- /gh-pr-create を Read で読み、その形（タイトル 70 文字以内、`## Summary` / `## Changes` / `## Tests`）で
  PR を作る。/gh-pr-create の「ローカルレビュー（PR を出す前）」の段落は、この手順の上の周で置き換える（その周も
  /git-merge の「直す指摘の基準」の歯止めの 3 周に数える）。ほかの規則（Summary の先行 PR、Tests に書く直さない指摘の issue の番号など）は従う。`cd <worktree> && git push -u origin <ブランチ名>` と `cd <worktree> && gh pr create …` は別々の
  呼び出しにする（push 前の状態で hook が止める）
- PR の head にローカルレビューの記録（`record-local-review.sh`）があれば、Copilot のレビューを待たずにマージの
  直前へ進める。Copilot の指摘を受けたいときだけ、`~/.claude/scripts/gh-wait-review.sh <PR の URL>`
  （URL は `gh pr create` の出力）を `run_in_background=true` で実行して待つ。待つ間に最後の報告を返さない
  （待機の終わりの通知で再開する）
- /gh-pr-review を Read で読み、その手順で対応する。スクリプトには PR の URL を渡す。周の終わりは
  `decide-next.sh` の `VERDICT` に従う。最後の分岐は次に置き換える: 要判断（escalate）はユーザーの指示を
  待たず報告の「マージの前後で人の手が要ること」に書いて止まり、/gh-pr-merge には進まない。3 周を回した後は、
  `VERDICT` がローカルレビューを求めても回さず、/git-merge の「直す指摘の基準」の歯止めのとおり報告する（3 周目で blocking を
  直したときは、同じ節の「3 周目で blocking を直したら」に従う）

どちらも:

- 指摘の前提の確かめ方、直す指摘（blocking）と直さない指摘の扱い、ADR を合わせる範囲、hook の抜け道の扱い、周の終わりと
  歯止めの 3 周と 3 周目で直したときの扱いは、/git-merge の
  「レビュー」の節（「直す指摘の基準」）に従う
- 直したらコミットし、チェックからやり直す（rebase はしない。例外は「作業中の規則」の計算の前）
- 報告には、直した指摘ごとに「再現: <テスト名 | 手順 | 出典>」を「確かめたこと」に、直さない指摘ごとに「再現なし → <issue の番号>」
  「前提が誤り: <確かめた事実>」「抜け道: <理由>」のどれかと理由を「対応しなかった指摘」に書く（親が分け方を確かめるため）
- 最後の周の後のコミット（追加の指示の変更など）が挙動（コード、計算、hook の判定、テストの比べる範囲、スキルと hook の文書、
  記録の数値）を変えるなら、歯止めの中でもう 1 周回し、使い切っていれば回さずに「確かめていないこと」に書く。挙動を変えない
  文書と記録の本文だけの修正は、回さずに報告に列挙する（2026-10-28 に xlc の担当 2 本が、誤りを報告する順やテストの比べる
  範囲を変える修正を、レビューの後に積んで列挙だけで報告し、直した箇所が誰にも読まれないまま残った）

### 8. マージの直前で止める

`git merge`、`gh pr merge`、/git-merge、/gh-pr-merge と rebase は親のセッションに残し、ここで止める（計算を投げる直前の rebase だけは「作業中の規則」の例外）。これを止める hook は無く、
許可も通るので、手順で守る。止める前に、ブランチと main の両方が変えたファイルを次で出し、続けて main の進みの件数を
`git -C <worktree> rev-list --count HEAD..<base>` で数えて、両方を報告に書く（`base-moved.sh` は GitHub の origin の比較元を比べる前に
fetch するので、件数はその後に数える。件数は rev-list の値を書き、`BASE_MOVED:` の件数（マージを 1 件と数える）は使わない）:

```bash
cd <worktree> && ~/.claude/scripts/base-moved.sh <ブランチ名> --base <base>
```

`COMMON:` の行が両方が変えたファイルで、終了コード 0 で出力が空なら重なりは無い。`WARN:`、`ERROR:`、0 でない終了コードの
ときは比較が済んでいないので、重なりと件数の両方を未確認と書く（fetch が済んでいない追跡ブランチの件数は古い）。重なりの有無はこの出力で書き、記憶や推測で書かない（2026-10-24 に「lattice の
crate は main で変わっていない」と報告したが、main は同じ crate の 4 ファイルを変えていた）。

### 9. 報告する

報告の前に片付ける:

- 結果を待っている計算とレビュー（Slurm のジョブ、/code-review、`gh-wait-review.sh`）は、終わりの通知で再開して結果を
  取り込み、そのあとで報告する。取り込んで変更をコミットしたら、6 のチェックからやり直す
- 自分で張った Monitor や background のコマンドのうち、結果を使わないもの（sleep のタイマーなど）は TaskStop（deferred の
  ときは ToolSearch で読み込む）で止める。止めずに報告すると、その通知で再開して同じ報告を送り直す（2026-10-22 に、
  レビューを待つ sleep の Monitor を残したまま報告を返し、タイマーが切れるたびに送り直して計 3 度送った）。報告の後に
  タイマーの通知で再開したら、「報告は送り済み」の 1 行だけで終える（SubagentHandback は呼ばない）。親からの追加の指示は
  「作業中の規則」に従う
- `git -C <worktree> status --short` が空であることを確かめる。空でなければ 6 の冒頭の扱いで片付け、コミットしたら 6 の
  チェックからやり直す

最後の報告は次の見出しで書く。該当が無い節は「なし」と書き、節を省かない。

```markdown
## 親が先に読む要点
<1〜5 行。途中で止まったときは、どの手順でなぜ止まったか。最初の依頼に前提の欄が無ければ「前提の欄が無い」（追加の指示には書かない）。この 2 つをここに書くのは、止まった理由には本文に節が無く、欄が無いことは親が次の依頼で直すものだから。親の判断が
要ることは、詳しく書いた節（「マージの前後で人の手が要ること」など）を指す>

## ブランチと worktree
- リポジトリ: <path>
- ブランチ: <branch>（<base> から N コミット遅れ | 遅れは未確認（`base-moved.sh` の `WARN:` か `ERROR:`））
- <base> と両方が変えたファイル: <`base-moved.sh` の `COMMON:` のパス | なし | 未確認（`WARN:` か `ERROR:` の内容）>
- worktree: <path>
- PR: <URL | なし>

## コミット
<古い順に `hash 件名` を 1 行ずつ。`git -C <worktree> log --reverse --format='%h %s' <base>..HEAD`>

## 決めたことと根拠
- 依頼の範囲: <決めたこと> — <根拠（ADR、コード、測った値）>
- 変える範囲の外で変えたこと: <変更> — <理由>

## 確認の結果
- 完成の形: <満たしたか。確かめた方法>
- 確かめたこと: <チェックの終了コード、テストの件数、レビューの周と結果、直した指摘ごとの「再現: <テスト名 | 手順 | 出典>」、最後の周を回した HEAD の hash（親は /git-merge で、これより後に挙動を変えるコミットがあるかを見て、あればブランチ全体をレビューする。リモートありでは /gh-pr-review の head ごとの記録に従う。周ごとに HEAD を控え、最後の周の後に rebase や amend をしない）>
- 前提: <出典が添えてなかった行と見つけた出典、欄の外で確かめた事実とその出典、「確かめていない」と添えた値を確かめた結果 | なし>
```

### どの依頼でも守ること

- `~/.claude` の下は生成物なので、直すものは元のリポジトリのファイルとして報告に書く
- 判断したことは、その根拠を書く。依頼そのものはユーザーの承認ではないので、ユーザーの判断と承認は、依頼と追加の指示が
  ユーザーの言葉（引用か要約）として書いたときだけ書く
- 依頼と追加の指示で、会話の記録（`.jsonl`）のパスと `timestamp` を添えて「」で括ったものは、ユーザーの言葉の引用である。
  ADR、issue、報告に引用として書く前に、記録に同じ文があるかを確かめる。親の言い換えを括った引用は、確かめずにコピーすると
  ユーザーの発言として確定した ADR に残る。パスと `timestamp` の無い「」は語や見出しにも使うので、ユーザーの言葉と
  書いてあっても引用として扱わず、要約として書く。記録は 1 行 1 JSON で、ユーザーが打った発言は `type` が `user` で
  `origin.kind` が `human` の行の `message.content` と、ターンの途中に送った発言の `type` が `attachment` で
  `attachment.type` が `queued_command` の行の `attachment.prompt` にある（どちらも文字列か、`type` が `text` の要素の配列）。
  ほかの行には、ツールの結果、ほかの担当の報告、会話の圧縮の要約（言い換えた引用を含む）、コマンドの出力（`origin` の無い
  `user` の行）も入り、`human` の行にも IDE の通知や command-message（`<` で始まる要素）、ユーザーが貼り付けた文
  （`<pasted_content …>` の中。エージェントの言い換えを含みうる）が入るので、`grep` で文字列を探すだけでは確かめにならない。
  `origin` の無い `user` の行（ローカルのコマンド、別のクライアントの発言）は拾わないので、その発言の引用は要約に落ちる。
  引用の文を「…」の印を含めて（括る「」は入れずに）そのまま 1 つのファイルに書き（シェルの引用符と食い違わないため）、次で探す:

  ```bash
  jq -rR --rawfile q <引用の文のファイル> '
    ($q | rtrimstr("\n")) as $q
    | ($q | split("…") | map(gsub("^\\s+|\\s+$"; "")) | map(select(. != ""))) as $parts
    | if $parts == [] then "引用の文が空\n" | halt_error(1) else . end
    | def text_of:
        (if type == "string" then [.] elif type == "array" then map(select(.type? == "text") | .text) else [] end)
        | map(gsub("<pasted_content[^>]*>.*?</pasted_content[^>]*>"; ""; "m")
              | if test("<command-args>") then capture("<command-args>(?<a>.*?)</command-args>"; "m").a
                elif test("^\\s*<") then empty else . end)
        | join("\n");
      def in_order($s): reduce $parts[] as $p ($s; if . == null then null
        else split($p) as $x | if ($x | length) < 2 then null else ($x[1:] | join($p)) end end) != null;
      fromjson? | select(type == "object")
      | (if .type == "user" and .origin.kind? == "human" then .message.content
         elif .type == "attachment" and .attachment.type? == "queued_command"
           and (.attachment.commandMode // "prompt") == "prompt"
           and (.attachment.origin.kind? // "human") == "human" then .attachment.prompt
         else empty end | text_of) as $t
      | select($t | in_order(.))
      | "\(input_filename) \(.timestamp) \(.timestamp[0:19] + "Z" | fromdate + 32400 | strftime("%Y-%m-%d %H:%M JST"))\n\($t)\n---"
  ' <記録の .jsonl>
  ```

  コマンドは、引用を「…」で切った部分がどれも同じ発言に同じ順で出る発言ごとに、記録のパス、`timestamp`、JST の日時と、
  発言の全文を出す（`-R` と `fromjson?` は、書きかけの行で後のファイルを読まずに止まらないため）。添えられた `timestamp`
  の発言が出て、引用の両端が全文の文の区切り（「。」「？」「！」、改行、発言の端）か「…」の印に当たれば、引用として書く
  （文の途中で切って印の無い引用は、後半の条件や否定を落としうる）。これを満たさないとき、記録が添えられていないとき、
  記録が読めない、消えている（Claude Code は古い記録を消す）ときは、「」で括らず要約として書き、食い違いを報告の
  「確認の結果」の「前提」に書く
- ADR や issue に書くユーザーの言葉は、引用は `「<引用>」（ユーザー <日付>）`、要約は括らずに `<要約>（ユーザー <日付>）` と書く。
  日付は JST で書く（上のコマンドが出す。記録の `timestamp` は UTC で、JST の 9 時より前の発言は UTC では前の日になる）。
  分からなければ「日付不明」と書く
- 別のサブエージェントの報告や調査は、確かめてから事実として書く。確かめていなければ「確かめていない」と書く

### 作業中の規則

- 報告は途中で止まらず、最後に 1 度だけ返す。親からの追加の指示は、「報告の催促」と書かれていない限り、作業を続けて
  取り込む（親は追加の指示に「報告の催促ではない」と書く）。取り込む前に、手順 1 の確かめ（CLAUDE.md、
  採用中の ADR、コードの事実との照合と、事実の前提の出典。追加の指示に前提の欄は無いので、事実は欄の外のものとして確かめる）を同じく行い、規則（CLAUDE.md、ADR、このスキル
  以外のスキル。頼む側の書き方の規則と同じ範囲）の例外や別の解釈を書いた指示は、その規則の原文と照らす。食い違うか出典が見つからなければ（「確かめていない」と添えた値は、手順 1 と同じく確かめることが作業になる）、その指示だけを取り込まず、ほかの作業は依頼どおり続け、
  食い違いを最後の報告の「親が先に読む要点」に書く。追加の指示は
  依頼より後に急いで書かれ、規則と照らされていないことがある（2026-10-24 に、親が「割り込まれうる main のジョブの時間も
  `suspended:` が無ければ記録に使える」と伝え、xlc の CLAUDE.md の「付けないジョブは main で、timed のジョブに止められうるので、
  その時間は記録に書かない」と食い違った。2 人の担当が取り込み、レビューの指摘で撤回して再測定した）
- 自分の worktree の外に触らない。ほかの worktree と既定ブランチの作業ツリーを編集しない（マージの実行だけは既定
  ブランチの worktree から。ただし上の「マージの直前で止める」が先）。
  2026-10-14 に、`cd` が別のサブシェルになって `dvc repro` が既定ブランチの作業ツリーで走り、追跡ファイルを書き換えた
- 計算を投げるときは /slurm-run の規則に従う: `cd <worktree> && ~/.claude/scripts/slurm-run.sh ...`、区分と目的は
  完成の形のものを `--class`、`--ref`、`--purpose` に書き、実績のない計算は種類ごとに 1 段階を測ってから本数を掛けて見積もる
- 計算を投げる直前に既定ブランチの進みを見る（手順 8 と同じく `base-moved.sh` を実行して比較元を fetch してから、`git -C <worktree> rev-list --count HEAD..<base>`）。結果を変える変更
  （コード、入力、環境）が入っていれば、先に rebase してから投げる。古い土台のまま投げると、結果が古い方法のものになり、
  投げ直しになる（2026-10-14 に起きた）。rebase は「マージの直前で止める」の例外として、この場合だけ行う
- レビューの周は、/git-merge の「レビュー」の節の「直す指摘の基準」に従う
- 使用量を節約する。同じ測定を繰り返さない。実機の試験や計算は、投げる前に 1 本の見積もりと合計の時間を出し、
  失敗や方針の変更で再実行するときは理由を控え、どちらも報告の「確認の結果」の「計算」に書く。見積もりは、流す前に
  損を数えて方式を選ぶため、理由は、親が外れた方式の再実行を見分けるため。完成の形に本数の上限があれば（待ち行列が
  混むときだけ書かれる）、超えそうなら止まって報告する

## 頼む側（親のセッション）の書き方

手順と報告の形はこのスキルにあるので、依頼には作業ごとに変わることだけを書く:

```text
最初に /delegate を呼び、その手順に従って進める。

リポジトリ: <path>
ブランチ: <branch>
何をするか: <目的と範囲。決定済みの内容（ADR、issue、ユーザーとの合意。ユーザーの言葉は下の項の形で）と、判断が要るときの軸。ユーザーの案は「案（決定ではない）」と親の評価。評価が使う事実を含め、事実は「前提」に書き、本文で要るときは前提の行の語をそのまま書いて指す>
前提: <事実として使う値と前提を 1 行に 1 つ。各行に出典か「確かめていない」。書き方は下の「前提」の項。事実を使わなければ「なし」>
完成の形: <何ができれば終わりか。テストや確認で示す振る舞い。実機の試験や計算があれば目的と区分>
変える範囲: <変えてよいファイルやディレクトリ>
```

- 6 つの欄は、行頭に欄の名前を置き、直後に `:` か `（…）:` を続けた見出しで書く（`前提:`、`前提（確かめていない）:`。
  箇条書きの中の語は見出しに数えない）。依頼をファイルに置くときは、prompt の 1 行目に「依頼文は <絶対パス> にある」と書く。
  空でない最初の行に「/delegate を呼び、」（「呼ぶ。」「呼んで、」など、句読点か行末が続く形）がある Agent の prompt（またはそれが指すファイル）に欠けた欄があれば、
  PreToolUse の hook（claude-hooks の delegate-request-fields）が欠けた欄の名前つきで止める。判定の規則と修正方法は、
  その拒否の文言にある
- 追加の指示を送るときは、報告の催促でなければ「報告の催促ではない」と書く
- 実機の試験や計算には、目的（結果が何を決めるか、きっかけの issue か ADR の番号）と区分（/slurm-run の `timed`、`record`、
  `decision`、`trial`）を完成の形に書く。担当はそれを `slurm-run.sh` のジョブに付け、待ち行列の順は区分で決まる。
  本数の上限は、待ち行列が混む（ほかのセッションのジョブが待っている）ときだけ書く。上限は読み方で守ったかが変わり
  （2026-10-29 に xlc の依頼の「Slurm は 2 本まで」のもとで、担当が 4 本、Elapsed の和で 8 時間 42 分を流した）、見積もりを書かせることも外れた方式の損を
  限ることも果たさなかった。見積もりと再実行の理由は担当が報告に書く
- モデルは依頼文ではなく、サブエージェントを起動するときの指定（Agent の `model`）で渡す
- trailer を依頼に書くときは、`Co-Authored-By:` のモデル名を `<自分のモデル名>` と書き、`Claude-Session:` だけ親の値を
  そのままコピーする。担当のモデルは Agent の `model` で決まり、親の system-reminder の行をそのままコピーすると親のモデル名になって
  担当の system-reminder と食い違う（2026-10-30 に xlc の依頼が親の Fable 5.1 の行をコピーし、Opus の担当が食い違いを報告した）
- Agent の `description` の先頭にモデル名を書く（例: `Opus: 履歴の書き換えツールの PR`）。ユーザーが実行中の一覧で
  モデルを見分けるため。`subagent_type: "fork"` は `model` を無視して親のモデルで走るので親のモデル名を書き、/code-review などスキルが
  起動するものは description を選べないので、起動を伝える文にモデルを書く
- ユーザーへの報告でも、担当に触れるたびにモデルを添える（「履歴の書き換えの担当（Opus）」）
- 決定済みの内容は、どこで決まったか（ADR などの記録の場所、ユーザーの言葉）を添える。サブエージェントの文脈に親の会話は無く、
  ユーザーの言葉は依頼に書いたものしか届かない（会話の記録のファイルは読める）。ADR などの記録の決定は、言い換えずに文を
  コピーする（要る部分だけ。省いたところに「…」を入れる）か、番号と節だけで指す。言い換えると、どの項や量に掛かるか（主語、
  否定、条件）がずれ、担当はそれを決定として設計する（2026-10-30 に xlc の依頼が、ADR-0215 の「第 3 項は … ミクロ燃焼の補正を
  持たない項目（拡散係数、ADF など）では 0」を「持たない項目（拡散係数、ADF、χ、形状関数、k∞）は 0」と R の全体に掛け、「R に書かない形でもよい」と選択肢まで足した。担当が
  ADR と照らして見つけた）
- 依頼と追加の指示でユーザーの言葉（判断、承認、案）を「」で括って引用するときは、会話の記録の `.jsonl` のパスと、その発言の
  `timestamp` を添え、記録からそのままコピーする（語尾や後半を変えない。長ければ要る部分だけを引用し、省いたところに「…」を
  付ける。切る位置は文の区切り（「。」「？」「！」、改行、発言の端）にし、文の途中で切るなら切った端にも「…」を付ける。受ける側は
  両端がこれに当たらない引用を要約に落とす）。記録は `~/.claude/projects/` の下に、会話を始めたディレクトリ（worktree を含む）ごとのディレクトリに会話ごとの
  ファイルで置かれ（ファイル名の ID は `Claude-Session:` の ID とは別）、前の会話の発言も入る。パスと `timestamp` は、
  受ける側の「どの依頼でも守ること」の `jq` のコマンドの `<記録の .jsonl>` に `~/.claude/projects/*/*.jsonl` を渡して引く。
  記録からコピーしない言葉は「」で括らず、`<要約>（ユーザー <日付> の判断の要約）` と書く（日付は JST）。言い換えを「」で
  括ると、受ける側がユーザーの発言として ADR にコピーする（2026-10-29 に xlc の依頼が、ユーザーの発言の語尾を変え後半を
  落として括った）
- 「変える範囲」には、issue の作成と追記を含めると書く。担当が作業中に見つけた別のトピックを、範囲の外だとして報告にだけ
  残さないため
- 前提: 依頼が事実として使う値と前提は、「前提」の欄に 1 行に 1 つ書き、「何をするか」の本文には書かない（両方に
  書くと片方だけ直ってずれる。1 行ずつ出すのは、行ごとに出典を開いたかを書く側も受ける側も見返せるようにするため）。
  各行は出典で確かめて出典を添えるか、確かめていなければ「確かめていない」と添える（欄の無い追加の指示に書く事実も同じ）。外部の値（ツールの既定値、仕様の数値と表の番号、体系の構成）は版と、
  ファイルの行か文書のページや節。対象のリポジトリの事実（何を出力し、何を残すか、入力の中身）はファイルと、関数、型、
  入力の項目などの名前（行は main が進むとずれる）。出力について書くときは、書き出す箇所だけでなく、それを切り替える
  入力の項目と設定も読む。出典は依頼を書く時点で開いた文書の場所か、実行したコマンドとその出力にする（会話で前に見た値は、
  上書きで更新する文書の数値、ADR の status、main が進んだ後の名前など、その後に変わっていることがある）。前に終わった
  計算の結果は、保存されたログや記録を開き直せばよく、計算をやり直さない。確かめていないものは「確かめていない」と書く
  （確かめるのは受ける側の作業になる）。前提が誤ると、担当はそれを土台に設計する。この規則は値と前提に掛かり、決定の
  出典（ADR、ユーザーの言葉）は「何をするか」に添える。測った値に比を掛けた見込み（計算の時間の倍率など）は、「確かめていない」と
  添える行でも、比の元の測定（ジョブやログ。割り込まれず CPU を共有しないジョブか）と、何と何の比かを添える。使う比は、分子が
  見込みを当てる計算と同じ条件で、分母が比を掛ける測定と同じ条件のものだけにする（分母が違う比を掛けると、別の量の見込みになる）
- ユーザーの案を依頼に入れるときは、先に親が評価し、その結果（賛否と理由、成り立つ条件、反例を探した範囲。
  測らないと決められなければその旨と、測る計算の目的と区分を「完成の形」に）を添えて、「何をするか」の
  中で「案（決定ではない）」と明示する。決定と区別せずに書くと、担当は検討せずに作る。成り立たないか、より良い代案が
  あると判断した案は、理由と代案をユーザーに返し、依頼には入れない
- 時間や精度の目標を依頼に書くときは、分かっている内訳のうち、その依頼で手を付けない部分の合計を先に出す。目標が
  その合計以下なら、その部分も範囲に入れるか、目標を上げる。内訳は「前提」の欄に書き、分からなければ、先に測るか「内訳は確かめていない」と書く（2026-10-22 に高速版の依頼へ「1 本 10 分」と書いたが、
  依頼文にある手を付けない部分が MOC 7.4 秒 × 輸送 81 回 ≈ 599 秒 ≈ 10 分で、目標が下限と同じだった。担当は測って未達と報告した）
- 依頼の範囲から外す部分（「〜は変えない」）は、外してよい理由（その部分が目標の精度や速度を満たしている、など）を「前提」の欄に
  出典か「確かめていない」を添えて書く。精度の目標は、変える範囲だけでなく、変える関数とそれから求める関数の定義域の全体（負の側、
  区間の境界、±∞、NaN）を、実装の前に多倍長などの参照と比べる形で「完成の形」に書く（2026-10-28 に erfcx の依頼へ「x < 2.5 の級数の
  側は変えない」「2.5 ≤ x を細かく比べる」と書いたが、級数の側は桁落ちで 16,444 ulp ずれていた。担当はレビューの周ごとに、級数の
  桁落ち、erf と erfc、負の x、±∞ の NaN を 1 つずつ見つけて直し、/code-review を 8 回呼んだ）
- 呼び出しの形（スクリプトの引数、出力の行の形、ファイルの形式、スキルの名前）を変える依頼では、「変える範囲」を書く前に、その形を
  書くか読む（照合する、解析する）リポジトリの中の場所（スクリプト、hook の拒否の文言と照合、スキル、CLAUDE.md、README、ADR、テスト、
  モジュールのコメント）を grep で探し、古い形のものを範囲に入れる。探す語は、スクリプト名、行の見出し、ファイル名、スキルの名前
  （`/` を付けない形。`/名前` とパスにも当たる）で、名前を変えるときは古い名前で探す。ヒットごとに新しい形かを見る（必須の引数を足す変更では、古い形は
  新しい引数が無いことでしか見分けられない）。ADR のヒットは、どこを直してよいかを /adr の「確定後の運用」で決める（凍結する部分、
  決定が変わるときの「## 変更」と置き換え、自由に直せる status とブランチの上の ADR はそこにある）。直さない凍結する部分は、範囲から外す
  場所に数えない。ほかに外す場所は、上の項のとおり理由を「前提」の欄に書き、誰がいつ合わせるかを「何をするか」に書く（これからの作業で、
  事実ではないため。リポジトリの外の呼び出しは、親がマージの後に合わせると書けばよい）。古い形が残ると、担当は
  範囲の外として直さず、親が範囲を広げて続きを頼む周が増える（2026-10-30 に slurm-run.sh へ `--class`、`--ref`、`--purpose` を
  必須にした依頼が、「変える範囲」を slurm-run.sh、スキル、テスト、ADR に限り「hook は変えない」と書いたため、担当は同じリポジトリの
  古い形の呼び出し（グローバルの CLAUDE.md、guard-sbatch の拒否の文言、modules/slurm/common.nix のコメント）を直さず、親が範囲を
  広げて続きを頼む周が増えた。別のリポジトリの xlc の CLAUDE.md は、親がマージの後に合わせる）
- 規則（対象のリポジトリの CLAUDE.md、ADR、delegate 以外のスキル）の解釈や例外を依頼や追加の指示に書くときは、先にその規則の原文を
  読み、場所を添える。規則と食い違う例外は書かず、要るならユーザーに聞くか、先に規則を直す（受ける側は、規則と食い違う追加の
  指示を取り込まずに報告する）
- hook のエスケープの付け方や「〜なら付けてよい」は依頼に書かない（依頼に条件を書くと、サブエージェントはエスケープを
  手順の一部として使う。親が「rebase 後は付けてよい」と書いた依頼で、サブエージェントが未レビューのマージを
  エスケープつきで 2 回試みた）
- 委任の前に、対象のリポジトリで `git -C <リポジトリ> fetch` のあと、同じものを直している PR・ブランチ・worktree が
  無いかを確かめる（`gh pr list`（リモートがあれば）、`git -C <リポジトリ> branch -a`、
  `git -C <リポジトリ> worktree list`）。別のセッションのものがあれば、委任せずその PR に任せるか、マージを待つ。
  自分のセッションが作ったブランチ（コミットの `Claude-Session:` で分かる）への続きの委任は、そのブランチで進める
- 依頼の方式に関わる採用中の ADR を、対象のリポジトリの docs/adr/ で確かめ（`design-records` か
  `grep -l <語> <リポジトリ>/docs/adr/*.md`。status が採用中のものに絞る）、依頼にその番号と「この ADR に従う」か
  「この ADR を置き換える」を書く。ADR の「検討した案」で採らなかった方式は頼まない
- 1 つの成果物（例: 辞書の追加とその調査の結果）は 1 つの PR にまとめて頼む
- 使うツールが追跡されていない場所（`references/`、手元のスクリプト）にあれば、それを昇格させる作業を本作業より先に
  別の依頼で頼み、マージしてから本作業を頼む
- 受けた側の手順 1 の「食い違えば報告に書いて止まる」は、ADR とコードの事実の食い違いに対する安全網である。
  重複する PR や未追跡のツールは拾えないので、上の確認は頼む前に行う
- 報告は確かめる前の暫定として扱う。マージの前に、報告のコミットと確認の結果を自分で確かめる。担当が ADR と issue に書いた
  「」で括ったユーザーの言葉は、受ける側と同じ `jq` のコマンドを `~/.claude/projects/*/*.jsonl` に掛けて同じ文があるかと、
  両端が文の区切りか「…」に当たるかを見て、満たさなければマージの前に要約の形に直す
