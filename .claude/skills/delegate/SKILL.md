# Delegate

親のセッションから頼まれた 1 トピックのブランチ作業を、マージの直前か、5 分より長い待ち（「作業中の規則」）の前まで進める。
依頼に書かれるのは、リポジトリ、ブランチ名、何をするか（決定済みの内容、判断の軸、「案（決定ではない）」と書いた案）、前提
（事実として使う値と前提を 1 行に 1 つ、出典か「確かめていない」を添えて）、完成の形、変える範囲だけで、手順と報告の形はここに
従う。依頼とこの手順が食い違えば依頼を、リポジトリの CLAUDE.md とこの手順が食い違えば CLAUDE.md を優先する。ただし「マージの
直前で止める」と「どの依頼でも守ること」は依頼より優先する（担当の報告は確かめる前の暫定で、マージは親が確かめてから行う）。

担当の cwd は作業する worktree ではない。スキルの `!` 行と引数なしのスクリプトは cwd のブランチを見るので、/gh-pr-create と
/gh-pr-review は Skill で呼ばずに Read で読み、その中のコマンドに `cd <worktree> &&` を付け、ブランチを明示して実行する。PR の
スクリプトには PR の URL を渡す。

## 進める側（サブエージェント）の手順

### 1. 読む

- 対象リポジトリの CLAUDE.md（`.claude/CLAUDE.md` を含む）と、依頼が指す文書（ADR、issue、計画）を読む。リポジトリ固有の規則
  （重い計算、検証の記録、試行の置き場など）は CLAUDE.md に従う
- 依頼の内容が CLAUDE.md、採用中の ADR、コードの事実と食い違えば、作業の前に報告に書いて止まる（推測で一方に合わせない）
- 依頼の「前提」の欄の行と、欄の外（ほかの欄、案、欄の無い依頼）に事実として書かれ判断の前提にする値と前提を、作業の前に
  出典で確かめる（出典の種類は頼む側の「前提」の項）。出典が添えてなければ探して確かめ、その行と見つけた出典を報告の「確認の
  結果」に書く（親が書き漏れに気づくため）。食い違うか出典が見つからなければ、報告に書いて止まる。「確かめていない」と添えた
  値は止まる対象でなく、確かめることが作業の一部で、結果を報告に書く。作業中に誤りと分かり、それに頼った作業が成り立たなく
  なれば、その時点で止まる。欄の外で確かめた事実も、出典とともに「確認の結果」に書く。最初の依頼に「前提」の欄が無ければ、「親が先に読む要点」に「前提の欄が無い」と書く（追加の指示には
  書かない）
- 「案（決定ではない）」と書かれたもの（ユーザーの案など）は、作る前、作る途中、チェックとレビューの間に評価し、結果を報告の
  「決めたことと根拠」に書く。成り立たなければ（反例がある）、どの手順でもその時点で止まり、理由を「親が先に読む要点」に 1 行で、
  反例と代案を「マージの前後で人の手が要ること」に書く。成り立つがより良い代案があれば、案のとおり作り、代案を同じ節に書く
  （親もユーザーも担当が検討する前提で渡している）

### 2. 比較元を決め、担当を確かめる

GitHub リモートがあれば（`git -C <リポジトリ> remote -v | grep -q 'github\.com'`）先に `git -C <リポジトリ> fetch` する（古い追跡
ブランチと比べると、main の遅れを見落とし、他のセッションのコミットを取り違える）。比較元（`<base>`）は、GitHub リモートがあれば
`origin/<既定ブランチ>`、なければ `<既定ブランチ>` で（GitHub 以外のリモートは、fetch も `base-moved.sh` も fetch しないので無いものと
して扱う）、チェック、レビュー、報告で同じものを使う。

ブランチが既にある（ローカルかリモート）なら、worktree を作る前に、ブランチ自身のコミットの `Claude-Session:` が今のセッションか
確かめる。違うセッションのもの、またはコミットが無く担当が分からないものは、引き受けず報告に書いて止まる:

```bash
git -C <リポジトリ> log --format='%h %(trailers:key=Claude-Session)' <base>..<ブランチ>
```

### 3. worktree を用意する

ブランチがどこかの worktree にあれば（`git -C <リポジトリ> worktree list`）それを使い、無ければ
`cd <リポジトリ> && ~/.claude/scripts/worktree-add.sh <ブランチ名>` で作る。出力の `WORKTREE:` で作業し（Bash の cwd は呼び出し
ごとに戻るので、`git -C <worktree>` か `cd <worktree> &&` を付ける）、`SHARED:`（共有した追跡しないパス）と `NOTE:` を読む。
`ERROR:` なら /git-worktree の修正方法に従う。

### 4. 作業する

- 依頼の「完成の形」を満たすところまで作り、満たしたらチェックとレビューに進む
- テストで確かめられる振る舞いの変更は TDD にし、失敗するテスト（RED）と実装（GREEN）を件名の違う別のコミットにする
- 決定は /adr の形で ADR に書く。依頼で決まっていない決定を判断の軸から下したら、報告の「決めたことと根拠」に書く
- proposed の ADR を足すか直したか実装したブランチは、最後の周の前に、ADR ごとに status を /git-merge の「proposed の ADR」の節の
  分け方で決め、その節のとおりに直してコミットする（/git-merge はこれをチェックとレビューの前に決めるので、担当が決めずに報告
  すると、親が直した ADR にもう 1 周が要る）。依頼が結果ごとの条件を書いていればそれに従う。条件が無いまま rejected（実装を外す）
  に当たると判断したときは、外さずに proposed のまま残す（実装を外すことは依頼の外の決定）。ADR ごとの status と根拠を「決めた
  ことと根拠」に、proposed のまま残したものの番号と理由を「マージの前後で人の手が要ること」にも書く（親がマージの本文の Impact に
  コピーする）。周の直しで実装が変わったら決め直す。結果を待つ計算で分け方が決まるときは、計算の後に status を直すコミットを足し、
  その周を歯止めの中に残しておく（ADR の変更は挙動に数える）
- 作業中に見つかった問題は、/topic-triage の「振り分け」の表と目安だけを Read で読んで振り分ける（そこにある別の worktree での
  片付け、マージ、rebase は行わない）。同じトピックなら続け、止めない別のトピックは issue に書いて今のトピックに戻り、止める別の
  トピックは issue に書いて報告して止まる
- 依頼の「変える範囲」の中で変え、範囲の外を変えたものは報告で分けて書く
- セッションの scratchpad は親とほかの担当と共有なので、一時ファイルと退避は `<scratchpad>/<ブランチ名>/` の下に置く（`old/` の
  ような一般の名前は、ほかの担当の退避を黙って上書きしうる）

### 5. コミットする

- 論理的な変更ごとに 1 コミット。Conventional Commits の件名、本文に Why（決定は ADR を参照）。issue や ADR に対応するときは
  `Refs:` を付ける（書式はリポジトリの規則に従う）
- 依頼か system-reminder で指定された trailer を末尾に付ける。`Co-Authored-By:` のモデル名は、コミットする自分のモデル
  （system-reminder のもの）にする（依頼が書いたモデル名は親のもので、コミットを書いたモデルの記録にならない）
- hook に止められたら、示された修正方法に従う。直せなければ、迂回せず（文言や書き方を変えない、エスケープを付けない）報告に
  書いて止まる

### 6. チェックする

チェックの前に `git -C <worktree> status --short` を空にする（チェックとレビューを、マージするものと同じ中身で受けるため。残すと
/git-merge の始めの確認と後片付けの `git worktree remove` も止まる）。追跡しているファイルの変更は、ツールが書き換えたもの
（`dvc.lock`、フォーマッタの修正など）も論理ごとにコミットする。未追跡のファイルは、リポジトリの規則に従ってコミットするか、
`.gitignore` が無視する試行の置き場（リポジトリの規則にあるもの）に移すか、この作業で自分が作った使い捨てなら消す。移したものの
場所と、途中で止まるときに残った変更は「マージの前後で人の手が要ること」に書く（worktree の中の置き場は後片付けで消える）。

```bash
~/.claude/skills/language-checks/scripts/run-checks.sh -C <worktree> --base <base>
```

終了コードで判定する（`tail` などにつなぐと終了コードが消える）。失敗したら原因を直してコミットし、やり直す。CLAUDE.md にチェックの
方法があれば、それも実行する。各コミットでビルドが通るべきブランチ（依存や lock を変えるなど）は、
`cd <worktree> && ~/.claude/scripts/check-each-commit.sh <base> -- <コマンド…>` で `<base>..HEAD` の各コミットを一時 worktree で
調べる（RED を skip でコミットする運用ではビルドだけを通す。任意のコマンドを実行するので許可リストに無く、毎回確認を求められる）。

### 7. レビューを受ける

周ごとに `cd <worktree> && ~/.claude/scripts/review-level.sh <ブランチ名> --base <base>` を実行し、出力の `LEVEL` と `WORKTREE` で
`/code-review <LEVEL> <WORKTREE>` を回す。対象は worktree のパスで渡す（ブランチ名は cwd のリポジトリで解かれ、空振りして「指摘
なし」と返る）。LEVEL はスクリプトが決め、前の周の直しが小さくても自分で下げない。/code-review が background で走ったら終わりの
通知だけで待ち（Monitor、sleep、until のループは足さない）、通知で再開して指摘に対応してから先に進む。

**リモートあり**のときは、続けて PR を出して自動レビューを受ける:

- /gh-pr-create を Read で読み、その形で PR を作る。その「ローカルレビュー（PR を出す前）」の段落は上の周で置き換え（その周も
  /git-merge の「直す指摘の基準」の歯止めに数える）、ほかの規則は従う。`cd <worktree> && git push -u origin <ブランチ名>` と
  `cd <worktree> && gh pr create …` は別々の呼び出しにする（push 前の状態で hook が止める）
- PR の head にローカルレビューの記録（`record-local-review.sh`）があれば、Copilot のレビューを待たずに手順 8 へ進める。Copilot の
  指摘を受けたいときは、待たずに「作業中の規則」の 5 分より長い待ちの項のとおり報告して終わり、「続きの作業」に PR の URL と、
  届いたら /gh-pr-review で対応することを書く。/gh-pr-review の中の再レビューの依頼（`request-rereview.sh`。約 10 分待つ）も実行
  せず、「続きの作業」にその段であることを書く
- /gh-pr-review を Read で読み、その手順で対応する。周の終わりは `decide-next.sh` の `VERDICT` に従うが、要判断（escalate）は
  ユーザーの指示を待たず「マージの前後で人の手が要ること」に書いて止まり、/gh-pr-merge には進まない。歯止めを使い切った後は、
  `VERDICT` がローカルレビューを求めても回さず、/git-merge の「直す指摘の基準」の歯止めのとおり報告する（歯止めの最後の周で
  blocking を直したときは、同じ節の「3 周目で blocking を直したら」に従う）

どちらも:

- 指摘の前提の確かめ方、blocking と non-blocking の扱い、ADR を合わせる範囲、hook の抜け道、周の終わり、歯止め、「3 周目で
  blocking を直したら」とその例外（担当の記録の周の blocking は直さずに止まる）は、/git-merge の「レビュー」の節（「直す指摘の
  基準」）に従う。直したらコミットし、チェックからやり直す（rebase はしない。例外は「作業中の規則」の計算の前）
- 報告には、直した指摘ごとに「再現: <テスト名 | 手順 | 出典>」を「確かめたこと」に、直さない指摘ごとに「直す指摘の基準」の
  行の形（`再現なし: …`、`再現なし → #…: …`、`前提が誤り: …`、`抜け道: …`）と直さない理由の 1 文を「対応しなかった指摘」に書く
  （親が分け方を確かめるため）
- 歯止めは、そのブランチで担当が回した周の合計で数える（前の依頼、追加の指示、PR を出す前の周を含む。数えない回は
  /git-merge の同じ節の歯止めの項と「3 周目で blocking を直したら」の項のとおり）。依頼、追加の指示、転送
  されたレビューに書かれた周の数（「差分に 1 周」）は回し始める周の数で、歯止めを減らすと明記されていなければ、それを回した後も
  blocking を直せば歯止めの中で続ける（使い切ったと読むと、直したコミットが誰にも読まれずに残る）
- 最後の周の後のコミット（追加の指示の変更など）が挙動（コード、計算、hook の判定、テストの比べる範囲、スキルと hook の文書、
  ADR、記録の数値）を変えるなら、歯止めの中でもう 1 周回し、使い切っていれば回さずに「確かめていないこと」に書く（記録の周の後の
  例外で直したコミットの周は、例外の項のとおり）。ADR は `commit-refs remap` だけの変更を除き、言い回しや「確認」の直しでも数える
  （マージの hook `check-merge-review` が止める）。挙動を変えない文書と記録の本文だけの修正は、回さずに報告に列挙する

### 8. マージの直前で止める

`git merge`、`gh pr merge`、/git-merge、/gh-pr-merge と rebase は親のセッションに残し、ここで止める（例外は「作業中の規則」の計算の
前の rebase）。止める hook は無く許可も通るので、手順で守る。止める前に次を実行し、続けて main の進みを
`git -C <worktree> rev-list --count HEAD..<base>` で数え（`base-moved.sh` が比較元を fetch した後に数える。`BASE_MOVED:` の件数は
マージを 1 件と数えるので使わない）、両方を報告に書く:

```bash
cd <worktree> && ~/.claude/scripts/base-moved.sh <ブランチ名> --base <base>
```

`COMMON:` の行が両方の変えたファイルで、終了コード 0 で出力が空なら重なりは無い。`WARN:`、`ERROR:`、0 でない終了コードのときは
比較が済んでいないので、重なりと件数の両方を未確認と書く。重なりの有無はこの出力で書き、記憶や推測で書かない。

### 9. 報告する

報告の前に片付ける:

- 結果を待っている計算（5 分以内の Slurm のジョブ）と /code-review は、終わりの通知で再開して結果を取り込んでから報告する。
  取り込んで変更をコミットしたら、6 のチェックからやり直す
- 自分で張った Monitor や background のコマンドのうち、結果を使わないもの（sleep のタイマーなど）は TaskStop（deferred のときは
  ToolSearch で読み込む）で止める（残すと、その通知で再開して同じ報告を送り直す）。報告の後にタイマーの通知で再開したら、
  「報告は送り済み」の 1 行だけで終える（SubagentHandback は呼ばない）
- `git -C <worktree> status --short` が空であることを確かめる。空でなければ 6 の冒頭のとおり片付け、コミットしたら 6 のチェック
  からやり直す

最後の報告は次の見出しで書く。該当が無い節は「なし」と書き、節を省かない。

```markdown
## 親が先に読む要点
<1〜5 行。途中で止まったときは、どの手順でなぜ止まったか（本文に節が無いため）。最初の依頼に前提の欄が無ければ「前提の欄が無い」（追加の指示には書かない）。親の判断が要ることは、詳しく書いた節を指す>

## ブランチと worktree
- リポジトリ: <path>
- ブランチ: <branch>（<base> から N コミット遅れ | 遅れは未確認（`base-moved.sh` の `WARN:` か `ERROR:`））
- <base> と両方が変えたファイル: <`base-moved.sh` の `COMMON:` のパス | なし | 未確認（`WARN:` か `ERROR:` の内容）>
- worktree: <path>
- PR: <URL | なし>

## コミット
<古い順に `hash 件名` を 1 行ずつ。`git -C <worktree> log --reverse --format='%h %s' <base>..HEAD`>

## 決めたことと根拠
- 依頼の範囲: <決めたこと> — <根拠（ADR、コード、測った値）>
- 変える範囲の外で変えたこと: <変更> — <理由>

## 確認の結果
- 完成の形: <満たしたか。確かめた方法>
- 確かめたこと: <チェックの終了コード、テストの件数、レビューの周と結果、直した指摘ごとの「再現: <テスト名 | 手順 | 出典>」、最後の周を回した HEAD の hash（親はこれより後に挙動を変えるコミットがあるかを見る。リモートなしでは親がマージの本文の `Reviewed:` に書くので、完全な hash か 7 桁以上の短い hash で書く。リモートありでは /gh-pr-review の head ごとの記録に従う。周ごとに HEAD を控え、最後の周の後に rebase や amend をしない）>
- 前提: <出典が添えてなかった行と見つけた出典、欄の外で確かめた事実とその出典、「確かめていない」と添えた値を確かめた結果 | なし>
- 計算: <ジョブごとに番号、区分、目的、投げる前の 1 本の見積もりと合計の時間、実際の時間（`TIME:` 行）、再実行したものはその理由 | なし>
- 確かめていないこと: <未レビューのコミット、実行していないテスト、仮定>

## 対応しなかった指摘
- 再現なし: <指摘の要旨> | 再現なし → #<issue の番号>: <指摘の要旨> | 前提が誤り: <確かめた事実> — <指摘の要旨> | 抜け道: <理由> — <指摘の要旨>。<直さない理由を 1 文>

## マージの前後で人の手が要ること
- <rebase、記録の周の blocking と引いた先、未レビューの変更の判断、proposed のまま残した ADR の番号と理由（マージの本文の Impact に要る）、担当の決めた status を親が変えるかの判断、issue を閉じる、など>

## 続きの作業
<5 分より長い待ちの前で終わったとき（「作業中の規則」の 5 分より長い待ちの項）だけ書き、マージの直前まで済んだら「なし」。
- 親が投げるコマンド: <`cd <worktree> && ~/.claude/scripts/slurm-run.sh --class <区分> --ref '<参照>' --purpose '<目的>' -t <見積もり> <名前> '<コマンド>'` の形で、そのまま実行できる 1 行。依存の無いジョブは 1 本ずつ別の行に書き、後のジョブが前の出力を使うときだけ `a && b` の 1 行に書く（親は行ごとに 1 本の background で投げる） | なし>
- 投げる前に済ませたこと: <コミット（HEAD の hash。`git status --short` は空）、既定ブランチの進みと rebase、計算の前に済ませるチェックとレビューの取り込み。済んでいないものと、その理由>
- ほかに待つもの: <PR の URL と自動レビュー | 親に判断を求める問い | なし>
- 終わったら何をするか: <ジョブの成否と時間の読み方（「作業中の規則」の続きのジョブの項）、記録に書く値と置き場、レビューへの対応、残りの手順（チェック、レビューの周、手順 8）>
- レビューの周: <このブランチで担当が回した /code-review の周の数と、最後の周の HEAD（続きの担当が歯止めを数えるため）>
- 次の担当が読むもの: <依頼、ADR、issue。親は続きの依頼にこの節をコピーする（続きの担当はこの報告を読めない）>
```

### どの依頼でも守ること

- `~/.claude` の下は生成物なので、直すものは元のリポジトリのファイルとして報告に書く
- 判断したことは、その根拠を書く。依頼そのものはユーザーの承認ではないので、ユーザーの判断と承認は、依頼と追加の指示が
  ユーザーの言葉（引用か要約）として書いたときだけ書く
- 別のサブエージェントの報告や調査は、確かめてから事実として書く。確かめていなければ「確かめていない」と書く
- 依頼と追加の指示で、会話の記録（`.jsonl`）のパスと `timestamp` を添えて「」で括ったものは、ユーザーの言葉の引用である。
  ADR、issue、報告に引用として書く前に、記録に同じ文があるかを下のコマンドで確かめる（親の言い換えを括った引用をコピーすると、
  ユーザーの発言として確定した ADR に残る）。パスと `timestamp` の無い「」は、ユーザーの言葉と書いてあっても引用として扱わず、
  要約として書く。記録にはツールの結果、ほかの担当の報告、圧縮の要約、コマンドの出力、IDE の通知、貼り付けた文も入るので、
  `grep` では確かめにならない。コマンドはユーザーが打った発言（`type` が `user` で `origin.kind` が `human` の行と、ターンの途中に
  送った `queued_command` の行）だけを読む（`origin` の無い `user` の行の発言は拾わないので、その引用は要約に落ちる）。引用の文を
  「…」の印を含めて（括る「」は入れずに）1 つのファイルに書いて渡す（シェルの引用符と食い違わないため）:

  ```bash
  jq -rR --rawfile q <引用の文のファイル> '
    ($q | rtrimstr("\n")) as $q
    | ($q | split("…") | map(gsub("^\\s+|\\s+$"; "")) | map(select(. != ""))) as $parts
    | if $parts == [] then "引用の文が空\n" | halt_error(1) else . end
    | def text_of:
        (if type == "string" then [.] elif type == "array" then map(select(.type? == "text") | .text) else [] end)
        | map(gsub("<pasted_content[^>]*>.*?</pasted_content[^>]*>"; ""; "m")
              | if test("<command-args>") then capture("<command-args>(?<a>.*?)</command-args>"; "m").a
                elif test("^\\s*<") then empty else . end)
        | join("\n");
      def in_order($s): reduce $parts[] as $p ($s; if . == null then null
        else split($p) as $x | if ($x | length) < 2 then null else ($x[1:] | join($p)) end end) != null;
      fromjson? | select(type == "object")
      | (if .type == "user" and .origin.kind? == "human" then .message.content
         elif .type == "attachment" and .attachment.type? == "queued_command"
           and (.attachment.commandMode // "prompt") == "prompt"
           and (.attachment.origin.kind? // "human") == "human" then .attachment.prompt
         else empty end | text_of) as $t
      | select($t | in_order(.))
      | "\(input_filename) \(.timestamp) \(.timestamp[0:19] + "Z" | fromdate + 32400 | strftime("%Y-%m-%d %H:%M JST"))\n\($t)\n---"
  ' <記録の .jsonl>
  ```

  出力は、引用を「…」で切った部分がどれも同じ順に出る発言ごとの、記録のパス、`timestamp`、JST の日時と全文（`-R` と
  `fromjson?` は、書きかけの行で止まらないため）。添えられた `timestamp` の発言が出て、引用の両端が全文の文の区切り（「。」「？」
  「！」、改行、発言の端）か「…」の印に当たれば、引用として書く（文の途中で切って印の無い引用は、後半の条件や否定を落としうる）。
  満たさないとき、記録が添えられていない、読めない、消えている（Claude Code は古い記録を消す）ときは、括らず要約として書き、
  食い違いを報告の「確認の結果」の「前提」に書く
- ADR や issue に書くユーザーの言葉は、引用は `「<引用>」（ユーザー <日付>）`、要約は括らずに `<要約>（ユーザー <日付>）` と書く。
  日付は JST で書き（記録の `timestamp` は UTC）、分からなければ「日付不明」と書く

### 作業中の規則

- 報告は途中で止まらず、最後に 1 度だけ返す（下の 5 分より長い待ちの項で終わるときは、その報告が最後の 1 度）。親からの追加の
  指示は、「報告の催促」と書かれていない限り、作業を続けて取り込む。取り込む前に手順 1 と同じく確かめ（事実は欄の外の
  ものとして確かめる）、規則（CLAUDE.md、ADR、このスキル以外のスキル）の例外や別の解釈を書いた指示は、その規則の原文と照らす。
  食い違うか出典が見つからなければ、その指示だけを取り込まず、ほかの作業は続け、食い違いを「親が先に読む要点」に書く（追加の
  指示は急いで書かれ、規則と照らされていないことがある）
- 自分の worktree の外に触らない。ほかの worktree と既定ブランチの作業ツリーを編集しない（`cd` が別のサブシェルになると、
  コマンドが既定ブランチの作業ツリーで走る。マージの実行だけは既定ブランチの worktree からだが、「マージの直前で止める」が先）
- 5 分より長い待ち（Slurm の計算、PR の自動レビュー、親の判断）の前で、待たずに報告して終わる。見積もり（`-t`）が 5 分を超える
  計算は投げない。投げる前に済ませること（コミットして `git status --short` を空にする、下の項の既定ブランチの進みの確認と
  rebase、依頼とリポジトリの規則が計算の前に求めるチェックとレビューの取り込み）を済ませ、手順 8 と 9 のとおり報告し、投げる
  コマンドと済ませたことを「続きの作業」に書いて終わる。投げて待つのは親で、記録とレビュー対応は親が新しい担当に同じブランチの
  続きとして頼む（担当のキャッシュは 5 分ほどで切れ、長い待ちの後に同じ担当が続けると、伸びた文脈の全体を書き直し、その後も
  毎回読み直すため）。自分の文脈の大きさで切る上限は置かない（担当は自分のトークン数を見られず、呼び出しの回数も当てにならない）
- 5 分以内の計算は、/slurm-run の規則に従って `cd <worktree> && ~/.claude/scripts/slurm-run.sh ...` で投げ、終わりまで待って続ける。
  区分と目的は完成の形のものを `--class`、`--ref`、`--purpose` に書き、実績のない計算は種類ごとに 1 段階を測ってから本数を掛けて
  見積もる。親に渡すコマンドも同じ規則で書く
- 親が投げたジョブの続きを頼まれたら、依頼にある親の background の出力のファイルから、ジョブの番号（`JOB:`）、ログ（`LOG:`）、
  成否（`EXIT:`）を取る（`sacct` は allowed-tools に無いので使わない）。親は報告の行ごとに 1 本の background で投げるので、
  `EXIT:` は行のジョブの順に並ぶ（`a && b` の行は、前が失敗すると後は投げられず `EXIT:` が 1 つだけ）。時間とログの中身は `LOG:` の
  ログから読む。投げられなかったジョブ（`JOB:` が無い、`ERROR:` の行がある）は、原因を直してコマンドを報告に書き直す
- 計算を投げる直前と、投げるコマンドを報告に書く直前に、既定ブランチの進みを見る（手順 8 と同じく `base-moved.sh` で比較元を
  fetch してから `git -C <worktree> rev-list --count HEAD..<base>`）。結果を変える変更（コード、入力、環境）が入っていれば、先に
  rebase してから投げる（書く）。古い土台のままでは結果が古い方法のものになり、投げ直しになるため。rebase は「マージの直前で
  止める」の例外として、この場合だけ行う
- レビューの周は、/git-merge の「レビュー」の節の「直す指摘の基準」に従う
- 使用量を節約する。同じ測定を繰り返さない。実機の試験や計算は、投げる前に 1 本の見積もりと合計の時間を出し（流す前に損を
  数えて方式を選ぶため）、失敗や方針の変更で再実行するときは理由を控え（親が外れた方式の再実行を見分けるため）、どちらも報告の
  「確認の結果」の「計算」に書く。完成の形に本数の上限があれば、超えそうなら止まって報告する

## 頼む側（親のセッション）の書き方

手順と報告の形はこのスキルにあるので、依頼には作業ごとに変わることだけを書く:

```text
最初に /delegate を呼び、その手順に従って進める。

リポジトリ: <path>
ブランチ: <branch>
何をするか: <目的と範囲。決定済みの内容（ADR、issue、ユーザーとの合意。ユーザーの言葉は下の項の形で）と、判断が要るときの軸。ユーザーの案は「案（決定ではない）」と親の評価。評価が使う事実を含め、事実は「前提」に書き、本文で要るときは前提の行の語をそのまま書いて指す。ADR を書かせるか実装させるときは、マージでの status を結果ごとの条件で 1 行（下の「ADR を書かせるか」の項）>
前提: <事実として使う値と前提を 1 行に 1 つ。各行に出典か「確かめていない」。書き方は下の「前提」の項。事実を使わなければ「なし」>
完成の形: <何ができれば終わりか。テストや確認で示す振る舞い。実機の試験や計算があれば目的と区分>
変える範囲: <変えてよいファイルやディレクトリと、issue の置き場（docs/issues/ か GitHub の issue）>
```

- 6 つの欄は、行頭に欄の名前を置き、直後に `:` か `（…）:` を続けた見出しで書く（`前提:`、`前提（確かめていない）:`。`（…）` の
  中に出典の括弧を 1 段まで入れてよい。箇条書きの中の語は見出しに数えない）。依頼をファイルに置くときは、prompt の 1 行目に
  「依頼文は <絶対パス> にある」と書く。空でない最初の行に「/delegate を呼び、」（「呼ぶ。」「呼んで、」など、句読点か行末が
  続く形）がある Agent の prompt（またはそれが指すファイル）に欠けた欄があれば、PreToolUse の hook（claude-hooks の
  delegate-request-fields）が止める。判定の規則と修正方法は、その拒否の文言にある
- 「変える範囲」には、issue の作成と追記を含めると書く（欄に `issue` の語が無ければ delegate-request-fields が止める。理由は拒否の
  文言にある）
- 追加の指示を送るときは、報告の催促でなければ「報告の催促ではない」と書く
- モデルは依頼文ではなく、Agent の `model` で渡す
- trailer を依頼に書くときは、`Co-Authored-By:` のモデル名を `<自分のモデル名>` と書き、`Claude-Session:` だけ親の値をコピーする
  （親の行をそのままコピーすると親のモデル名になり、担当の system-reminder と食い違う）
- Agent の `description` の先頭にモデル名を書く（例: `Opus: 履歴の書き換えツールの PR`。ユーザーが実行中の一覧で見分けるため）。
  `subagent_type: "fork"` は `model` を無視して親のモデルで走るので親のモデル名を書き、/code-review などスキルが起動するものは
  description を選べないので、起動を伝える文にモデルを書く。ユーザーへの報告でも、担当に触れるたびにモデルを添える
- 依頼は 5 分より長い待ち（Slurm の計算、PR の自動レビュー、親の判断）で切る（例:「実装して計算のコマンドを書くまで」と「記録と
  レビュー対応」）。担当は長い待ちの前で報告して終わるので、待ちの後の作業まで 1 つの依頼に入れると毎回やり残しになる。待ちの
  後に同じ担当を起こして続けさせない（理由は「作業中の規則」の 5 分より長い待ちの項）
  - 計算: 報告の「続きの作業」のコマンドを、報告の行ごとに 1 本の `run_in_background=true` の Bash で、そのまま実行する（依存の
    無いジョブは 1 行 1 本、`a && b` の行はそのまま。出力の `EXIT:` が行のジョブの順に並び、続きの担当が成否をジョブに対応づけ
    られる）。投げる直前に、担当の項と同じく `base-moved.sh` で比較元を fetch してから `git -C <worktree> rev-list --count HEAD..<base>`
    を見て、結果を変える変更（コード、入力、環境）が既定ブランチに入っていれば、投げずに続きの担当に rebase を先に頼む。すべての
    background の終わりの通知を待ってから、出力のファイルのパスだけを続きの依頼の前提の欄に書き（ジョブの番号、ログ、成否は続きの
    担当が読む）、前の報告の「続きの作業」を何をするかと完成の形にコピーして、新しい担当に同じブランチの続きとして頼む。親は出力の
    ファイルとログを、Grep でも Bash でも読まない（親の費用は文脈の大きさで決まり、読んだログはその後の毎回の読み出しと書き直しに
    残るため）。通知が来るまで、そのジョブの worktree を変える続きの依頼は出さない（ジョブは走りながら worktree の入力を読み、出力を
    書くので、途中で変えると記録と違う版で走る）
  - PR の自動レビュー: 止まった担当には通知が来ないので、親が /gh-pr-review の手順のとおり background で待つ（担当が再レビューの
    依頼の段で止まったときは `request-rereview.sh <PR の URL>`、ほかは `gh-wait-review.sh <PR の URL>`。終了コードの扱いは
    /gh-pr-review に従う）。計算と両方を待つ報告は、自動レビューの続きを計算の続きと同じ担当に、計算の後で頼む
- ADR を書かせるか実装させる依頼と、そうする追加の指示には、その ADR をマージでどの status にするかを、/git-merge の「proposed の
  ADR」の節の分け方（全部を実装、一部を実装、試して採らない、試しただけ、決定だけ）ごとに、accepted、proposed、rejected（実装を
  ブランチから外す）のどれかで書く（担当の扱いは手順 4。担当の周の後に親が accept を指示すると、直した ADR にもう 1 周が要る）
- 追加の指示でレビューの周を頼むときは、「<base>（手順 2 の比較元。最後の周の HEAD ではない）より後の差分に周を回す」と書き、
  報告の時点で最後の周の後に挙動を変えるコミットが無いことを求める。周の終わり、歯止めの数え方、3 周目で直したときの扱いと周の
  数（「差分に 1 周」）は書かず、手順 7 の「どちらも」の項に任せる（書き直した文は規則が変わっても残り、周の数は上限と読まれる）
- 実機の試験や計算には、目的（結果が何を決めるか、きっかけの issue か ADR の番号）と区分（/slurm-run の `timed`、`record`、
  `decision`、`trial`）を完成の形に書く。本数の上限は、待ち行列が混む（ほかのセッションのジョブが待っている）ときだけ書く（上限は
  読み方で守ったかが変わり、外れた方式の損を限らない。見積もりと再実行の理由は担当が報告に書く）
- 決定済みの内容は、どこで決まったか（ADR などの記録の場所、ユーザーの言葉）を添える（担当の文脈に親の会話は無く、ユーザーの
  言葉は依頼に書いたものしか届かない）。ADR などの決定は、言い換えずに要る部分の文をコピーする（省いたところに「…」）か、番号と
  節だけで指す（言い換えると、どの項や量に掛かるか（主語、否定、条件）がずれ、担当はそれを決定として設計する）
- ユーザーの言葉（判断、承認、案）を「」で括って引用するときは、会話の記録の `.jsonl` のパスとその発言の `timestamp` を添え、
  記録からそのままコピーする（語尾や後半を変えない。長ければ要る部分だけを、文の区切り（「。」「？」「！」、改行、発言の端）で
  切って引用し、省いたところと、文の途中で切った端に「…」を付ける。受ける側は両端がこれに当たらない引用を要約に落とす）。記録は
  `~/.claude/projects/` の下の、会話を始めたディレクトリ（worktree を含む）ごとのディレクトリにあり（ファイル名の ID は
  `Claude-Session:` の ID と別）、パスと `timestamp` は受ける側の `jq` のコマンドに `~/.claude/projects/*/*.jsonl` を渡して引く。
  記録からコピーしない言葉は括らず、`<要約>（ユーザー <日付> の判断の要約）` と書く（日付は JST。言い換えを括ると、受ける側が
  ユーザーの発言として ADR にコピーする）
- 前提: 依頼が事実として使う値と前提は、「前提」の欄に 1 行に 1 つ書き、「何をするか」の本文には書かない（両方に書くと片方だけ
  直ってずれる。1 行ずつなのは、行ごとに出典を開いたかを両方が見返せるため）。各行は出典で確かめて出典を添えるか、「確かめて
  いない」と添える（前提が誤ると、担当はそれを土台に設計する。確かめるのは受ける側の作業になる。欄の無い追加の指示の事実も同じ）。決定の出典（ADR、ユーザーの言葉）は
  「何をするか」に添える
  - 出典の種類: 外部の値（ツールの既定値、仕様の数値と表の番号、体系の構成）は版と、ファイルの行か文書のページや節。対象の
    リポジトリの事実（何を出力し、何を残すか、入力の中身）はファイルと、関数、型、入力の項目などの名前（行は main が進むとずれる）。
    出力について書くときは、書き出す箇所と、それを切り替える入力の項目と設定も読む。出典は依頼を書く時点で開いた文書の場所か、
    実行したコマンドとその出力にする（前に見た値は、その後に変わっていることがある）。前に終わった計算の結果は、保存された
    ログや記録を開き直せばよく、計算をやり直さない
  - 比を掛けた見込み（計算の時間の倍率など）は、「確かめていない」と添える行でも、比の元の測定（ジョブやログ。割り込まれず
    CPU を共有しないジョブか）と、何と何の比かを添える。分子が見込む計算と同じ条件で、分母が比を掛ける測定と同じ条件の比だけを
    使う（分母が違う比を掛けると、別の量の見込みになる）
  - 記録の値（検証の記録、比較の JSON、担当の報告の数値）は手でコピーせず、出典（JSON のパスとキー、記録の節の名前）で指すか、
    その時点に出典から値を出したコマンドと出力を貼る（手でコピーすると、開いた出典が正しくても写し間違える）。範囲（a〜b）は列の min と max を計算して書く（列は単調とは限らない）。担当の
    報告の値は、報告が拠った記録か JSON を開いて取る（報告の後に書き直されているか、別の点の集まりを比べていることがある）
  - 原因の見方（どの量が差を生むか）を依頼の理由に使うときも 1 行で書き、その量の語で open の issue と ADR の「候補」「確かめて
    いない」の行を検索して、既存の分析と食い違わないことを確かめ、拠った issue か ADR の節を出典に添える（食い違う見方を書くと、
    担当は既存の分析と照らすところから始める）
- ユーザーの案を依頼に入れるときは、先に親が評価し、その結果（賛否と理由、成り立つ条件、反例を探した範囲。測らないと決められ
  なければその旨と、測る計算の目的と区分を「完成の形」に）を添えて、「何をするか」の中で「案（決定ではない）」と明示する（決定と
  区別せずに書くと、担当は検討せずに作る）。成り立たないか、より良い代案があると判断した案は、理由と代案をユーザーに返し、依頼には
  入れない
- 時間や精度の目標を書くときは、分かっている内訳のうち、その依頼で手を付けない部分の合計を先に出し、目標がその合計以下なら、
  その部分も範囲に入れるか目標を上げる。内訳は「前提」の欄に書き、分からなければ、先に測るか「内訳は確かめていない」と書く
- 依頼の範囲から外す部分（「〜は変えない」）は、外してよい理由（目標の精度や速度を満たしている、など）を「前提」の欄に出典か
  「確かめていない」を添えて書く。精度の目標は、変える関数とそれから求める関数の定義域の全体（負の側、区間の境界、±∞、NaN）を、
  実装の前に多倍長などの参照と比べる形で「完成の形」に書く
- 呼び出しの形（スクリプトの引数、出力の行の形、ファイルの形式、スキルの名前）を変える依頼では、「変える範囲」を書く前に、その形を
  書くか読む（照合する、解析する）リポジトリの中の場所（スクリプト、hook の拒否の文言と照合、スキル、CLAUDE.md、README、ADR、
  テスト、モジュールのコメント）を、スクリプト名、行の見出し、ファイル名、スキルの名前（`/` を付けない形。名前を変えるときは古い
  名前）で grep し、ヒットごとに新しい形かを見て、古い形のものを範囲に入れる（必須の引数を足す変更では、古い形は新しい引数が
  無いことでしか見分けられない）。ADR のヒットは、直してよい所を /adr の「確定後の運用」で決め、直さない凍結する部分は外す場所に
  数えない。ほかに外す場所は、上の項のとおり理由を「前提」の欄に、誰がいつ合わせるかを「何をするか」に書く（リポジトリの外の
  呼び出しは、親がマージの後に合わせると書けばよい）。古い形が残ると、担当は範囲の外として直さず、続きの依頼が増える
- 規則（対象のリポジトリの CLAUDE.md、ADR、delegate 以外のスキル）の解釈や例外を依頼や追加の指示に書くときは、先にその規則の
  原文を読み、場所を添える。規則と食い違う例外は書かず、要るならユーザーに聞くか、先に規則を直す（受ける側は取り込まずに報告する）
- レビューの (c)（/git-merge の「直す指摘の基準」）を担当に直させる依頼と追加の指示には、指摘ごとに、何が引いた先と食い違うかと、
  どの出典で直すかだけを書き、直した後の文と値は書かない（担当がそのまま入れると、親の誤りが次の周の (c) になる）
- hook のエスケープの付け方や「〜なら付けてよい」は依頼に書かない（担当はエスケープを手順の一部として使う）
- 委任の前に、対象のリポジトリで `git -C <リポジトリ> fetch` のあと、同じものを直している PR・ブランチ・worktree が無いかを
  確かめる（`gh pr list`（リモートがあれば）、`git -C <リポジトリ> branch -a`、`git -C <リポジトリ> worktree list`）。別のセッションの
  ものがあれば、委任せずその PR に任せるか、マージを待つ。自分のセッションが作ったブランチ（コミットの `Claude-Session:` で
  分かる）への続きの委任は、そのブランチで進める
- 依頼の方式に関わる採用中の ADR を、対象のリポジトリの docs/adr/ で確かめ（`design-records` か `grep -l <語> <リポジトリ>/docs/adr/*.md`。
  status が採用中のものに絞る）、依頼にその番号と「この ADR に従う」か「この ADR を置き換える」を書く。ADR の「検討した案」で採らな
  かった方式は頼まない
- 1 つの成果物（例: 辞書の追加とその調査の結果）は 1 つの PR にまとめて頼む
- 使うツールが追跡されていない場所（`references/`、手元のスクリプト）にあれば、それを昇格させる作業を本作業より先に別の依頼で
  頼み、マージしてから本作業を頼む（受ける側の手順 1 の止まる条件は ADR とコードの食い違いの安全網で、重複する PR や未追跡の
  ツールは拾えないので、ここまでの確認は頼む前に行う）
- 報告は確かめる前の暫定として扱う。マージの前に、報告のコミットと確認の結果を自分で確かめる。担当が ADR と issue に書いた「」で
  括ったユーザーの言葉は、受ける側と同じ `jq` のコマンドを `~/.claude/projects/*/*.jsonl` に掛けて同じ文があるかと、両端が文の
  区切りか「…」に当たるかを見て、満たさなければマージの前に要約の形に直す
