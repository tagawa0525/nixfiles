# ADR

何をなぜ決めたかを、1 件 1 決定で残す。

## どのプロジェクトで使うか

自分のプロジェクトの ADR はこの形で書く。他人のプロジェクトでは、そのプロジェクトの流儀（テンプレート、
CONTRIBUTING）に従う。既存の ADR が別の形の自分のプロジェクトでは、新しい ADR からこの形で書き、既存の ADR を
揃えるかはプロジェクトごとに決める。

## ADR にするもの

作り直したときに他へ波及する決定を ADR にする（データの形式、モジュールの境界、外部への依存、検証の方法など）。
範囲、期間、危険、費用のどれかが大きい決定も同じ。作り直しても他に波及しない決定、規約で決まっていること、
一時的な回避策や実験は、issue の「経緯」か、コミットの本文に書く。

## ファイル

- 置き場所は `docs/adr/NNNN-verb-phrase.md`。4 桁の連番と、決めたことを動詞で始めた英語の kebab-case
  （例: `0006-adopt-madr-for-adrs.md`）
- 番号は既存の最大 + 1。一度使った番号は、ファイルが残っていなくても使い回さない
- 一覧のファイルは作らない。採用中の ADR は `grep -l '^status: accepted$' docs/adr/[0-9]*.md` で引く

!`git ls-files docs/adr`

## テンプレート

```markdown
---
status: proposed
date: YYYY-MM-DD
requires: []
supersedes: []
superseded-by:
issues: []
---

# ADR-NNNN: {決めたことを 1 文で}

## 背景

{何を決める必要があるか。前提と制約。2〜3 文か、具体的な状況で書く。関係する issue や資料へのリンク}

## 決定の要因

- {判断の軸。例: 精度、速さ、保守性、外部の依存を増やさないこと}

## 検討した案

- {案 1}
- {案 2}

## 決定と理由

採用: 「{案 1}」。理由は{要因のどれを満たすか、測った値や出典}。

### 帰結

- 良い点: {…}
- 悪い点: {…}
- 見直す条件: {…}

### 確認

{決定どおりに実装されたことを何で確かめたか。テストの名前、比較と判定の閾値、レビュー。確かめるものが無い約束事なら、
そう 1 行で書く}

## 各案の長所と短所

### {案 1}

{例、説明、資料へのリンク}

- 良い点: {…}
- どちらでもない: {…}
- 悪い点: {…}

## 補足

{決定を裏付ける資料、ほかの ADR や issue へのリンク}
```

## 前付け

キーは 1 行に 1 つ、一覧は `[a, b]` の形で 1 行に書く（grep で引けるように）。

| キー            | 書くもの                                                                                                                                                                                                                            |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `status`        | `proposed`（書いている途中）、`accepted`（採った）、`rejected`（決めて採らなかった）、`withdrawn`（決める前に取り下げた）、`deferred`（決めるのを後回しにした）、`superseded`（置き換えられた）、`deprecated`（置き換えずに廃れた） |
| `date`          | 最後に status が変わった日                                                                                                                                                                                                          |
| `requires`      | 前提にしている ADR（例: `[ADR-0002]`）。その ADR を置き換えるときは `grep -l 'requires:.*ADR-0002' docs/adr` で見直す ADR を引く                                                                                                    |
| `supersedes`    | この ADR が置き換えた ADR                                                                                                                                                                                                           |
| `superseded-by` | この ADR を置き換えた ADR。古い ADR だけを読んでも置き換えに気づけるよう、置き換えは両方の ADR に書く                                                                                                                               |
| `issues`        | きっかけになった issue と、この ADR で解決した issue（例: `["#12"]`）                                                                                                                                                               |

## 節

| 節               |      | 書くもの                                                                                                     |
| ---------------- | ---- | ------------------------------------------------------------------------------------------------------------ |
| 背景             | 必須 | 何を決める必要があるか、前提と制約                                                                           |
| 決定の要因       | 任意 | 案を比べる軸                                                                                                 |
| 検討した案       | 必須 | 比べた案の名前。採った案も含める                                                                             |
| 決定と理由       | 必須 | 採った案と、なぜか。ユーザーが決めたならそう書く                                                             |
| 帰結             | 推奨 | 良い点、悪い点、見直す条件。実装が決定に追いついていなければ、その差を書き、issue を立てて `issues` に入れる |
| 確認             | 推奨 | 決定どおりかを何で確かめたか                                                                                 |
| 各案の長所と短所 | 任意 | 案ごとの良い点と悪い点。検討した案だけで足りれば書かない                                                     |
| 補足             | 任意 | 裏付けの資料、関係する ADR と issue、確定後に分かったこと                                                    |

- 見出しは英語（MADR の原文: Context and Problem Statement / Considered Options / Decision Outcome / Consequences /
  Confirmation）でもよい
- 任意の節は、要るときだけ書く。表に無い節を足してもよい
- 測った値や、変わりうる値（費用、規模）には、出典のファイルとコミットと日付を添える
  （例: 「1B で −3080 pcm（examples/vera/verification.md、a0af869、2026-10-07）」）

## 運用

決定の中身は変えず、変えるときは新しい ADR で置き換える。マージした後の作り直しも同じで、ADR は増えていくことを
前提にする。今の決定は `status: accepted` で引き、過去の判断は置き換えのリンクで辿る。

- **proposed の間**: 実装の前に proposed で書き、自由に直す。実装をマージするブランチで、本文（「確認」の実際の
  テストと結果、「帰結」）を実装に合わせて直し、同じ変更で `status: accepted` にして `date` をその日にする
- **確定した後**（accepted、rejected、withdrawn、superseded、deprecated）に新しい ADR なしで直すのは、次だけ:
  - 誤字、文法、マークアップ、壊れたリンク
  - 前付けの `status`、`superseded-by`、`date`
  - 「補足」の節への、日付つきの追記（`- YYYY-MM-DD: …`）。決定の後に分かったことのうち、決定を変えないもの
- **決定を変えるとき**: 新しい ADR を書き、新しい方の `supersedes` と古い方の `superseded-by` で結び、古い方を
  `status: superseded` にする。新しい ADR は、古い決定のうちまだ有効な部分を書き直して含める（採用中の ADR だけで
  今の決定が分かるように）。前の決定を採って戻したなら、その理由と測った値を新しい ADR の「検討した案」に書く
- main にマージする前は、ブランチの上の ADR を status によらず直してよい
