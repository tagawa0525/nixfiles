# ADR

何をなぜ決めたかを、1 件 1 決定で残す。

## このリポジトリの扱い

!`git config --default unset --get claude-hooks.own-project`

`false` なら他人のプロジェクト。このスキルの形ではなく、そのプロジェクトの流儀（テンプレート、CONTRIBUTING）に
従い、以下は使わない。`unset` は、最初に `docs/adr/` へ書くときに hook が remote から判定して書き込む。

## 手元の ADR を手本にしない

既存の ADR は形の手本ではなく、下の形に照らして評価する対象。欠陥を見つけたら真似ず、直す提案をする
（別のトピック。/topic-triage）。

## 形（MADR に倣う）

```markdown
---
status: accepted          # proposed / accepted / superseded by ADR-NNNN
date: YYYY-MM-DD
---

# ADR-NNNN: <決定を 1 文で>

## 背景
## 検討した案
## 決定と理由
## 帰結
## 確認
```

- **背景**（必須）: 何が問題で、何を満たす必要があるか。制約と要求
- **検討した案**: 比べた案と、それぞれの長所・短所。採った案に「（採用）」
- **決定と理由**（必須）: 選んだ案と理由。誰の判断か（ユーザーの判断なら明記）
- **帰結**: 決定から恒久的に生じること。良い面、悪い面、続く制約や運用（例: ホストを足すたびに鍵を足す）
- **確認**: 決定どおりに実装されたことを何で確かめたか

節はこの 5 つだけ（hook の `check-adr-sections` がコミット時に検査する）。

## 書かないもの

| 書きたくなるもの                                           | 置き場所                                                                 |
| ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| ホストやリポジトリの今の状態（何が残っている、何を消した） | 書かない。状態は変わり、ADR が古くなる                                   |
| 未解決の問題、やること                                     | issue                                                                    |
| コードや設定の写し                                         | コミットハッシュやファイルへの参照。写しは古くなる                       |
| 手順書（導入・再開の手順）                                 | 手順の置き場（README、docs、そのコードのリポジトリ）。ADR からは参照する |
| 実装の細部（競合状態、エッジケース）                       | 実装の PR でテストとともに                                               |

## 番号

!`ls docs/adr`

最大の番号 + 1。1 ブランチに新しい ADR は 1 件（hook が 2 件以上を止める）。
