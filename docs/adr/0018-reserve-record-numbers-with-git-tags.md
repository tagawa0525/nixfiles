# ADR-0018: 設計の記録の番号を git のタグで予約し、ぶつかった番号は design-records で振り直す

## 背景

`design-records new`（ADR-0009）は、ローカルの全ブランチの履歴と作業ツリーから次の番号を振る。これでは番号が
ぶつかる経路が 2 つ残る。

- 作ってからコミットするまでの間に、別のセッションが `new` を走らせると、同じ番号になる。2026-10-11 に xlc で
  ADR-0127 がぶつかった
- PR の流れ（別の clone、別のマシン）では、ほかの clone のブランチはローカルの履歴に無いので、数えられない

xlc の衝突は、マージのときに `cargo test`（crates/docs の検査）が見つけ、番号の振り直しはファイル名、表題、参照を
手で付け替えた。docs/issues の issue も同じ規則（全ブランチで最大の番号 + 1、使い回さない）で番号を振るので、
同じ衝突が起きる。

## 決定の要因

- 番号を決めることと予約することを 1 つの不可分な操作にする（compare-and-swap）。調べてから書くまでの間に
  ほかの人が割り込めない
- 予約の場所は、すべての clone から見え、main の履歴とブランチの保護を汚さない
- 予約が漏れて衝突したときも、振り直しを手作業にしない
- 番号は使い回さない（ADR-0009。古い参照が別の記録を指してしまう）

## 検討した案

- 案 A: 予約を main に直接 push する（予約のコミットを main に積む）
- 案 B: 予約だけを置く孤立したブランチ（`reservations` など）にコミットして push する
- 案 C: 注釈つきのタグ `adr-NNNN`（`issue-NNNN`）を打って push する

## 決定と理由

採用: 「案 C」。タグの作成は ref の作成なので、ローカルでは `git tag` が、リモートでは `git push` が、同じ名前が
既にあれば拒む。これがそのまま compare-and-swap になる。作業ツリーにもブランチの履歴にも何も足さない。

採らなかった案:

- 案 A: main への直接の push は、hook（`guard-git-push`、`block-main-commit`）と GitHub の branch protection で
  禁じている。予約のために例外を作ると、禁止の判定が複雑になる。main の履歴に、書きかけの記録（予約だけで
  終わったもの）のコミットが残る
- 案 B: チェックアウトしていないブランチにコミットするには、plumbing（`git commit-tree`、`git update-ref`）で
  コミットを組み立てる。push が拒まれたら（先に誰かが予約した）、fetch して積み直す手順が要る。タグなら 1 回の
  ref の作成で済む

### 予約（`new`）

- `origin` があれば、先に `refs/tags/adr-*`、`refs/tags/issue-*` を、次に origin の既定ブランチ（origin の HEAD が
  指すブランチ。指す先が無ければ `main`、`master` のうち origin にあるもの）を fetch する。タグを先に取るのは、
  ほかの clone がマージを push してから予約を解放するため（後に取るブランチには、そのとき消えていたタグの記録が
  入っている。逆の順では、間にマージと解放が起きると、マージ前のブランチと消えたタグを見て番号を使い回す）。既定ブランチも取ってくるのは、`prune` が予約を解放した後の番号が、origin の
  既定ブランチの履歴にしか残らないため。タグはリモートを正として、同じ名前の手元のタグ（push の前に止まった
  予約）を上書きし、origin で消えたタグ（ほかの clone の `prune` と `renumber` が解放したもの）は手元からも消す。
  `--prune` は同じ fetch の refspec の行き先をすべて刈るので、タグだけの fetch に付ける（ブランチの fetch に
  付けると、origin に無いリモート追跡ブランチまで消える）。タグを打つ先は、この fetch の
  後の origin の既定ブランチで決める。番号は、全ブランチの履歴、作業ツリー、その種類のタグ（`adr-NNNN` か
  `issue-NNNN`）のうち最大の番号 + 1 にする
- 番号を決めたら、注釈つきのタグ（メッセージは slug）を既定ブランチの先端に打つ。`origin` があれば、取ってきた
  origin の既定ブランチの先端に打ち、`git push origin refs/tags/<tag>` する。ローカルの既定ブランチに打つと、
  まだ push していないコミットがタグと一緒にリモートに出てしまう。origin に既定ブランチが無ければ、手元の古い
  `origin/*` に落ちずに止める
- push が失敗し、リモートにそのタグがある（ほかの人が先に予約した）なら、ローカルのタグを消し、fetch して次の
  番号でやり直す。リモートにタグが無い失敗（通信の失敗など）は、ローカルのタグを消して止める（予約できない
  まま番号を振らない）。ローカルの `git tag` が拒まれた（同じ clone の別のセッションが先に予約した）ときも
  やり直す
- 浅い clone では止める。履歴が切った先を返さず、マージした記録の予約は `prune` で消えるので、切った先で消した
  記録の番号を数えられない
- `origin` が無ければ、ローカルのタグだけで予約する。コミットが 1 つも無いリポジトリは、タグを打つ先が無いので
  止める
- ファイルは予約が済んでから書く
- 予約（fetch、タグの作成、push）と解放（`prune`、`renumber` の旧番号の解放）は、clone の中で 1 つずつ行う。共有する
  git のディレクトリの `design-records.lock` を flock する。fetch の `--prune` は、同じ clone のほかのセッションが
  打って push する前のタグも消すので、重ねると同じ番号のタグが打ち直され、両方の push が通る

### 振り直し（`renumber`）

`design-records renumber [--kind adr|issue] <旧番号> [<新番号>]`。新番号を省けば `new` と同じ規則で振って予約する。
新番号を渡したときも、その番号のタグで予約する（既に使った番号なら止める）。

- 振り直す記録は、旧番号のファイルのうち、既定ブランチとの分岐点に無いもの（このブランチで足したもの）。ちょうど
  1 つでなければ止める。既定ブランチにある記録の番号は変えない（既に参照されている）。分岐点は、ローカルの既定
  ブランチ（/git-merge が rebase する先）と、取ってきた origin の既定ブランチ（PR の base）のうち新しい方で取る。
  共通の祖先の無いブランチ（orphan）は比べず、どちらとも無ければ基準なしにする（すべての記録と行が振り直しの
  対象になる）
- ファイル名と表題を変え、追跡しているファイル（振り直す記録を含む）のうち分岐点から足した行の参照を付け替える。
  rebase した後の重複では、同じ番号の参照が 2 つの記録を指している。main から来た行の参照は、main の記録を
  指すので変えない。振り直す記録の前付けの参照（`requires`、`blocked-by` など）も変えない。記録の前付けは
  自分を指さないので、同じ番号は既定ブランチの記録を指す
- 足した行は、hunk の見出しの範囲でなく `+` の行で数える（`diff.interHunkContext` で hunk がまとまると、範囲に
  変えていない行が入る）
- 付け替える参照は、ADR なら `ADR-NNNN`、issue なら `#NNNN`（どちらも 4 桁、前後が英数字でない。`check` と
  同じ読み方）と、両方の `NNNN-<slug>.md`（振り直す記録の slug のもの。3 桁で振った記録の `NNN-<slug>.md` も）
- 作業ツリーと index に変更（追跡していないファイルを含む）があれば止め、変更を 1 つのコミット（`docs: renumber ADR-0018 to ADR-0019` など）に
  する。書き換えかコミット（pre-commit の hook など）が失敗したら、HEAD に戻して止める。予約した番号は欠番になる
- 旧番号を既定ブランチ（origin があれば origin の）の記録も使っていて（重複を直す振り直し）、振り直した記録が
  旧番号を予約していたら（タグの slug がその記録のもの）、そのタグを消す。旧番号は既定ブランチの記録が使って
  いるので、使い回されない。ローカルの既定ブランチにしか無い記録の番号は、ほかの clone から空いて見えるので、
  予約を残す。残すと、
  `check` が既定ブランチの記録に、slug の違う予約の注意を出し続ける
- 重複の無い振り直しでは、旧番号の予約を残す。旧番号を使う記録はほかに無いので、消すとほかの clone がその番号を
  振る。残った予約は、その番号のファイルが無いので `check` の注意にならない

### 検査（`check`）

- docs/issues の番号の重複を、ADR と同じく違反にする。issue の前付けと節の形は検査しない（#270 で決める。それまで
  各リポジトリの検査に任せる）
- 番号を予約したタグの slug が、その番号のファイルの slug と違えば注意を出す（ほかの記録が予約した番号を使って
  いる）
- `check` は fetch しない。pre-commit で毎回のコミットに通信が入り、手元に通信が無いとコミットできなくなる。
  手元のタグは `new`、`renumber`、`prune` の fetch で更新される。rebase した後の番号の重複は、作業ツリーの
  ファイルどうしで見つかるので、タグを取ってこなくても `check` が示す。/git-merge は rebase の直後に `check`
  を走らせ、重複があれば `renumber` で直す

### 解放（`prune`）

`design-records prune` は、予約したタグのうち、既定ブランチの履歴にそのタグの記録（`docs/adr/NNNN-<slug>.md` か
`docs/issues/NNNN-<slug>.md`）があるものを、ローカルと `origin` から消す。履歴に記録が入った番号は、
履歴を数えるので、タグが無くても使った番号として残る。タグを消すのは、マージした記録ごとに 1 つずつタグが
積み上がり、`git tag` の一覧と fetch が記録の数に比例して重くなるため。既定ブランチの履歴に無い記録（マージ
しなかったブランチのもの）のタグは消さない。消すとその番号が使い回される。

`origin` があれば、既定ブランチの履歴は、取ってきた `origin` の既定ブランチで見る（手元の origin/HEAD の
symref には頼らない）。ローカルでマージして push する前に
リモートのタグを消すと、ほかの clone がその番号を予約できてしまう。`post-merge-cleanup.sh` は、予約のタグが
あれば、既定ブランチを最新にした後に `prune` を呼ぶ。design-records が PATH に無いときと origin に届かないときは、
タグを残して後片付けを続ける（残ったタグは番号を使い回させず、次の `prune` で消える）。`prune` そのものが
失敗したら、ブランチを消す前に `ERROR:` で止まる（原因を直して走らせ直せる）。

### CLI の形

種類は `--kind adr|issue`（省けば adr）で選び、サブコマンド（`new`、`renumber`）は ADR と issue で共有する。
今の CLI は `check --changed` のように、サブコマンドの後ろのオプションで振る舞いを変えている。`design-records issue
new` のように種類ごとのサブコマンドの木にすると、`check`、`status`、`prune`（種類を問わない）と形が揃わない。
issue の `new` は、番号を予約して `docs/issues/NNNN-<slug>.md` に表題の行（`# <title>`）だけを書く。前付けと節の
形は #270 で決める。

どのコマンドも、前に `-C <dir>` を付けると `<dir>` で走る（git の `-C` と同じ）。/git-merge は対象のブランチの
worktree を `git -C` で指して操作するので、`check` と `renumber` も同じ形で呼ぶ。

### 帰結

- 良い点: 同じ clone の並行したセッションと、ほかの clone やマシンの `new` が、同じ番号を振らない
- 良い点: rebase で見つかった重複を、`renumber` の 1 コマンドで直せる。main から来た参照は変えない
- 悪い点: `new` が通信を要する。`origin` に届かなければ記録を作れない（予約しないまま振ると衝突しうるので、
  止める）
- 悪い点: 予約だけして記録を作らずに終わった番号は、タグが残って欠番になる（使い回さない規則のとおり）
- 悪い点: 予約のタグの slug と違う slug でマージした記録（ファイル名の slug を後から変えた）のタグは、`prune` が
  消さない。`check` の注意で気づける
- 悪い点: ほかの clone のローカルのタグは、その clone が `new`、`renumber`、`prune` で fetch するまで残る（普通の
  `git fetch` はタグを消さない）。番号は履歴にあるので、残っても番号の計算は変わらない
- 実装が決定に追いついていない点: 機能を足す前に作った記録（タグの無いもの）は予約されていない。ぶつかったら
  rebase の後の `check` で見つけ、`renumber` で直す

### 確認

- CLI のテスト（`modules/home/parts/design-records/tests/cli.rs`）: 一時的なリポジトリと bare のリモートで、
  予約のタグ、タグの番号を避けること、push が拒まれたときの振り直し、届かないリモートで止まること、`renumber`
  が main から来た参照を変えないこと、issue の予約と振り直し、issue の番号の重複、`prune` がマージした記録の
  タグだけを消すこと
- `post-merge-cleanup.sh` のテスト（`.claude/tests/scripts/git-workflow.sh`）: マージした記録のタグをローカルと
  リモートから消し、マージしていない記録のタグを残す

## 補足

実装の途中で試して変えた版:

- **予約のタグの fetch に `--prune` を付けない版**: ほかの clone の `renumber` が origin から消したタグが手元に
  残り、`check` が既定ブランチの記録に、slug の違う予約の注意を出し続けた
- **`--prune` を付け、排他しない版**: 同じ clone の 2 つのセッションで、先のセッションが push する前のタグを次の
  セッションの fetch が消し、次のセッションが同じ名前のタグを打ち直して、両方の `new` が同じ番号を振った
  （`tests/cli.rs` の `sessions_in_one_clone_do_not_share_a_number_while_one_is_pushing` で再現した）
- **リモートの予約を別の名前空間（`refs/reservations/origin/*`）に取り、そこだけを prune する案**: 試す前に退けた。
  予約のタグは既定ブランチのコミットを指すので、普通の `git fetch` がタグを自動で `refs/tags` に取ってくる。
  そのタグは消されずに残るので、`--prune` を付けない版と同じ注意が出る
