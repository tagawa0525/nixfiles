# ADR-0008: ADR の形は MADR へのリンクと違う点だけをスキルに書き、雛形はスクリプトで作る

## 背景

ADR-0006 で ADR の形を MADR 基準に決め、スキル `adr` に MADR を元にしたテンプレート、節ごとの説明、前付け、運用を
すべて書いた（141 行）。MADR はモデルが知っている標準なので、書き写した分はスキルが読まれるたびの費用になり、
MADR との違いがどこかも読み取りにくい。番号付けや前付けのように決定的に決まる部分も、モデルがテンプレートから
毎回書き写していた。ADR-0006 は、ユーザーが方向に同意する前にマージされた（ADR-0006 の補足）。

## 決定の要因

- 標準に寄せるところは標準に任せ、調整はその差分だけを持つ
- 決定的に処理できることはスクリプトと検査に寄せ、非決定的で高価なモデルに任せない
- スキルは、それだけを読んで ADR を書ける

## 検討した案

- スキルには MADR へのリンクと違う点だけを書き、雛形はスクリプトで作る
- スキルに MADR を元にしたテンプレートと節の説明をすべて書く（ADR-0006）
- スキルには MADR へのリンクと違う点だけを書き、雛形はモデルが書く

## 決定と理由

採用: 「スキルには MADR へのリンクと違う点だけを書き、雛形はスクリプトで作る」。ユーザーが同意した方向。MADR の
中身はリンクでモデルに伝わり、スキルには調整だけが残る。番号、前付け、必須と推奨の見出しは `new-adr.sh` が作る。

採らなかった案:

- テンプレートと節の説明をすべて書く（ADR-0006）: MADR と同じ内容を、スキルが読まれるたびに読ませることになる。
  MADR と違う点が全文に埋もれ、どこを調整したのかが読み取れない
- 雛形はモデルが書く: 番号、前付けのキー、見出しは決まった値なので、モデルに書かせると揺れる。番号は作業ツリーの
  ADR だけを見て振ると、削除した ADR や別のブランチの ADR と重なる

ADR-0006 の決定のうち、次は引き継ぐ:

- **形の基準**: MADR 4.0.0。見出しは日本語（英語の原文でもよい）。節を足すことは許し、必須は背景・検討した案・
  決定と理由、推奨は帰結・確認
- **前付け**: `requires` / `supersedes` / `superseded-by` / `issues` を独立したキーにし（xlc の前付けと PEP の
  Requires から）、status に `withdrawn` と `deferred` を足す（PEP、KEP）。置き換えを status の文中に書く MADR の形
  では、grep で辿りにくい
- **ADR にするもの**: 作り直したときに他へ波及する決定と、範囲、期間、危険、費用のどれかが大きい決定
- **運用**: proposed の間は自由に直し、実装をマージするときに accepted にする。確定後は誤字、文法、マークアップ、
  リンク、前付けの status、補足への日付つきの追記だけを直す（PEP 1 と、lsp-det の日付つきの「追補」から）
- **ADR は増えていく前提にする**: LLM が決めてマージし、後で見直して作り直すことが多くなる。そのたびに新しい ADR で
  置き換え、前の判断の全文をファイルとして残す。書くのは LLM なので件数の手間は小さく、今の決定は
  `status: accepted` で引ける
- **検査**: 全プロジェクト共通の Claude Code の hook ではなく、各プロジェクトがオプトインする一般的な道具で行う。
  検査の本体を 1 つの flake に置き、各プロジェクトが git-hooks.nix で取り込む（#269）。全体の hook では、他人の
  プロジェクトかの判定に抜けが続いた

### 帰結

- 良い点: スキルが 141 行から 59 行になり、MADR と違う点がそのまま読める
- 良い点: 番号は全ブランチの履歴から振るので、削除した ADR や、別のブランチでコミットした ADR と重ならない。桁数に
  よらず数えるので、3 桁で振っていたプロジェクトでも続きから振る
- 悪い点: 別の worktree でまだコミットしていない ADR は見えないので、番号が重なりうる（#269 の検査で捕まえる）
- 悪い点: MADR の中身はモデルの知識に頼る。MADR の版が上がってモデルの知識とずれたら、リンク先と照らす必要がある
- 見直す条件: 検査を作るとき（#269）

### 確認

- `.claude/tests/scripts/adr.sh` で、番号（削除済み、まだコミットしていない、別のブランチにだけある、3 桁の ADR を
  数える）、前付け、見出し、slug の検査を確かめた
- この ADR は `new-adr.sh` で作った

## 補足

- 雛形をスクリプトで作るのは、決定的な部分をスキルの文章ではなくスクリプトに置く方針による
- ADR-0006 から外したもの: 節ごとの説明とテンプレートの全文（MADR に任せる）、「各案の長所と短所」の書き方の例
- `new-adr.sh` を使うことは強制しない。新しい ADR の Write を Claude Code の hook で止めてスクリプトへ寄せる形は
  考えられるが、全プロジェクトに効くので、他人のプロジェクトの ADR まで自分の形に寄せてしまう。自分のプロジェクトかの判定は ADR-0006 で抜けが続いて捨てた。番号の重複と形の崩れは、
  プロジェクトの側の検査（#269）で捕まえる

この PR で試して捨てた版:

- **MADR と違う点を、見出し、前付け、status だけに絞った版**: 試して捨てた方式の置き場所、決定と実装のずれを issue に
  すること、前の決定に戻すときの書き方、確定した status の一覧、`requires` を辿る見直しまで落ちた。どれも MADR に
  無いので、リンクでは伝わらない
- **作業ツリーの ADR の一覧をスキルに差し込む版**: 番号は `new-adr.sh` が振るので要らない。一覧は削除した ADR や
  別のブランチの ADR を含まず、スクリプトと違う番号を示してしまう
- **4 桁の番号だけを数える版**: pleasanter-rs のように 3 桁で振っていたプロジェクトでは、0001 から振り直した
