# ADR-0066: ローカルの /code-review は再現を書ける指摘だけを直し、それが無い周で終える

## 背景

ローカルの `/code-review` の周の打ち切りは、指摘の内容で決めていた（/git-merge の「レビュー」の節と、/delegate の
「作業中の規則」）。精度（正しさ、数値、記録と出力の一致）と速度に関わる指摘が出る限り直して回し、指摘が文言・構成・
置き場だけになったら打ち切る。この規則は 2026-10-14 に、文言の指摘で周が回り続けたことを受けたもの。周の数は
/git-merge が 13〜15 周、/delegate が 13 周と書いていて、食い違う（どちらも記録で数え直していない。担当と親のどちらが
回したかも確かめていない）。

2026-10-29 に、/delegate の担当 3 本がこの規則の下で次の周を回した（周の数は担当の報告による。記録で数え直していない）:

- nixfiles PR #513 の担当: `/code-review high` を 10 周回し、11 周目の結果を待つ途中で引き渡しを求められて止まった。
  PR は作っておらず、push もしていなかった。報告によれば、指摘はスキルの経路と既存のコードのエッジケースに移っていた。
  親の追加の指示で打ち切り、push した head でさらに 2 周回した（合計 12 周）
- /retro の担当（ユーザーの言葉の引用。ADR-0065 のブランチ）: `/code-review high` を 8 周回しても指摘は尽きなかった。
  8 周目には、決定の前提そのものの誤りが見つかった
- xlc の履歴の ADR の担当: `/code-review high` を 5 周回した。周ごとの指摘は、どれも精度に関わるもの（文献の読み方、
  主張の数値、測った量の区別など）だった

どの担当も規則に違反していない。レビューは周ごとに新しい候補を出すので、直した文や、それまで見ていなかった
エッジケースから、精度に関わる指摘が出続ける。「精度に関わるか」は、指摘を直す側（担当か親のモデル）が自分で付ける
分類で、外から確かめる基準が無い。`/code-review` の出力にも重大度は無い。

この ADR の最初の版（PR #517 の途中まで）は、周を 3 周に限る案（下の案 B）だった。ユーザーは「回数を決めるのではなく
内容で決められないものなんですか？」「重大度とか精度とか明確な基準があるわけでもないんですよね？世間一般ではどういう基準を
設定しているんですか？…軽く調査してから基準を提案して」（ユーザー 2026-10-29）と問い、親が下の世間の基準を調べて提案した
ところ、「君が運用しやすい方針を取ってくれればいいよ」（ユーザー 2026-10-29）と答えた。この版の基準は親が決めた。

世間の基準（2026-10-29 に各ページを開いて確かめた）:

- Google の eng-practices（[The Standard of Code Review](https://google.github.io/eng-practices/review/reviewer/standard.html)）:
  全体のコードの健全性を確実に改善する状態になったら、完璧でなくても承認する。重要でない指摘には「Nit:」を付けて、
  直さなくてよいと示す。周の回数の上限は書いていない
- [Conventional Comments](https://conventionalcomments.org/): 指摘に issue、suggestion、nitpick などのラベルと
  (blocking)、(non-blocking) の印を付ける。nitpick は性質上 non-blocking とする
- SonarQube（[10.3 の Issues](https://docs.sonarsource.com/sonarqube-server/10.3/user-guide/issues)）: 重大度は
  ソフトウェアの品質への影響で決まり、編集できない。旧来の BLOCKER と CRITICAL は、本番の挙動に影響する確率の高低で分ける
- AI のレビューの指摘が尽きない問題は世間でも同じで、対策に、バグ、セキュリティ、大きな保守の費用など実際の問題の強い
  根拠があるものだけを出す設定と、止める規則（テストとチェックが通り、重大な指摘が残っていなければ承認）の事前の合意が
  挙がっている（[掲示板の質問と回答](https://yomotherboard.com/question/how-do-we-stop-ai-assisted-code-reviews-from-becoming-endless-nitpicking/)。
  逸話で、測った値は無い）

このプロジェクトで違うのは、レビューも修正もモデルで、周ごとに新しい候補が出ることと、重大度を修正する側が自分で付ける
ことである。世間の基準のうち「重大度」と「重要でない」は、ここでは自己申告になる。「落ちるテストか再現する手順を書けるか」は、
報告を読む側が確かめられる。

周の数を決めない形は ADR-0023 と ADR-0027 の決定でもある。ADR-0023 は、スキル（gh-pr-merge、gh-pr-review、
gh-pr-create、git-push、git-merge）から周回数の記述を消し、ローカルレビューの周は回数でなく「その周に検証できる
誤りが無ければ終わり」を終わりの条件にした（レビューは周ごとに新しい候補を出すので、指摘ゼロを待たない）。ADR-0027 は、周の終わりを既存のスキルの条件に揃え、branch-task（今の delegate）で
独自の周回数を決めないとした。2 つのスキルの終わりの条件が食い違うと、サブエージェントはどちらかに違反するため。

Copilot の周には以前、上限（5 周）があった。ADR-0034 は上限を 2〜3 に下げる案を、2 回目以降でも新しい High が出る
レビューが Balanced で 30〜38%、Lite で 17% あり、回数で切るとそれを落とすとして採らなかった。ADR-0043 は head の
ローカルレビューの記録で終わる形にして上限を外した（`decide-next.sh` の `ROUND` は情報だけ）。High の残る記録は
レビュー済みとして数えない（ADR-0043、/gh-pr-review の「ローカルレビュー」）。

## 検討した案

- 案 A: 指摘の種類で打ち切る（今）。上の 3 件のとおり、「精度に関わる」指摘は周ごとに出続けて止まらない
- 案 B: 回数の上限だけ（3 周。この ADR の最初の版）。指摘の中身によらず 3 周目で止め、3 周目は High だけを直す。
  ADR-0034 が Copilot の上限を下げなかった理由（後の周でも新しい High が出る）がそのまま当たり、4 周目以降の誤りを落とす。
  3 周目の High の修正はレビューを受けない。High と Medium の分け方は自己申告のままで、Medium に下げれば直す義務が消える
  （#518 の 4、5）
- 案 C: 重大度で決める（High だけを直す）。SonarQube のような、影響で決まり編集できない重大度は、ここには無い。
  `/code-review` の出力に重大度は無く、修正する側が付けるので、案 A と同じく止まるかどうかが自己申告に依る
- 案 D: 周の上限を `review-level.sh` の LEVEL で変える（例: high は 3 周、medium は 1 周）。LEVEL は差分のファイルの
  場所（`docs/` の外があるか）で決まり、周が収束するかとは関わらない。上の 3 件はどれも high だった
- 案 E: 指摘の数で止める（ある周の指摘が N 件以下なら終える）。周ごとの件数は、PR のある head の記録
  （2026-10-12 に足した `record-local-review.sh`。コミット 4c44082a、決定は ADR-0034）にしか無く、PR を出す前の周とリモートの無いリポジトリには無いので、
  N を決める根拠が無い。件数の少ない周にも誤動作はありうる
- 案 F: 再現を書ける指摘だけを直し、それが無い周で終える（採用）。分け方を「落ちるテストか再現する手順を先に書けるか」
  「一次情報で確かめたか」に置き、読む側が確かめられる形にする。回数の上限は歯止めとして残す

## 決定と理由

案 F にする。直す指摘を、世間の blocking と non-blocking の分け方（Conventional Comments）に寄せ、blocking の判定を
自己申告の重大度でなく、確かめられる再現に置く。

- **直す（blocking）**:
  - (a) 通常の入力と流れで到達する誤動作、誤った数値、データの破損、セキュリティの欠陥、ゲートの迂回で、落ちるテストか
    再現する手順を先に書けるもの。スキルと hook の文書の、手順のとおりに実行すると失敗する誤り（壊れたパス、無い
    `VERDICT` の名前）も、その実行を再現の手順として (a) に数える
  - (b) ADR-0067 が凍結する部分（背景、決定の要因、検討した案、決定と理由、各案の長所と短所、表題、フロントマターの `requires` と `supersedes`）の事実の誤りで、一次情報で確かめたもの。
    マージの後に凍結する部分を直すには「## 変更」が要り、誤った決定が前の文として記録に残る。だからマージの前に直す。
    ADR の帰結と確認は、ADR-0067 のとおりマージの後にその場で直せるので、(b) に数えない（引いた先の一次情報との食い違いと出どころの抜けは下の (c)）
  - (c) issue、計画、検証の記録の本文と、ADR の凍結しない部分（帰結、確認など）が、引いた先の一次情報（表、比較の JSON、
    ログ、sacct、コミット）と食い違う値・符号・事実を指す語（ジョブの状態など）、または、そのリポジトリの CLAUDE.md か記録の
    規則が求める出どころ（コミットと日付など）の抜け（規則が無いリポジトリでは、出どころが無いことを (c) に数えない）。再現は、食い違いなら
    出典、抜けなら規則が求める出どころの項目と抜けている箇所と、見つけた引いた先。(a) と (b)
    と同じく blocking に数える（記録の周の後の扱いは「3 周目で blocking を直したら」の例外の項）。言い回しの指摘と、引いた先が
    見つからない出どころの抜けは、再現を書けないので (c) に入らず non-blocking。引いた先そのもの（検証の記録の表、計算が出した
    値）の誤りは計算の結果で、(a) の誤った数値として扱う。本文と引いた先のどちらが誤りかは、引いた先が別の一次情報から描かれた
    もの（検証の記録の表は比較の JSON から）ならその元を開いて決め、元と食い違えば引いた先の誤りで (a) の誤った数値として扱う。
    それでも決められないものは、どの周でも issue に書いてユーザーに判断を求め、答えが来るまでマージしない。スキルと hook の文書と
    ADR の凍結する部分は (c) に入らず、(a) か (b) に当たるものだけ blocking。当たらないもの（実行しても失敗しないスキルの文の
    食い違い）は non-blocking で issue
- **直さない（non-blocking）**: それ以外の全部（契約の外の呼び出し、将来の形式の変更への備え、効率、重複、文言、置き場、
  スキルの文の改善）。1 件の issue にまとめ、担当は報告の「対応しなかった指摘」、親はマージの本文の Impact に issue の番号を
  書く。マージの後に別のトピックで扱う。担当が残した non-blocking を親の周で直すこともしない（直した修正はレビューを
  受けず、修正が新しい誤りを作ることがある。2026-10-29 に、nixfiles PR #509 の 2 周目のレビューが見つけたのは、1 周目の
  修正 5f1b82e1 が作った誤りだった）。ただし (a)〜(c) のどれかに当たり、親が再現を書けた指摘は、担当の分け方の誤りとして blocking に数えて直す（直すのは親か新しい担当で、報告を返して終わった担当は起こさない。親の周と記録の周の blocking も同じ。数行の直しは親が直し、大きければ新しい担当に同じブランチの続きとして頼む。記録の周の後の例外も同じ）。
  前提が誤っていた指摘と、無いものとして扱う hook の抜け道の指摘は、issue にせず、確かめた事実か理由を書く
- **修正方法**: blocking を直すときは、指摘の前提に加えて、直した後の文の数値と主張も引いた先の一次情報で計算し直すか
  開き直して確かめてから、コミットする。指摘の前提だけを確かめて直すと、直した文そのものが次の周の blocking になる
- **終わり**: その周に blocking が無ければ終わり。blocking を直したら、直した差分を焦点に書いてもう 1 周回す（/code-review の
  引数の後ろの文で焦点を示す。レビューする差分はブランチ全体）
- **歯止め**: 回数の上限として、担当も親も 1 つのブランチで 3 周を残す（重大度の自己申告がずれたときのため。普段は
  届かない）。数え方は、対象を見つけられなかった回とエラーの回を数えず、rebase の後の周を数え、追加の変更があっても
  数え直さない。挙動を変えない文書（issue、計画、説明の文書。ADR、スキルと hook の文書、CLAUDE.md、記録の数値を変えるものを除く）だけの
  ブランチは 3 周でなく 1 周（担当のブランチは担当の 1 周、親が書いたブランチは親の 1 周）で、その周で直したら記録の周を回し、
  例外の周は回さない。記録の周の blocking が (c) だけなら、親が一次情報で確かめて直し、リモートの無いリポジトリでは周を回さずにマージする（マージの
  本文の `Reviewed:` は記録の周の head。リモートありでは /gh-pr-merge が記録の無い head を止めるので、直した head に 1 周を回して記録する。どちらが誤りかを決められないものは (c) の定義のとおり、(a) が 1 件でもあれば下の「最後の周で直したとき」のとおり
  issue に書いてユーザーに判断を求める）
- **周の費用**: 親が回す周は Opus で回す（/code-review は呼んだ側のモデルの fork で走るので、Agent の `model` で Opus を指定した
  担当に /code-review を呼ばせる）
- **最後の周で直したとき**: 担当でも親でも、3 周目で blocking を直したら、直した head に記録のための 1 周を回す（3 周に
  数えない）。この周の指摘は直さない。blocking（直しきれずに同じ指摘が出たものを含む）が無ければ、その head を記録して
  （リモートありでは `record-local-review.sh`、担当は報告の最後の周の HEAD）マージに進む。blocking があれば、直しを戻さず、
  マージせず、blocking を issue に書いてユーザーに判断を求める。マージの hook のエスケープ（`ALLOW_UNREVIEWED_HEAD`）は
  使わない。直しを読んだだけでは、直しが作った誤りを見落とす。
  ただし記録の周の blocking が (c) だけのときは、次の例外に従う。確認で (a) に変わったものを含め、(a) か (b) が 1 件でもあれば
  例外に入らず、上のとおり issue に書いてユーザーに判断を求める。担当は自分の記録の周で blocking が出たら、例外に入るかによらず直さず、報告の「マージの前後で人の手が要ること」に blocking と引いた先を書いて止まる（「対応しなかった指摘」には書かない）。親は blocking ごとに引いた先の一次情報を開いて (c) に
  当たるかを確かめる（どちらが誤りかの決め方と、決められないときの扱いは (c) の定義のとおり）。決められないものが無ければ、確かめ
  られたものをユーザーの判断を待たずに直す。決められないものがあれば、答えを待ってから、確かめられたものと答えで直すものを
  まとめて直す（答えで直したものの指摘の行は「再現: <出典>」）。直す主体は「直さない」の項の「ただし」の文の括弧のとおり。直した head に、
  直した箇所を焦点に例外の周を 1 周回し、記録する head はその後に取り直す。この周は記録の周と同じく 3 周に数えず、その周の
  blocking も同じく扱う（(c) だけならまた親が確かめてから直して（主体は同じ）回し、無ければその head を記録してマージに
  進む）。例外の周は 3 周までで、3 周目にも blocking が出たら直さず、issue に書いてユーザーに判断を求める。直した指摘が次の周にも出たときは、上のとおり issue に書いてユーザーに判断を求める。前提が誤っている再出（本文は
  直っている）は「前提が誤り」で数えず、再現できる再出だけを止める合図にする。直した誤りと周の数はマージの本文の Impact に書く。3 周に数えないのは、この
  直しが 3 周と記録の周の後に来るので、数えると 1 周も回せないため。(c) に限るのは、直しが作りうる誤りも同じ文書の
  中にあって次の周が読み、ユーザーに聞く往復が誤りの大きさに見合わないため
- **客観性**: 担当は報告の「対応しなかった指摘」と「確かめたこと」で、指摘ごとに「再現: テスト名か手順か出典」か
  「再現なし → issue の番号」を付ける。親はそれを読んで確かめる。歯止めの 3 周を使い切った後の変更（追加の指示など）は
  回さず、未レビューとして報告する

2026-10-29 の例: xlc の core のミクロ燃焼のブランチ（マージ 596c24372）は、親の 1 周目の指摘（収率の割合の内挿が 1 を超え、
公称でない状態で燃焼が止まる）をテスト（f8432bdd2）で再現して直し、親の 2 周目の指摘は入力の検査と効率だけで、issue に
まとめて終わった。PR #517 は、親の見立てでは、この基準なら担当の 1 周目で終わっていた（周ごとの指摘を記録で数え直していない）。

ADR-0067 の運用で、ADR-0023 の決定と理由（ローカルレビューの終わりの条件と、スキルに書く周回数）と ADR-0027 の決定と理由
（branch-task の周の終わり）を今の決定に直し、それぞれの「## 変更」に前の文と理由を書いた。「検証できる誤り」を上の
blocking に絞り、歯止めの 3 周（/git-merge、/gh-pr-create、/gh-pr-review、/gh-pr-merge と /delegate に書く。エスケープ名と
Copilot の周の回数は書かないまま）が加わる。どちらの ADR も、ほかの部分は変わらない。ADR-0027 が避けたスキルどうしの食い違いは、規則の本文を
/git-merge の「レビュー」の節の 1 か所に置き、/delegate、/gh-pr-create、/gh-pr-review からはそこを参照して避ける。

### 帰結

- 周は、blocking の無い周で終わる。2026-10-29 の 3 件（10 周、push した head でさらに 2 周（合計 12 周）、8 周、5 周）のように、精度に関わると自分で分けた指摘で周が続くことは
  減る見込み（確かめていない。次の担当の報告の周の数で見る）
- 再現を書けない指摘（読んで誤りに見えるが、テストも手順も (c) の出典も書けないもの）は直さず issue に残る。本当に誤りなら、マージの後の
  issue と人のレビューで拾う
- 担当の報告の指摘ごとの「再現」の欄で、親は分け方を確かめられる。欄が無いか、再現が書かれていない修正があれば、親は
  その分け方を疑う
- 最後の周で blocking を直した head も、記録の周を受けてから main に入る。記録の周で blocking が出たときはマージせず、
  issue に書いてユーザーが決める。ただし blocking が (c) だけなら、親が確かめ、親か新しい担当が直し（直す主体は
  決定の「直さない」の項の「ただし」の文の括弧のとおり）、直した箇所に例外の周を 3 周まで重ね、周の数をマージの本文で伝える。挙動を変えない
  文書だけのブランチは、blocking が (c) だけなら周を重ねずに直してマージする。どちらが誤りかを決められない
