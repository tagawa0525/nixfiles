# ADR-0066: ローカルの /code-review は /delegate の担当と /git-merge の親で 3 周までとし、残りの指摘は issue にまとめる

## 背景

ローカルの `/code-review` の周の打ち切りは、指摘の内容で決めていた（/git-merge の「レビュー」の節と、/delegate の
「作業中の規則」）。精度（正しさ、数値、記録と出力の一致）と速度に関わる指摘が出る限り直して回し、指摘が文言・構成・
置き場だけになったら打ち切る。この規則は 2026-10-14 に、文言の指摘で 13〜15 周回ったことを受けたもの（/git-merge の
記述。/delegate は 13 周と書いていた。担当と親のどちらが回したかは確かめていない）。

2026-10-29 に、/delegate の担当 3 本がこの規則の下で次の周を回した（周の数は、親が受け取った各担当の報告から）:

- nixfiles PR #513 の担当: `/code-review high` を 10 周回し、11 周目の結果を待つ途中で引き渡しを求められて止まった。
  PR は作っておらず、push もしていなかった。報告によれば、指摘はスキルの経路と既存のコードのエッジケースに移っていた。
  親の追加の指示で打ち切り、push した head でさらに 2 周回した
- /retro の担当（ユーザーの言葉の引用。ADR-0065 のブランチ）: `/code-review high` を 8 周回しても指摘は尽きなかった。
  8 周目には、決定の前提そのものの誤りが見つかった
- xlc の履歴の ADR の担当: `/code-review high` を 5 周回した。周ごとの指摘は、どれも精度に関わるもの（文献の読み方、
  主張の数値、測った量の区別など）だった

どの担当も規則に違反していない。レビューは周ごとに新しい候補を出すので、直した文や、それまで見ていなかった
エッジケースから、精度に関わる指摘が出続ける。指摘の種類では周が止まらない。

周の数を決めない形は ADR-0023 と ADR-0027 の決定でもある。ADR-0023 は、スキル（gh-pr-merge、gh-pr-review、
gh-pr-create、git-push、git-merge）から周回数の記述を消し、ローカルレビューの周は回数でなく「その周に検証できる
誤りが無ければ終わり」を終わりの条件にした（レビューは周ごとに新しい候補を出すので、指摘ゼロを待たない）。ADR-0027 は、周の終わりを既存のスキルの条件に揃え、branch-task（今の delegate）で
独自の周回数を決めないとした。2 つのスキルの終わりの条件が食い違うと、サブエージェントはどちらかに違反するため。

Copilot の周には以前、上限（5 周）があった。ADR-0034 は上限を 2〜3 に下げる案を、2 回目以降でも新しい High が出る
レビューが Balanced で 30〜38%、Lite で 17% あり、回数で切るとそれを落とすとして採らなかった。ADR-0043 は head の
ローカルレビューの記録で終わる形にして上限を外した（`decide-next.sh` の `ROUND` は情報だけ）。High の残る記録は
レビュー済みとして数えない（ADR-0043、/gh-pr-review の「ローカルレビュー」）。

## 検討した案

- 案 A: 周の上限を決めない（今）。上の 3 件のとおり、指摘の内容の規則では止まらない
- 案 B: 3 周の上限。4 周目は回さず、残った指摘は issue にまとめる
- 案 C: 周の上限を `review-level.sh` の LEVEL で変える（例: high は 3 周、medium は 1 周）。LEVEL は差分のファイルの
  場所（`docs/` の外があるか）で決まり、周が収束するかとは関わらない。上の 3 件はどれも high で、medium の
  （`docs/` だけの）ブランチには、すでに「文書と数値だけの変更は、事実の誤りに絞った 1 周で終わる」がある。
  分けても上の 3 件の扱いは変わらない
- 案 D: 指摘の数で止める（ある周の指摘が N 件以下なら終える）。周ごとの件数は記録に残っていない（/gh-pr-review の
  台帳は PR の周だけ）ので、N を決める根拠が無い。件数の少ない周にも High はありうるので、件数では重さを落とす

## 決定と理由

案 B にする。ユーザーが決めたのは /delegate の担当の上限で、親の推し（/delegate に 3 周の上限を足し、4 周目以降は回さず
残りの指摘は issue にまとめる）に対して「1、2 とも推奨に従います。」（ユーザー 2026-10-29）。親（/git-merge）にも同じ上限を
置くことと、3 周目の指摘の細かい扱いは、この ADR を書いた担当が、親の依頼の推し（親にも 3 周。親は担当の後の追加の周なので、
通常 1 周）に沿って決めた（下の「親の上限」）。これは ADR-0023 の「ローカルレビューの周回は回数ではなく「その周に検証できる誤りが無ければ終わり」を
終了条件にする」の部分と、ADR-0027 の「branch-task で独自の周回数を決めない」の部分を置き換える。終わりの条件は残り、
3 周の上限がそれに加わる。どちらの ADR も、ほかの部分は変わらない。ADR-0027 が避けたスキルどうしの食い違いは、同じ上限を
/git-merge の親の周にも置き、/gh-pr-review の「High は直して回し直す」との関係を両方のスキルに書き、/gh-pr-create の
周と終わり方は /delegate の規則で置き換えると /delegate に書いて避ける。

- **数え方**: 1 周は、ブランチに `/code-review` を 1 回回し、差分を読んだ結果が返ること（LEVEL、PR を作る前
  （/gh-pr-create）か後かを問わない。対象を見つけられなかった回とエラーの回は、ほかのスキルと同じく未実施で、数えない）。
  担当と親は別々に数える。担当は、親の追加の指示が新しい変更（依頼の範囲の追加）を頼んだときだけ、その変更から数え直す。
  rebase の後に回す周（親の、衝突を解いた、main の変更が同じファイルに触れたときの周と、担当の、計算を投げる前の周）は、
  残りの周があればその 1 周として数え、3 周を使い切った後なら上限の外で回す（main と合わせた中身はまだ誰も見ていない）。
  上限の外の周の指摘は 3 周目と同じく扱う
- **打ち切りの順**: 指摘の内容の規則（文言・構成・置き場だけの周で打ち切る、文書と数値だけの変更は 1 周）は、上限の
  前に止まる条件として残す。上限は、精度の指摘が出続けても 3 周目で止める歯止め
- **3 周目の指摘**: High（誤動作、データの破損、ゲートの迂回）は直す。Medium と Low は、検証できる誤りも含めて直さず、
  issue に 1 件でまとめ、報告（担当）かマージの本文（親）の「対応しなかった指摘」に書く。4 周目は回さない。
  3 周の後に届いた Copilot の指摘も同じく扱い、High を直したら Copilot を待たずに報告する。
  Medium と Low を直さないのは、直した修正がレビューを受けず、修正が新しい誤りを作ることがあるため（2026-10-29 に、
  nixfiles PR #509 の 2 周目のレビューが見つけたのは、1 周目の修正 5f1b82e1 が作った誤りだった）。リモートのある
  リポジトリでは、/gh-pr-review の記録の規則で `/code-review` を回した head にしか記録を書けないので、直さなければ
  3 周目の head に記録できる
- **3 周目に High を直した担当**: 報告に、直したコミットを、最後の周の HEAD より後の未レビューの挙動の変更として書く。
  親は /git-merge と /gh-pr-review の規則どおり、最後の周より後の挙動の変更としてブランチを回す。これが親の 1 周目に
  なる。リモートがあり PR があれば、直した head は `/code-review` を回していないので記録しない（/gh-pr-review の
  head ごとの記録の規則。3 周目の head の記録は High を含むので、レビュー済みに数えない）。報告に head に記録が無いことを
  書き、親が回してその head に記録する
- **親の上限**: 親（/git-merge）も 3 周まで。親の周は担当の周の後の追加で、通常は 1 周で終わる。周が止まらない
  仕組み（周ごとに新しい候補が出る）は、回すのが担当でも親でも同じ。担当が 3 周目に直さず issue にまとめた
  Medium と Low は、親の周で直してよい（親の周が修正をレビューする）。親が 3 周目に High を
  直したときは、後に回す人がいないので、マージせずに、直したコミットを示して 4 周目を回すかをユーザーに聞く
- **High を落とす代わりに**: ADR-0034 が Copilot の上限を 2〜3 に下げる案を採らなかった理由（後の周でも新しい High が
  出る）は、ここでも当たる。3 周目の High は直して親の周で確かめるので落とさない。4 周目以降に出るはずだった High は
  落ちる。2026-10-29 の 3 件は、5〜10 周を回しても指摘が尽きず、回し続けるほど担当の作業（PR、報告）が止まった。
  落ちる High は、親の周と人のレビュー、マージの後に見つかった誤りの issue で拾う

### 帰結

- 担当の `/code-review` は 3 回まで、親は通常 1 回で、1 つのブランチで 4 回ほどになる。2026-10-29 の 3 件は、
  担当だけで 5〜12 回だった
- 4 周目以降に見つかったはずの誤り（2026-10-29 の /retro の担当の 8 周目の、前提の誤りのようなもの）は、マージの後に
  見つかる。issue にまとめた 3 周目の指摘は、別のトピックとして直す
- /gh-pr-create（PR を出す前のローカルレビュー）と、リモートのあるリポジトリの親の周（/gh-pr-review）には、上限を
  書かない。担当は /delegate の上限に従う（/delegate が、/gh-pr-create の周と終わり方を自分の規則で置き換えると書く）。リモートのあるリポジトリでは、マージの hook が head に High の無い記録を
  求めるので、親が High を直せば回し直すことになり、親の周の終わりは hook の条件で決まる

### 確認

- /delegate の手順 7 と「作業中の規則」、/git-merge の「レビュー」の節が、3 周の上限、3 周目の指摘の扱い、High を
  直した head の扱いを書いていること
- 次に担当が 3 周で止まったとき、報告の「対応しなかった指摘」と issue に 3 周目の指摘が入っていること
