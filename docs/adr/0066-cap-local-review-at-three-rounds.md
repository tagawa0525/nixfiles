# ADR-0066: ローカルの /code-review は担当も親も 1 つのブランチで 3 周までとし、残りの指摘は issue にまとめる

## 背景

ローカルの `/code-review` の周の打ち切りは、指摘の内容で決めていた（/git-merge の「レビュー」の節と、/delegate の
「作業中の規則」）。精度（正しさ、数値、記録と出力の一致）と速度に関わる指摘が出る限り直して回し、指摘が文言・構成・
置き場だけになったら打ち切る。この規則は 2026-10-14 に、文言の指摘で周が回り続けたことを受けたもの。周の数は
/git-merge が 13〜15 周、/delegate が 13 周と書いていて、食い違う（どちらも記録で数え直していない。担当と親のどちらが
回したかも確かめていない）。

2026-10-29 に、/delegate の担当 3 本がこの規則の下で次の周を回した（周の数は担当の報告による。記録で数え直していない）:

- nixfiles PR #513 の担当: `/code-review high` を 10 周回し、11 周目の結果を待つ途中で引き渡しを求められて止まった。
  PR は作っておらず、push もしていなかった。報告によれば、指摘はスキルの経路と既存のコードのエッジケースに移っていた。
  親の追加の指示で打ち切り、push した head でさらに 2 周回した
- /retro の担当（ユーザーの言葉の引用。ADR-0065 のブランチ）: `/code-review high` を 8 周回しても指摘は尽きなかった。
  8 周目には、決定の前提そのものの誤りが見つかった
- xlc の履歴の ADR の担当: `/code-review high` を 5 周回した。周ごとの指摘は、どれも精度に関わるもの（文献の読み方、
  主張の数値、測った量の区別など）だった

どの担当も規則に違反していない。レビューは周ごとに新しい候補を出すので、直した文や、それまで見ていなかった
エッジケースから、精度に関わる指摘が出続ける。指摘の種類では周が止まらない。

周の数を決めない形は ADR-0023 と ADR-0027 の決定でもある。ADR-0023 は、スキル（gh-pr-merge、gh-pr-review、
gh-pr-create、git-push、git-merge）から周回数の記述を消し、ローカルレビューの周は回数でなく「その周に検証できる
誤りが無ければ終わり」を終わりの条件にした（レビューは周ごとに新しい候補を出すので、指摘ゼロを待たない）。ADR-0027 は、周の終わりを既存のスキルの条件に揃え、branch-task（今の delegate）で
独自の周回数を決めないとした。2 つのスキルの終わりの条件が食い違うと、サブエージェントはどちらかに違反するため。

Copilot の周には以前、上限（5 周）があった。ADR-0034 は上限を 2〜3 に下げる案を、2 回目以降でも新しい High が出る
レビューが Balanced で 30〜38%、Lite で 17% あり、回数で切るとそれを落とすとして採らなかった。ADR-0043 は head の
ローカルレビューの記録で終わる形にして上限を外した（`decide-next.sh` の `ROUND` は情報だけ）。High の残る記録は
レビュー済みとして数えない（ADR-0043、/gh-pr-review の「ローカルレビュー」）。

## 検討した案

- 案 A: 周の上限を決めない（今）。上の 3 件のとおり、指摘の内容の規則では止まらない
- 案 B: 3 周の上限。4 周目は回さず、残った指摘は issue にまとめる
- 案 C: 周の上限を `review-level.sh` の LEVEL で変える（例: high は 3 周、medium は 1 周）。LEVEL は差分のファイルの
  場所（`docs/` の外があるか）で決まり、周が収束するかとは関わらない。上の 3 件はどれも high で、medium の
  （`docs/` だけの）ブランチには、すでに「文書と数値だけの変更は、事実の誤りに絞った 1 周で終わる」がある。
  分けても上の 3 件の扱いは変わらない
- 案 D: 指摘の数で止める（ある周の指摘が N 件以下なら終える）。周ごとの件数は、PR のある head の記録
  （`record-local-review.sh`。2026-10-12 の ADR-0034 から）にしか無く、PR を出す前の周とリモートの無いリポジトリには無いので、
  N を決める根拠が無い。件数の少ない周にも High はありうるので、件数では重さを落とす

## 決定と理由

案 B にする。ユーザーの判断は「1、2 とも推奨に従います。」（ユーザー 2026-10-29）で、親が出した 2 つの推しへの答え。
1 は依頼でユーザーの言葉を渡す規則（ADR-0065）、2 はこの上限で、親の推しは「/delegate に 3 周の上限を足し、4 周目以降は
回さず、残りの指摘は issue にまとめる」だった。親（/git-merge、/gh-pr-review）にも同じ上限を置くことと、3 周目の指摘の
扱いは、この ADR を書いた担当が、親の依頼の推し（親にも 3 周。親は担当の後の追加の周）に沿って決めた。

これは ADR-0023 の「ローカルレビューの周回は回数ではなく「その周に検証できる誤りが無ければ終わり」を終了条件にする」の
部分と、ADR-0027 の「branch-task で独自の周回数を決めない」の部分を置き換える。終わりの条件は残り、3 周の上限がそれに
加わる。どちらの ADR も、ほかの部分は変わらない。ADR-0027 が避けたスキルどうしの食い違いは、規則の本文を /git-merge の
「レビュー」の節の 1 か所に置き、/delegate と /gh-pr-review からはそこを参照して避ける。

- **上限**: 担当も親も、1 つのブランチでローカルの `/code-review` は 3 周まで（担当と親は別々に数える）。数え直しはしない
  （親の追加の指示で変更が足されても、そのブランチで回した周の合計で数える）。rebase の後の周（親の衝突の後、担当の
  計算の前）も数に入れ、3 周を使い切っていれば回さず、その変更を未レビューとして報告（親はマージの本文）に書く。
  対象を見つけられなかった回とエラーの回は数えない
- **早めの打ち切り**: 指摘の内容の規則（文言・構成・置き場だけの周で打ち切る、文書と数値だけの変更は 1 周）は、その
  まま残す
- **3 周目の指摘**: High（誤動作、セキュリティ、データの破損、ゲートの迂回。/gh-pr-review の定義）だけを直し、4 周目は回さない。担当は、その修正を
  未レビューの変更として報告の「確かめていないこと」に書き、親の周が確かめる。親が自分の 3 周目に High を直したら、
  後に回す人がいないので、マージせずにユーザーに聞く。Medium と Low は、検証できる誤りも含めて直さず、1 件の issue に
  まとめて「対応しなかった指摘」（親はマージの本文）に書く。直した修正はレビューを受けず、修正が新しい誤りを作ることが
  ある（2026-10-29 に、nixfiles PR #509 の 2 周目のレビューが見つけたのは、1 周目の修正 5f1b82e1 が作った誤りだった）
- **担当が残した指摘**: 担当が issue にまとめた Medium と Low は、親に残りの周があるときだけ、親の周で直してよい
  （親の周がその修正をレビューする）。親の 3 周目では直さない
- **High を落とす代わりに**: ADR-0034 が Copilot の上限を 2〜3 に下げる案を採らなかった理由（後の周でも新しい High が
  出る）は、ここでも当たる。4 周目以降に出るはずだった High は落ちる。2026-10-29 の 3 件は、5〜10 周を回しても指摘が
  尽きず、回し続けるほど担当の作業（PR、報告）が止まった

### 帰結

- 通常は担当の 3 周以内で終わる。親の周は、/git-merge の「レビュー」の規則で回すとき（担当の最後の周の後に挙動の変更（3 周目の High の修正など）がある、担当が最後の周の HEAD を示していない、rebase で衝突を解いた、など）だけ
  回る（/git-merge の、担当の最後の周の HEAD より後の差分で決める規則）。2026-10-29 の 3 件は、担当だけで 5〜12 回だった
- 4 周目以降に見つかったはずの誤り（2026-10-29 の /retro の担当の 8 周目の、前提の誤りのようなもの）は、マージの後の
  issue と人のレビューで拾う。issue にまとめた 3 周目の指摘は、別のトピックとして直す
- リモートのあるリポジトリでは、3 周目に High を直した head にローカルレビューの記録が無い。マージの hook は、Copilot の
  レビューの代わりに High の無い記録を受け入れるだけで、push だけでは Copilot は再レビューせず、`request-rereview.sh` は
  記録の無い head の依頼を拒むので、通るのは親の周の記録だけ（docs/ だけの PR で一度レビューが成功していれば hook は記録を求めない）。親が自分の 3 周目に High を直した head は、ユーザーに聞く

### 確認

- /git-merge の「レビュー」の節に、上限、早めの打ち切り、3 周目の指摘、担当が残した指摘の扱いが 1 か所にあること
- /delegate（手順 7 と「作業中の規則」）と /gh-pr-review（「ローカルレビュー」）が、規則を複製せず /git-merge の
  その節を参照すること
- 次に担当が 3 周で止まったとき、報告の「対応しなかった指摘」と issue に 3 周目の指摘が入っていること
