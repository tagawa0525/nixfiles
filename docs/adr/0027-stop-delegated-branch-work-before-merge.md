# ADR-0027: サブエージェントに任せるブランチ作業はマージの直前で止め、手順と報告の形を branch-task スキルに置く

## 背景

親のセッションがサブエージェントに 1 トピックのブランチ作業を頼むとき、worktree の作り方、TDD、チェック、レビュー、
マージしないこと、報告の形を、毎回長い依頼文で書いていた。書くたびに抜けや揺れが出る。依頼文の書き方は
サブエージェントの振る舞いを誘う（ADR-0023 の背景では、依頼文の「rebase 後は付けてよい」がエスケープつきの
マージの試みを招いた）。

## 検討した案

- 案 A: 固定の手順と報告の見出しをスキル（`branch-task`）に置き、依頼にはリポジトリ、ブランチ名、何をするか、
  禁止事項だけを書く。サブエージェントはマージの直前（チェックとレビューの後、rebase の前）で止まり、マージは
  親が /git-merge か /gh-pr-merge で行う
- 案 B: 案 A と同じスキルで、サブエージェントにマージまで任せる
- 案 C: スキルを作らず、依頼文のテンプレートを親の側の文書（CLAUDE.md）に置く

## 決定と理由

採用: 「案 A」を、マージの作業の担い手だけ変えて使う。サブエージェントは rebase と push まで済ませ、報告を親に送って
マージの許可を求め、許可の後にマージと後片付け（`post-merge-cleanup.sh`）を行う。

- マージは、親がサブエージェントの報告を確かめて許可してから行う。サブエージェントの報告は確かめる前の暫定で、
  確かめずにマージすると、誤った結論が main に入る。許可を出すのは親だけで、ほかのサブエージェントやセッションの許可では
  マージしない
- マージの作業（rebase、push、マージの本文、マージ、後片付け）はサブエージェントが行う。親（全体を見て判断するセッション）の
  文脈はサブエージェントの文脈より高くつくので、マージの手作業を親の文脈に入れない（ユーザー 2026-11-11 の判断の要約）。
  rebase の後の再レビューの要否はサブエージェントが /git-merge の「rebase の後」で決め、許可の前の rebase は報告に書いて親が
  確かめ、許可の後の rebase はマージの本文に根拠を書く
- 許可を待つ間、サブエージェントは終わらずに SendMessage で報告を親に送り、/delegate の待ちの項のタイマーでキャッシュを保って
  返事を待ち、約 1 時間（通知 13 回）で打ち切って終わる。待つ間に main が進んだら、もう一度 rebase して push してからマージし、
  `git range-diff` で自分のコミットが同一なら許可を取り直さない（親が確かめた中身は変わらない）
- 許可の無いマージを止める hook は足さない。許可は自然文で、機械では判定できない。マージの hook（pre-merge-check、
  check-merge-review）は今のまま通す
- 周の終わりは、既存のスキルの条件（ローカルは /git-merge の「直す指摘の基準」の、blocking の無い周で終わりと、直した後の
  周を回すかの目安、GitHub は `decide-next.sh` の `VERDICT`。ADR-0023、ADR-0066）に揃え、branch-task で独自の条件を決めない。2 つのスキルの終わりの条件が
  食い違うと、サブエージェントはどちらかに違反する
- リポジトリ固有の規則（重い計算、検証の記録など）はスキルに入れず、リポジトリの CLAUDE.md に任せる。
  ユーザーの git の規約を持つどのリポジトリでも使えるようにするため
- 優先の順は、依頼 > スキル、リポジトリの CLAUDE.md > スキル。ただし親の許可の前にマージしないことと共通の禁止事項は
  依頼でも変えない

採らなかった案:

- 案 B: 報告を確かめる前にマージが済み、親が誤りを見つけても戻すのに revert が要る。ADR-0023 の背景も、
  サブエージェントがマージに進もうとした例
- 案 C: CLAUDE.md は毎回読み込まれ、サブエージェントへ頼まない会話でも場所を取る。テンプレートを参照する依頼文が
  結局長くなり、揺れも残る

### 帰結

- 良い点: 依頼文が短くなり、報告の見出しが揃うので親が確かめやすい
- 悪い点: マージのたびに、親が報告を確かめて許可を送る手番が要る。サブエージェントは許可を待つ間タイマーで答える（1 時間で
  最大 13 回）。後片付けは、サブエージェントの worktree の外（既定ブランチの pull、worktree とブランチの削除）に触れる例外になる。
  許可の前のマージを止めるのは /delegate の文章だけで、hook のゲートではない。
  グローバルの許可（`modules/home/parts/claude-code.nix` の `Bash(git merge:*)`、`Bash(gh pr:*)`）がマージを
  確認なしで通すので、スキルの allowed-tools を絞っても止まらない
- 見直す条件: サブエージェントが許可の前にマージに進む例が出たとき（サブエージェントの呼び出しを hook で見分けられるかは
  確かめていない）と、親の返事が 1 時間に間に合わず打ち切る例が多いとき

### 確認

- /delegate の受ける側の手順（`.claude/skills/delegate/references/working.md`）に、手順 8 の rebase と push、手順 9 の
  SendMessage で許可を求めてタイマーで待つこと、手順 10 の親の許可だけで進めること、許可の後の rebase と range-diff、
  /gh-pr-merge か /git-merge でのマージ、`post-merge-cleanup.sh` の後片付け、13 回での打ち切りがある。頼む側
  （`requesting.md`）に、親が確かめて許可か直しの指示を送り、rebase とマージを行わないことがある
- 担当が動いたまま SendMessage（`to: "main"`）で親に 1 行を送り、送れた（`Message queued for the main conversation's next turn.`。
  2026-11-11 にこの変更の担当が試した）。親の返事が動いている担当に届くかは、この形の最初の依頼で確かめる
- 実際に依頼を 1 件この形で出し、報告が見出しどおりに返ること

## 補足

- 2026-10-21: 依頼の「禁止事項」の欄は、ADR-0044 で「完成の形」と「変える範囲」の欄に置き換えた。共通の禁止事項は
  「どの依頼でも守ること」として肯定形で書き直し、hook が強制する「main に直接コミットしない」は消した
- 2026-10-22: 報告の見出しの先頭に「親が先に読む要点」を足した。長い報告から親の判断が要る点を拾う手間を減らすため
  （同じ日の 3 本の報告のうち、要点を頭に置いた 1 本が読みやすかった）。中身は本文の節を指すだけにし、同じ事実を
  2 か所に書かない。途中で止まった理由だけは本文に節が無いので要点に書く。この形で出した依頼はまだ無く、「確認」の
  最後の項は次の依頼で確かめる
- 2026-10-22: 依頼に書く外部の値（ツールの既定値、仕様の数値）は、頼む側が出典で確かめたものだけにし、受ける側も
  作業の前に確かめる。同じ日に、依頼の「OpenMC 0.15.2 の既定と同じ」という値が、担当が出典を読むと別の値だった
  （参照解に与えていた値と既定が違っていた）。頼む側だけ、受ける側だけで確かめる案は、どちらか一方の読み違いが
  そのまま決定に入るので採らない。費用は出典を 1 度読む分だけ
- 2026-10-24: 依頼の定型に「前提」の欄を足した（ADR-0060）。最初の依頼に欄が無ければ、受ける側は「前提の欄が無い」を
  途中で止まった理由と同じく要点に書く

- 2026-11-08: /delegate と /git-merge から経緯（日付、周の数、起きた事故）を消し、規則の理由を 1 文に縮めた（スキルは担当と
  レビューの周の全部の文脈に入るため。ユーザー 2026-11-07 の判断の要約）。消した経緯のうち ADR に無かったもの:

## 変更

- 2026-10-29: ローカルの周の終わりの条件。前は「周の終わりは、既存のスキルの条件（ローカルは「その周に検証できる誤りが
  無ければ終わり」、GitHub は `decide-next.sh` の `VERDICT`。ADR-0023）に揃え、branch-task で独自の周回数を決めない。」。
  ADR-0023 のローカルの条件を、再現を書ける指摘だけを直す基準と歯止めの 3 周に変えたため。回数は /git-merge の 1 か所に置き、
  delegate はそれに揃える（ADR-0066）
- 2026-11-11: ローカルの周の終わりの条件。前は「ローカルは /git-merge の「直す指摘の基準」の、blocking の無い周で終わりと
  歯止めの 3 周」。ADR-0066 の 2026-11-11 の変更で、周の上限を外し、直した後の周を回すかをモデルが決めることにしたため
- 2026-11-11: マージの作業の担い手。前は決定が「採用: 「案 A」。」で、理由の 1、2 項目が「マージは、親がサブエージェントの報告を
  確かめてから行う。サブエージェントの報告は確かめる前の暫定で、確かめずにマージすると、誤った結論が main に入る」「rebase も
  サブエージェントに任せない。rebase した後は再レビューの要否の判断が要り、それはマージの判断と一体なので、マージする側（親）が
  行う」、優先の順の項の後半が「ただしマージの直前で止めることと共通の禁止事項は依頼でも変えない」。親が、マージを担当に任せるかを
  尋ねたところ、ユーザーは、許可は親が出し作業は担当が行う形を求め、順序は担当が rebase と push まで済ませてから親に許可を求め、
  許可の後に担当がマージと後片付けを行うものだと念を押した（ユーザー 2026-11-11）。許可を待つ間の形（終わらずにタイマーで待ち
  約 1 時間で打ち切る、main が進んだら rebase し直し、差分が rebase だけなら許可を取り直さない）は親が示し、ユーザーはその形で
  進めるよう答えた（ユーザー 2026-11-11）。背景は、親の文脈は担当の文脈より貴重なので、マージの手作業を親の文脈に入れないという
  ユーザーの考え（ユーザー 2026-11-11）。比べた案: 担当は今までどおり報告して終わり、親が SendMessage で許可を送って再開させる形。
  再開は 2026-11-11 に 4 回動いたが、5 分を超えた再開ごとにキャッシュの書き直しが 1 回出る。担当が動いたまま親に送れると
  分かったので、終わらずに待つ形にした。検討した案 B（マージまで任せる）を採らなかった理由（確かめる前にマージが済む）は、
  許可の後にマージするので当たらない。決定の核（マージは親が確かめてから）は変わらないので、置き換えずにこの ADR を直した
