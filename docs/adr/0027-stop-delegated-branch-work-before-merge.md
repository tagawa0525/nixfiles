# ADR-0027: サブエージェントに任せるブランチ作業はマージの直前で止め、手順と報告の形を branch-task スキルに置く

## 背景

親のセッションがサブエージェントに 1 トピックのブランチ作業を頼むとき、worktree の作り方、TDD、チェック、レビュー、
マージしないこと、報告の形を、毎回長い依頼文で書いていた。書くたびに抜けや揺れが出る。依頼文の書き方は
サブエージェントの振る舞いを誘う（ADR-0023 の背景では、依頼文の「rebase 後は付けてよい」がエスケープつきの
マージの試みを招いた）。

## 検討した案

- 案 A: 固定の手順と報告の見出しをスキル（`branch-task`）に置き、依頼にはリポジトリ、ブランチ名、何をするか、
  禁止事項だけを書く。サブエージェントはマージの直前（チェックとレビューの後、rebase の前）で止まり、マージは
  親が /git-merge か /gh-pr-merge で行う
- 案 B: 案 A と同じスキルで、サブエージェントにマージまで任せる
- 案 C: スキルを作らず、依頼文のテンプレートを親の側の文書（CLAUDE.md）に置く

## 決定と理由

採用: 「案 A」。

- マージは、親がサブエージェントの報告を確かめてから行う。サブエージェントの報告は確かめる前の暫定で、
  確かめずにマージすると、誤った結論が main に入る
- rebase もサブエージェントに任せない。rebase した後は再レビューの要否の判断が要り、それはマージの判断と一体なので、
  マージする側（親）が行う
- 周の終わりは、既存のスキルの条件（ローカルは「その周に検証できる誤りが無ければ終わり」、GitHub は
  `decide-next.sh` の `VERDICT`。ADR-0023）に揃え、branch-task で独自の周回数を決めない。2 つのスキルの終わりの条件が
  食い違うと、サブエージェントはどちらかに違反する
- リポジトリ固有の規則（重い計算、検証の記録など）はスキルに入れず、リポジトリの CLAUDE.md に任せる。
  ユーザーの git の規約を持つどのリポジトリでも使えるようにするため
- 優先の順は、依頼 > スキル、リポジトリの CLAUDE.md > スキル。ただしマージの直前で止めることと共通の禁止事項は
  依頼でも変えない

採らなかった案:

- 案 B: 報告を確かめる前にマージが済み、親が誤りを見つけても戻すのに revert が要る。ADR-0023 の背景も、
  サブエージェントがマージに進もうとした例
- 案 C: CLAUDE.md は毎回読み込まれ、サブエージェントへ頼まない会話でも場所を取る。テンプレートを参照する依頼文が
  結局長くなり、揺れも残る

### 帰結

- 良い点: 依頼文が短くなり、報告の見出しが揃うので親が確かめやすい
- 悪い点: マージのたびに親の手番が要る。マージを止めるのは SKILL.md の文章だけで、hook のゲートではない。
  グローバルの許可（`modules/home/parts/claude-code.nix` の `Bash(git merge:*)`、`Bash(gh pr:*)`）がマージを
  確認なしで通すので、スキルの allowed-tools を絞っても止まらない
- 見直す条件: サブエージェントがマージに進む例が出たとき（サブエージェントの呼び出しを hook で見分けられるかは
  確かめていない）

### 確認

- `.claude/skills/branch-task/SKILL.md` の手順に、マージと rebase を実行するところが無いこと
- 実際に依頼を 1 件この形で出し、報告が見出しどおりに返ること

## 補足

- 2026-10-21: 依頼の「禁止事項」の欄は、ADR-0044 で「完成の形」と「変える範囲」の欄に置き換えた。共通の禁止事項は
  「どの依頼でも守ること」として肯定形で書き直し、hook が強制する「main に直接コミットしない」は消した
- 2026-10-22: 報告の見出しの先頭に「親が先に読む要点」を足した。長い報告から親の判断が要る点を拾う手間を減らすため
  （同じ日の 3 本の報告のうち、要点を頭に置いた 1 本が読みやすかった）。中身は本文の節を指すだけにし、同じ事実を
  2 か所に書かない。途中で止まった理由だけは本文に節が無いので要点に書く。この形で出した依頼はまだ無く、「確認」の
  最後の項は次の依頼で確かめる
- 2026-10-22: 依頼に書く外部の値（ツールの既定値、仕様の数値）は、頼む側が出典で確かめたものだけにし、受ける側も
  作業の前に確かめる。同じ日に、依頼の「OpenMC 0.15.2 の既定と同じ」という値が、担当が出典を読むと別の値だった
  （参照解に与えていた値と既定が違っていた）。頼む側だけ、受ける側だけで確かめる案は、どちらか一方の読み違いが
  そのまま決定に入るので採らない。費用は出典を 1 度読む分だけ
