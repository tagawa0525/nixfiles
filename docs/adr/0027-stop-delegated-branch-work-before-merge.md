# ADR-0027: サブエージェントに任せるブランチ作業はマージの直前で止め、手順と報告の形を branch-task スキルに置く

## 背景

親のセッションがサブエージェントに 1 トピックのブランチ作業を頼むとき、worktree の作り方、TDD、チェック、レビュー、
マージしないこと、報告の形を、毎回長い依頼文で書いていた。書くたびに抜けや揺れが出る。依頼文の書き方は
サブエージェントの振る舞いを誘う（ADR-0023 の背景では、依頼文の「rebase 後は付けてよい」がエスケープつきの
マージの試みを招いた）。

## 検討した案

- 案 A: 固定の手順と報告の見出しをスキル（`branch-task`）に置き、依頼にはリポジトリ、ブランチ名、何をするか、
  禁止事項だけを書く。サブエージェントはマージの直前（チェックとレビューの後、rebase の前）で止まり、マージは
  親が /git-merge か /gh-pr-merge で行う
- 案 B: 案 A と同じスキルで、サブエージェントにマージまで任せる
- 案 C: スキルを作らず、依頼文のテンプレートを親の側の文書（CLAUDE.md）に置く

## 決定と理由

採用: 「案 A」。

- マージは、親がサブエージェントの報告を確かめてから行う。サブエージェントの報告は確かめる前の暫定で、
  確かめずにマージすると、誤った結論が main に入る
- rebase もサブエージェントに任せない。rebase した後は再レビューの要否の判断が要り、それはマージの判断と一体なので、
  マージする側（親）が行う
- 周の終わりは、既存のスキルの条件（ローカルは /git-merge の「直す指摘の基準」の、blocking の無い周で終わりと歯止めの
  3 周、GitHub は `decide-next.sh` の `VERDICT`。ADR-0023、ADR-0066）に揃え、branch-task で独自の条件を決めない。2 つのスキルの終わりの条件が
  食い違うと、サブエージェントはどちらかに違反する
- リポジトリ固有の規則（重い計算、検証の記録など）はスキルに入れず、リポジトリの CLAUDE.md に任せる。
  ユーザーの git の規約を持つどのリポジトリでも使えるようにするため
- 優先の順は、依頼 > スキル、リポジトリの CLAUDE.md > スキル。ただしマージの直前で止めることと共通の禁止事項は
  依頼でも変えない

採らなかった案:

- 案 B: 報告を確かめる前にマージが済み、親が誤りを見つけても戻すのに revert が要る。ADR-0023 の背景も、
  サブエージェントがマージに進もうとした例
- 案 C: CLAUDE.md は毎回読み込まれ、サブエージェントへ頼まない会話でも場所を取る。テンプレートを参照する依頼文が
  結局長くなり、揺れも残る

### 帰結

- 良い点: 依頼文が短くなり、報告の見出しが揃うので親が確かめやすい
- 悪い点: マージのたびに親の手番が要る。マージを止めるのは SKILL.md の文章だけで、hook のゲートではない。
  グローバルの許可（`modules/home/parts/claude-code.nix` の `Bash(git merge:*)`、`Bash(gh pr:*)`）がマージを
  確認なしで通すので、スキルの allowed-tools を絞っても止まらない
- 見直す条件: サブエージェントがマージに進む例が出たとき（サブエージェントの呼び出しを hook で見分けられるかは
  確かめていない）

### 確認

- `.claude/skills/branch-task/SKILL.md` の手順に、マージと rebase を実行するところが無いこと
- 実際に依頼を 1 件この形で出し、報告が見出しどおりに返ること

## 補足

- 2026-10-21: 依頼の「禁止事項」の欄は、ADR-0044 で「完成の形」と「変える範囲」の欄に置き換えた。共通の禁止事項は
  「どの依頼でも守ること」として肯定形で書き直し、hook が強制する「main に直接コミットしない」は消した
- 2026-10-22: 報告の見出しの先頭に「親が先に読む要点」を足した。長い報告から親の判断が要る点を拾う手間を減らすため
  （同じ日の 3 本の報告のうち、要点を頭に置いた 1 本が読みやすかった）。中身は本文の節を指すだけにし、同じ事実を
  2 か所に書かない。途中で止まった理由だけは本文に節が無いので要点に書く。この形で出した依頼はまだ無く、「確認」の
  最後の項は次の依頼で確かめる
- 2026-10-22: 依頼に書く外部の値（ツールの既定値、仕様の数値）は、頼む側が出典で確かめたものだけにし、受ける側も
  作業の前に確かめる。同じ日に、依頼の「OpenMC 0.15.2 の既定と同じ」という値が、担当が出典を読むと別の値だった
  （参照解に与えていた値と既定が違っていた）。頼む側だけ、受ける側だけで確かめる案は、どちらか一方の読み違いが
  そのまま決定に入るので採らない。費用は出典を 1 度読む分だけ
- 2026-10-24: 依頼の定型に「前提」の欄を足した（ADR-0060）。最初の依頼に欄が無ければ、受ける側は「前提の欄が無い」を
  途中で止まった理由と同じく要点に書く

- 2026-11-08: /delegate と /git-merge から経緯（日付、周の数、起きた事故）を消し、規則の理由を 1 文に縮めた（スキルは担当と
  レビューの周の全部の文脈に入るため。ユーザー 2026-11-07 の判断の要約）。消した経緯のうち ADR に無かったもの:
  - 2026-10-12: /code-review にブランチ名を渡し、cwd の別のリポジトリで空振りして「指摘なし」が 2 回返った（対象は worktree のパスで渡す）
  - 2026-10-14: `cd` が別のサブシェルになり、`dvc repro` が既定ブランチの作業ツリーで走って追跡ファイルを書き換えた（worktree の外に触らない）
  - 2026-10-14: 古い土台のまま計算を投げ、結果が古い方法のもので投げ直しになった（投げる直前に既定ブランチの進みを見る）
  - 2026-10-22: レビューを待つ sleep の Monitor を残して報告し、タイマーが切れるたびに計 3 度送り直した（TaskStop で止める）
  - 2026-10-22: `examples/` へ移した試行の入力の隣に、出力 34 個が未追跡で残った（チェックの前に `git status --short` を空にする）
  - 2026-10-22: xlc の高速版の依頼の「1 本 10 分」が、手を付けない部分（MOC 7.4 秒 × 輸送 81 回 ≈ 599 秒）と同じで、担当は未達と報告した（内訳の合計を先に出す）
  - 2026-10-24: 担当が「lattice の crate は main で変わっていない」と報告したが、main は同じ crate の 4 ファイルを変えていた（重なりは `base-moved.sh` の出力で書く）
  - 2026-10-24: 親の追加の指示「割り込まれうる main のジョブの時間も `suspended:` が無ければ記録に使える」が xlc の CLAUDE.md と食い違い、2 人の担当が取り込んで再測定した（規則の例外の指示は原文と照らす）
  - 2026-10-28: xlc の担当 2 本が、誤りを報告する順やテストの比べる範囲を変える修正をレビューの後に積み、列挙だけで報告した（挙動を変えるならもう 1 周）
  - 2026-10-28: xlc の erfcx の依頼の「x < 2.5 の級数の側は変えない」の側が桁落ちで 16,444 ulp ずれ、担当は /code-review を 8 回呼んだ（定義域の全体を参照と比べる）
  - 2026-10-29: xlc の担当が、Python の修正を含む 3 周目をスクリプトを通さずに medium で回した（LEVEL を自分で下げない）
  - 2026-10-30: xlc の依頼が親の Fable 5.1 の trailer の行をコピーし、Opus の担当が食い違いを報告した（モデル名は `<自分のモデル名>`）
  - 2026-10-30: xlc の依頼が ADR の「第 3 項は … では 0」を R の全体に掛けて言い換え、担当が ADR と照らして見つけた（決定はコピーか番号と節で指す）
  - 2026-10-31: xlc の担当が、別の担当の退避が既にあった scratchpad の `old/` に前の出力を退避した（`<scratchpad>/<ブランチ名>/` に置く）
  - 2026-11-03: xlc の追加の指示の「差分に 1 周」のもとで、担当がその周の指摘を直した 2 コミットを読まれないまま残して報告した（周の数は回し始める数）
  - 2026-11-03: xlc の依頼が実装する ADR の status を書かず、担当の周の後に親が accept を指示して、accept の周と直しの周 3 周が要った（#0093 のマージの本文。依頼に status の条件を書く）

## 変更

- 2026-10-29: ローカルの周の終わりの条件。前は「周の終わりは、既存のスキルの条件（ローカルは「その周に検証できる誤りが
  無ければ終わり」、GitHub は `decide-next.sh` の `VERDICT`。ADR-0023）に揃え、branch-task で独自の周回数を決めない。」。
  ADR-0023 のローカルの条件を、再現を書ける指摘だけを直す基準と歯止めの 3 周に変えたため。回数は /git-merge の 1 か所に置き、
  delegate はそれに揃える（ADR-0066）
