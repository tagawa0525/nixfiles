# ADR-0004: 文書（docs/）だけの PR は最初の自動レビューで足りるとする

## 背景

ADR や文書の PR で、自動レビューが何周も続く。文章は細部をいくらでも掘れるので、指摘を直すたびに
直した文が次の指摘の的になり、周回が収束しない。

- nucrawler #145 は 22 コミット・74 コメント、#146 も指摘 0 件の後に毎回新しい論点が出た
- 2026-10-10 の kikitori #20（文書）は 3 周、nixfiles #263（ADR）は 2 周。指摘は文章中の主張に集中し、
  2 件は検証せずに古いコメントから写した記述だった

計画（`docs/plans/`）だけの PR には、すでに「最初のレビューで止める」規則があった（`STOP_PLAN_REVIEWED`、
`pre-merge-check` の検証 8）。ADR や `docs/` のほかの文書には無かった。

## 検討した案

- 案 A: 計画だけに限る（現状）。ADR は周回が収束しないまま
- 案 B（採用）: `docs/` 配下のファイルだけを変える PR に広げる
- 案 C: ADR・計画・issue に限り、`docs/*.md` のような文書は対象外にする。区別する理由が無い。
  `docs/x1ng1-xmm7360-lte.md` も同じ散文で、同じ周回の問題を持つ
- 案 D: 周回の上限を 5 から 2 に下げる。コードの PR の再レビューまで減る

## 決定と理由

案 B にする（ユーザーの判断）。判定は `docs/` の前方一致で、`pre-merge-check`（`is_docs_only`）と
`decide-next.sh`（`docs_only`）とローカルの `review-level.sh` が同じ規則を使う。

- **条件**: 変更ファイルがすべて `docs/` 配下で、かつ一度は自動レビューが成功している。取得に失敗したときは
  文書だけとみなさず、再レビューを求める側に倒す
- **移動は旧パスも数える**: `src/` から `docs/` への移動は、files API の `filename` だけだと文書だけの変更に見える。
  `previous_filename` も取得する
- **受け入れる弱点**: 最初のレビューの後に直した文は、GitHub の自動レビューを受けない。ADR の決定を後から
  書き換えても通る。決定はユーザーが下すもので、レビューの主な役割は事実の確認なので受け入れる。補うために:
  - PR を出す前にローカルの `/code-review` で事実の誤りを取り切る（`gh-pr-create`）
  - 文書の PR でレビューの指摘を直した後は、ローカルで `/code-review medium` を一度だけ回してから push する
    （`gh-pr-review`）
- **指摘の選別**: 文書の指摘のうち直すのは、検証できる誤り（コードや事実と食い違う記述、壊れた参照）と
  方針に関わるものだけ。実装の細部や言い回しは decline する。文書にはコードの挙動を写さず、コードへの
  参照を書く

## 確認

- `.claude/tests/hooks.sh` と `.claude/tests/scripts/gh-pr-review.sh` に、ADR だけの PR、`docs/` に似た別の場所、
  移動の旧パスのテストを足した
- `.claude/tests/scripts/review-level.sh` に、ローカルレビューのレベル判定（docs/ だけは medium、似た別の場所と
  移動は high、差分が空ならエラー、古い main の扱い）のテストを足した。`docs/` の前方一致は
  `pre-merge-check`、`decide-next.sh`、`review-level.sh` の 3 か所にあり、Rust と bash で共有できないため、
  それぞれのテストで同じ規則を確かめている
