# ADR-0013: 履歴の中の番号を、親と文書が指すコミットの順に fast-import へ 1 回流して付け直す

## 背景

ADR-0012 で、コミットの番号の付け直しを `commit-refs` にまとめ、履歴全体の付け直し（`rewrite-history`）を足すと
決めた。ここでは、その書き換えをどう行うかを決める。

使う場面: git filter-repo などで履歴を書き換えると（ファイルを履歴から消すなど）、全てのコミットの番号が変わる。
過去のコミットの文書と本文に書いた番号は古いまま残る。書き換えの後に、その番号を書き換えた後の番号に付け直す。

難しさは、番号を付け直すとそのコミットの内容が変わり、番号がまた変わることにある。文書は、書いたときにあった
コミットしか指せないので、指す先を先に作れば、その最後の番号は先に決まっている。指す先は祖先とは限らない
（`cherry-pick -x` の本文は別のブランチのコミットを指す）。

xlc の `references/history-rewrite`（2026-10-11 に xlc の履歴を書き換えたときの道具。git で追跡していない）は、
filter-repo を Python のコールバックつきで繰り返し、前の回の commit-map で番号を置き換え、対応表が変わらなくなるまで
回した（上限 400 回。収束までの回数は記録が無い）。

## 決定の要因

- 1 回で終わり、回数が履歴の形に左右されない
- 外部の依存（Python、filter-repo、crate）を増やさない（ADR-0012）
- 書き換えた履歴が、元の履歴に番号の置き換えだけを当てたものであることを、ref を移す前に確かめられる

## 検討した案

- 案 A: filter-repo を Python のコールバックつきで、収束するまで繰り返す（xlc の道具）
- 案 B: filter-repo のコールバックから、ブロブごとに `commit-refs` を呼ぶ
- 案 C: `git fast-export --no-data` で全てのコミットを読み、親と文書が指すコミットの両方を依存として並べ、番号を
  置き換えて `git fast-import` に渡す。コミットを 1 つ渡すたびに `get-mark` で新しい番号を受け取り、後のコミットの
  置き換えに使う。1 回で終わる
- 案 D: gix や git2 などの crate で、オブジェクトを直接書く
- 案 E: コミットごとに `git hash-object` と `git commit-tree` を呼ぶ

## 決定と理由

採用: 案 C。

- fast-import は、`get-mark` を受けると、作ったばかりのコミットの完全な番号を `--cat-blob-fd` にすぐ返す。依存の順に
  流せば、文書が指すコミットの最後の番号は、そのコミットを渡す前に分かっている（2026-10-11、git 2.55.0 で、
  2 つ目のコミットの本文に 1 つ目の `get-mark` の答えを書いて流せることを確かめた）
- 依存を求めるために、流す前に全てのコミットの本文とブロブを読む。ブロブは流れに載せず（`--no-data`）、`git cat-file
  --batch` で読む。手元に置くのはコミットの見出し、本文、ファイルの操作だけで、ブロブの中身は置かない
- 案 A は、繰り返しの回数が履歴の中の参照の深さで決まり、全体を何度も書き直す。Python と filter-repo に頼る
- 案 B は、ブロブごとにプロセスを起こし、繰り返しも要る
- 案 D は、fast-import がすでにすることを crate で作り直し、依存を増やす
- 案 E は、オブジェクトごとにプロセスを起こす

書き換えの範囲と、止める条件:

- 対象は全てのブランチとタグ。テキストのブロブ（先頭 8000 バイトに NUL が無い。git の `buffer_is_binary` と同じ
  判定）と、コミットとタグの本文の番号を付け直す。置き換えの規則は `commit_refs::Map`（ADR-0012）を使う
- 入力の対応表は、書き換える前の番号から、今の履歴の番号への対応（filter-repo の `.git/filter-repo/commit-map`）。
  今の履歴のコミットは、対応表に無くても照合に入れる（この書き換えで番号が変わるので）
- 並べる順は、親と、文書が指すコミット（書き換えるもの）の両方を先にする。同じ順位なら fast-export の順にする
- 止める条件は `remap` と同じものに、次を足す: 文書が指すコミットが循環する（子を指すなど）、文書がそのコミット
  自身を指す。どれも流す前に、全ての理由をまとめて出す
- 注釈つきのタグは fast-export の流れから読まず、元のタグのオブジェクトから `git mktag` で作り直す（fast-import の
  `tag` は `refs/tags/` に ref を作り、`reset` はタグを指せない。2026-10-11、git 2.55.0 で `mark :N not a commit`
  で止まることを確かめた）。タグを指すタグは、指す方を先に作る
- シンボリックリンクの行き先は書き換えない（`remap` と同じ）
- 書き換えるのは `refs/heads/` と、たどるとコミットに着く `refs/tags/`。ほかの ref（`refs/remotes/` など）は書き換えず、
  出力の `NOT_REWRITTEN:` で知らせる
- fast-export の設定は filter-repo 2.47.0（`git_filter_repo.py` の `fep_cmd` と `fip_cmd`）を基にする

確かめてから移す:

- fast-import はコミットを一時的なブランチ（`refs/commit-refs/new/stream`）に積む。元の全てのコミットとタグに
  ついて、作者、日時、親の対応、全てのファイル（テキストは元に置き換えを当てたもの、ほかは元のまま）、本文が合う
  ことを確かめてから、ブランチとタグを 1 つの `git update-ref --stdin` のトランザクションで移す
- 元の ref は `refs/commit-refs/original/` に残し、戻せるようにする
- 作業ツリーに追跡しているファイルの変更があるとき、ほかの worktree があるとき（ブランチを移すとその worktree が
  食い違う）、HEAD が書き換えるブランチとタグから届かないときは、始める前に止める
- ref を移したらすぐに、元の番号から最後の番号への対応表を、filter-repo の commit-map と同じ形で
  `.git/commit-refs/commit-map` に書く。その後に作業ツリーを新しい HEAD に合わせる

### 帰結

- 良い点: 履歴の大きさに比例した 1 回の書き換えで終わる。Python と filter-repo が要らない
- 悪い点: 流す前に、全てのコミットの見出し、本文、ファイルの操作を手元に置く（ブロブの中身は置かない）
- 良い点: 確かめが通らなければ ref を動かさないので、失敗しても元の履歴はそのまま
- 悪い点: テキストかどうかを `.gitattributes` で決めない（`remap` の git grep `-I` は属性も見る）。属性で
  バイナリにしたテキストのファイルも、履歴の中では付け直す
- 悪い点: 署名つきのコミットとタグは、署名を外す（中身が変わるので、元の署名は合わない）

### 確認

- `commit-refs rewrite-history` の結合テスト（`modules/home/parts/commit-refs/tests/rewrite_history.rs`）: 文書と本文の
  番号が最後の番号になる、別のブランチを指す文書を流れの順によらず付け直す、作者と日時を保つ、全てのブランチと
  両方の種類のタグとタグを指すタグを移す、バイナリとシンボリックリンクを変えない、作業ツリーを合わせる、元の ref と
  対応表を残す、書き換えない ref を知らせる、循環・消えたコミット・作業ツリーの変更・ほかの worktree・届かない
  detached HEAD・前の書き換えの ref で止まり ref を動かさない
- xlc の clone（2026-10-11、xlc f828bf78、release ビルド）:
  - 変えない対応表: 書き換えるブランチとタグのどれも動かない（0.71 秒）
  - filter-repo 2.47.0 で `.gitignore` を履歴から消した後: 1648 コミットのうち 731 が変わり、3855 語を置き換えた
    （0.86 秒）。HEAD で置き換わった 173 組の番号は、元と新のコミットの件名、作者、日時がどれも一致した
- 流す側でブロブの置き換えをわざと捨てると、突き合わせが止め、ref を動かさないことを手で確かめた

## 補足

実装の途中で試して変えた版:

- **fast-export の順のまま流す版**: 親から順に流せば、文書が指す先は先に流れていると考えた。別のブランチのコミットを
  指す文書（main のコミットが、日時の後の side のコミットを `cherry-pick -x` の形で指す）では、指す先がまだ流れて
  おらず、書き換え全体が止まった（テスト
  `rewrites_references_to_commits_on_other_branches_whatever_the_export_order`）。依存の順に並べ直す版にした
- **注釈つきのタグを fast-export の流れから作る版**: タグを指すタグで、作ったタグが指すものが突き合わせで
  合わなかった（原因は確かめていない。候補は、流れの中のタグの印の扱い）。タグのオブジェクトから作り直す版にした
