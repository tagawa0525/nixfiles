# ADR-0006: ADR は MADR を基準に書き、スキルで形を示して hook で確かめる

## 背景

ADR の形はどこにも書かれておらず、既存の ADR を手本に書いていた。手本を真似ると、欠陥も一緒に複製される。
2026-10-10 には、ADR-0002 に書いたホストの状態の項目と再開手順の節を、ADR-0003 が同じ形で真似た。
周りに合わせて書くのはモデルの既定の振る舞いなので、モデル自身は誤りに気づきにくい。
ADR の形をどこで示し、どう守らせるか。

## 決定の要因

- 一般的な標準を基準にし、ほかの仕組みに良い考えがあれば積極的に取り入れる
- grep で引け、機械で検査できる形にする
- 書く時点で形が手元にあること（呼び忘れると効かない仕組みにしない）
- 他人のプロジェクトにはこちらの形を押し付けない

## 検討した案

- MADR 4.0.0 を基準に、ほかの仕組みの良いところを取り入れ、スキルで示して hook で確かめる
- 自作の形（日本語の 5 節）をスキルと hook で守らせる
- 既存の道具を使う（adr-tools、log4brains）
- CLAUDE.md に 1 行足す

## 決定と理由

採用: 「MADR 4.0.0 を基準に、ほかの仕組みの良いところを取り入れ、スキルで示して hook で確かめる」。理由は、標準の形を
そのまま土台にでき、足りないところだけを出典のある考えで埋められるため。決めたのはユーザー。

取り入れたもの。スキル `adr` には、これらを反映したテンプレートと運用だけを書き、それだけで完結させる（出典は
この ADR に置く）:

- **前付け**: `supersedes` / `superseded-by` / `issues` を独立したキーにする（xlc。MADR は置き換えを status の文中に
  書くので grep で辿りにくい）。`requires` で前提にしている ADR を挙げる（PEP の Requires）。status に `withdrawn`
  と `deferred` を足す（PEP、KEP）
- **見出し**: 日本語で書く。節を足せる以上、見出しは固定されないので、読みやすさを取る（hook は英語の原文も
  受け付ける）。必須は MADR の 3 節（背景・検討した案・決定と理由）、推奨は帰結と確認（MADR の minimal
  テンプレートと、テンプレートの注記）。テンプレートは MADR 4.0.0 を CC0-1.0 で受け、見出しと前付けを改めた
- **運用**: proposed の間は自由に直し、実装をマージするときに accepted にする（xlc、PEP）。確定した後に直すのは、
  誤字やリンク、前付けの status、補足の節への日付つきの追記だけ（PEP 1、AWS の手引き、ADR の事例集）。決定を
  変えるときは新しい ADR で置き換え、まだ有効な部分を書き直して含める（xlc）
- **ADR にするもの**: 作り直したときに他へ波及する決定と、範囲、期間、危険、費用のどれかが大きい決定（事例集）
- **ADR は増えていく前提にする**: LLM が決めてマージし、後で見直して作り直すことが多くなる。そのたびに新しい ADR で
  置き換え、前の判断の全文をファイルとして残す（grep で読め、git の履歴をあさらずに済む）。書くのは LLM なので
  件数の手間は小さく、今の決定は `status: accepted` で引ける

確かめる仕組み:

- **`require-adr-skill`**: Skill ツールの成功（PostToolUse）を hook 自身がセッション単位で記録し、Write / Edit での
  `docs/adr/NNNN-*.md` への書き込みの前に確かめる。モデルが付ける印ではないので、読まずに書くことはできない
- **`claude-hooks adr-sections`**: git の pre-commit で、必須の節が無ければ止め、推奨の節が無ければ警告する。
  index が確定するのはコミットの時なので、PreToolUse では検査しない
- **他人のプロジェクトでは外す**: 既定は有効。`upstream` を持つ fork か、GitHub のリモートの所有者に自分
  （`claude-hooks.owner`。組織など複数可）以外がいれば他人のプロジェクトと判定し、`git config claude-hooks.own-project`
  に書く。手で書いた値を優先する。自分のアカウントが未設定なら、所有者で判定できないので書き込まない

### 帰結

- 良い点: 形の基準が手元の ADR から MADR に移り、欠陥が複製されにくくなる
- 良い点: 他人のプロジェクトでは、何もしなくても外れる
- 良い点: 必須の 3 節の見出しを既存の ADR（0001〜0004）と同じ名前にしたので、既存の ADR も検査を通る
- 悪い点: 既存の ADR の前付けは新しいキー（`requires` など）を持たず、MADR に無い節（ADR-0001 の「結果」、
  ADR-0002・0003 の「再開するとき」）も残る。直すのは別の PR
- 悪い点: hook の対象が Write / Edit に広がり、そのたびに hook が 1 回走る（ADR 以外のパスでは git を呼ばずに返す）
- 悪い点: SSH の別名（`git@github-work:…`）のように github.com を含まないリモートは、所有者を判定できない。
  そのリポジトリが他人のものなら、`git config claude-hooks.own-project false` を手で書く
- 悪い点: 中身（決定か状態か）と、確定後の変更が許された範囲かは検査できず、レビューに頼る
- どちらでもない: 他人のプロジェクトの判定が、git の hook の fork 判定（`upstream` の有無）と別にある（#266）
- 見直す条件: 前付けの検査（キー、status の値、置き換えの双方向の一致、参照先の存在）を hook に足すとき。
  issue の書式を決めるとき

### 確認

- `.claude/tests/hooks.sh` に `require-adr-skill`（`post-tool-use` の記録を含む）と `adr-sections`（必須の検査と
  推奨の警告）のテストを足した
- この ADR が `adr-sections` を通ることを確かめた

## 各案の長所と短所

### 自作の形（日本語の 5 節）

- 悪い点: 一般的な形と食い違う（MADR で必須の検討した案を任意にし、決定の要因などが無かった）
- 悪い点: 独自の規則が増え、その保守も自分で負う

### 既存の道具（adr-tools、log4brains）

- 良い点: adr-tools は nixpkgs にあり、作成と置き換えを CLI で扱える。log4brains は MADR に準拠し、静的サイトに
  できる
- 悪い点: adr-tools の形式は Nygard 形式で、MADR ではない。log4brains は Node が要る。どちらも構造を検査しない

### CLAUDE.md に 1 行足す

- 良い点: 常に読まれる
- 悪い点: 形の中身（テンプレートと運用）までは持てない

## 補足

調べたが取り入れなかったもの:

- 決めた場所へのリンク（PEP の Resolution、Rust RFC の RFC PR）: ADR を加えたコミットとマージのコミットから引ける
- 話題ごとに 1 件の ADR をその場で直す（生きた ADR。事例集が報告する、変えられる方がうまくいったチームの運用に
  近い）: 番号が今の決定を指し続け、古い ADR への参照が残らない利点がある。しかし前の決定の理由の全文が git の
  履歴にしか残らず、作業ツリーには要約しか残らない。決定の経緯を残すことが ADR の価値なので採らない。古い ADR
  への参照は、hook の警告で新しい番号に直す（#269）
- 一部だけ改める（IETF の Updates）: 採用中の ADR だけで今の決定が分かる、という置き換えの運用と相容れない
- 決めた段階と実装した段階を分ける（PEP の Accepted と Final、KEP の implementable と implemented）: 実装を
  マージするときに accepted にするので、決めたのに実装していない状態が無い
- 決めた人・承認した人（MADR の decision-makers、PEP の Author、KEP の approvers）: 1 人で決めるので情報が増えない
- 正誤表（IETF の errata）: 補足の節への日付つきの追記と同じ情報で、別のファイルを持つ分だけ重い

実装の途中で試して捨てた方式:

- **節を 5 つに限る許可リスト**: MADR は節を足すことを禁じていない。ADR-0002・0003 の「残るもの」は箇条書きだった
  ので捕まらず、同じ中身は補足の節に書けてしまう。中身の判断はレビューの役目なので捨てた
- **見出しを英語の原文のままにする**: 節を足せる以上、見出しは固定されず、英語のままにする利点が薄い
- **MADR の原本を手を加えずにスキルに収め、調整を別に書く**: 使う側が原本と調整を頭の中で合成する必要があり、
  出典の注記（この ADR や、取り入れ元の名前）もスキルの外の文書を前提にしていた。スキルだけで完結しないので、
  調整済みのテンプレートを収める形に改めた
- **PreToolUse での節の検査**: `git commit` の実行前の index を見るので、`git add … && git commit` や
  `git commit -a` を素通りした。index が確定する git の pre-commit に移した
- **PreToolUse での Skill の記録**: 呼び出しが拒否されたり展開に失敗したりしても、記録だけが残った。成功後の
  PostToolUse に移した
- **「書かないもの」の一覧**: 禁止を並べる形になる。置き場所（ADR にするもの、issue、コミットの本文）と運用で示す
  形に改めた
