# ADR-0006: ADR は MADR を基準にした形で書き、その形をスキルで示す

## 背景

ADR の形はどこにも書かれておらず、各プロジェクトで既存の ADR を手本に書いていた。手本を真似ると、欠陥も一緒に
複製される。2026-10-10 には、ADR-0002 に書いたホストの状態の項目と再開手順の節を、ADR-0003 が同じ形で真似た。
ADR を持つ自分のプロジェクト 4 つ（xlc 117 件、lsp-det 23 件、pleasanter-rs 7 件、nixfiles）は、形がすべて違う
（2026-10-11 に数えた）。ADR の形をどこで示し、どう守らせるか。

## 決定の要因

- 一般的な標準を基準にし、ほかの仕組みに良い考えがあれば積極的に取り入れる
- grep で引け、機械で検査できる形にする
- 20 以上ある自分のプロジェクトで同じ形を使え、他人のプロジェクトには押し付けない
- 自前の仕組み（ハーネス）を増やさず、一般的な道具を使う

## 検討した案

- 形をグローバルのスキルで示し、検査は各プロジェクトがオプトインする一般的な道具で行う
- 形をスキルで示し、検査を全プロジェクト共通の Claude Code の hook（claude-hooks）で行う
- 既存の道具を使う（adr-tools、log4brains）
- CLAUDE.md に 1 行足す

## 決定と理由

採用: 「形をグローバルのスキルで示し、検査は各プロジェクトがオプトインする一般的な道具で行う」。理由は、形は
プロジェクトによらない知識なので全プロジェクトで読める場所が合い、検査はプロジェクトの側に置けば、他人の
プロジェクトかを推測する仕組みが要らないため。決めたのはユーザー。

形（スキル `adr`）は MADR 4.0.0 を基準にし、次を取り入れた。スキルには、これらを反映したテンプレートと運用だけを
書き、それだけで完結させる（出典はこの ADR に置く）:

- **前付け**: `supersedes` / `superseded-by` / `issues` を独立したキーにする（xlc。MADR は置き換えを status の文中に
  書くので grep で辿りにくい）。`requires` で前提にしている ADR を挙げる（PEP の Requires）。status に `withdrawn`
  と `deferred` を足す（PEP、KEP）
- **見出し**: 日本語で書く。節を足せる以上、見出しは固定されないので、読みやすさを取る。必須は MADR の 3 節
  （背景・検討した案・決定と理由）、推奨は帰結と確認（MADR の minimal テンプレートと、テンプレートの注記）。
  テンプレートは MADR 4.0.0 を CC0-1.0 で受け、見出しと前付けを改めた
- **運用**: proposed の間は自由に直し、実装をマージするときに accepted にする（xlc、PEP）。確定した後に直すのは、
  誤字やリンク、前付けの status、補足の節への日付つきの追記だけ（PEP 1、AWS の手引き、ADR の事例集、lsp-det の
  「追補」）。決定を変えるときは新しい ADR で置き換え、まだ有効な部分を書き直して含める（xlc）
- **ADR にするもの**: 作り直したときに他へ波及する決定と、範囲、期間、危険、費用のどれかが大きい決定（事例集）
- **ADR は増えていく前提にする**: LLM が決めてマージし、後で見直して作り直すことが多くなる。そのたびに新しい ADR で
  置き換え、前の判断の全文をファイルとして残す（grep で読め、git の履歴をあさらずに済む）。書くのは LLM なので
  件数の手間は小さく、今の決定は `status: accepted` で引ける

検査（必須の節、前付け、置き換えの双方向の一致、古い ADR への参照）は、検査の本体を 1 つの flake に置き、各
プロジェクトが git-hooks.nix で取り込む（#269）。プロジェクトに置く設定と雛形は、増えてきたら copier で配る。

### 帰結

- 良い点: 形の基準が手元の ADR から MADR に移り、プロジェクトごとに分かれていた形が揃っていく
- 良い点: 検査を取り込んだプロジェクトにだけ効くので、他人のプロジェクトの判定が要らない
- 悪い点: 検査はまだ無い。それまでは、形を守るのはスキルとレビューだけ（#269）
- 悪い点: 既存の ADR（nixfiles の ADR-0001〜0005、xlc、lsp-det、pleasanter-rs）は別の形のまま。揃えるかは
  プロジェクトごとに決める
- 見直す条件: 検査を作るとき（#269）。issue の書式を決めるとき（#270）

### 確認

- スキルのテストで、動的なコマンドが動くことを確かめた
- この ADR は、スキルのテンプレートの形で書いた

## 各案の長所と短所

### 形をスキルで示し、検査を全プロジェクト共通の Claude Code の hook で行う

- 良い点: 各プロジェクトで設定しなくても効く。書く前にスキルを読ませる確認もできる
- 悪い点: 全プロジェクトに効くので、他人のプロジェクトかを推測する仕組み（remote の所有者の判定など）が要る。
  この PR で作り、抜けを塞ぐたびに新しい抜けが出た（下の補足）
- 悪い点: Claude Code に固有で、一般的な道具ではない

### 既存の道具（adr-tools、log4brains）

- 良い点: adr-tools は nixpkgs にあり、作成と置き換えを CLI で扱える。log4brains は MADR に準拠し、静的サイトに
  できる
- 悪い点: adr-tools の形式は Nygard 形式で、MADR ではない。log4brains は Node が要る。どちらも構造を検査しない

### CLAUDE.md に 1 行足す

- 良い点: 常に読まれる
- 悪い点: 形の中身（テンプレートと運用）までは持てない

## 補足

調べたが取り入れなかったもの:

- 決めた場所へのリンク（PEP の Resolution、Rust RFC の RFC PR）: ADR を加えたコミットとマージのコミットから引ける
- 話題ごとに 1 件の ADR をその場で直す（生きた ADR）: 番号が今の決定を指し続ける利点はあるが、前の決定の理由の
  全文が git の履歴にしか残らない。決定の経緯を残すことが ADR の価値なので採らない。古い ADR への参照は検査で
  新しい番号に直す（#269）
- 一部だけ改める（IETF の Updates）: 採用中の ADR だけで今の決定が分かる、という置き換えの運用と相容れない
- 決めた段階と実装した段階を分ける（PEP の Accepted と Final、KEP の implementable と implemented）: 実装を
  マージするときに accepted にするので、決めたのに実装していない状態が無い
- 決めた人・承認した人（MADR の decision-makers、PEP の Author、KEP の approvers）: 1 人で決めるので情報が増えない
- 正誤表（IETF の errata）: 補足の節への日付つきの追記と同じ情報で、別のファイルを持つ分だけ重い

この PR で試して捨てた方式（コミットの履歴にも残る）:

- **全プロジェクト共通の Claude Code の hook での強制**: Skill の成功を記録して ADR の書き込みの前に確かめる
  `require-adr-skill` と、git の pre-commit で節を検査する `adr-sections` を作った。他人のプロジェクトでは外すため、
  `upstream` の有無と、GitHub のリモートの所有者（`git config claude-hooks.owner`）から判定して
  `git config claude-hooks.own-project` に書いた。抜けを塞ぐたびに新しい抜けが出た（ユーザーが打った `/adr` を
  記録できない、会話の要約の後も記録が残る、`ssh://…:443/` のポートを所有者と取り違える、hook の matcher を
  書き換えると同じグループの別のコマンドまで変わる、など）。検査をプロジェクトの側に置けば判定そのものが要らない
  ので捨てた
- **節を 5 つに限る許可リスト**: MADR は節を足すことを禁じていない。ADR-0002・0003 の「残るもの」は箇条書きだった
  ので捕まらず、同じ中身は補足の節に書けてしまう。中身の判断はレビューの役目なので捨てた
- **見出しを英語の原文のままにする**: 節を足せる以上、見出しは固定されず、英語のままにする利点が薄い
- **PreToolUse での節の検査**: `git commit` の実行前の index を見るので、`git add … && git commit` や
  `git commit -a` を素通りした
- **MADR の原本を手を加えずにスキルに収め、調整を別に書く**: 使う側が原本と調整を頭の中で合成する必要があり、
  出典の注記もスキルの外の文書を前提にしていた
- **「書かないもの」の一覧**: 禁止を並べる形になる。置き場所と運用で示す形に改めた

決定の後に分かったこと:

- 2026-10-11: 「決定と理由」の「決めたのはユーザー」は事実と違う。ユーザーは方向（形をスキルで示し、検査をプロジェクトの
  側に置く）には同意していたが、この ADR とスキルの中身には同意しておらず、PR #271 は同意の前にマージされた。ユーザーの
  意図は、これを参考にして作り直すことだった（ADR-0008）
