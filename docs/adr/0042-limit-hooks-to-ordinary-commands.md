# ADR-0042: hook は独自の手順のルール、うっかりミス、lint と fmt を、モデルが普通に書く形で守らせ、作為的な抜け道は塞がない

## 背景

claude-hooks（`modules/home/parts/claude-hooks`）の PreToolUse hook は、Bash ツールのコマンドを読んで、
このリポジトリの手順に外れる操作を止める。その範囲を書いた ADR は無く、個々のルールの ADR が基準を決めてきた。
ADR-0020 は「実際に Slurm へ投げるスクリプトは、どの書き方でも止める（見落としたら止める側に倒す）」を決定の
要因にし、ADR-0025 はそれを引いて、`bash -c` の文字列を深さ 5 まで読み、`sudo`、`xargs`、`ssh`、`eval` などの
包みをほどき、走らせるものが決まらない形を止める方向に広げた。

2026-10-20 から 21 にかけて、hook のルールを直す 2 つのブランチで、ローカルのレビューの周が終わらなかった
（数は 2026-10-21 00:05 JST に `git log --oneline origin/main..<ブランチ>` と
`git diff --stat origin/main...<ブランチ>` で数えた。origin/main は 70ca576）:

- fix/pre-pr-create-accept-chained-push（#388、PR #402。先端 4389025）: 27 コミット、6 ファイル、+665 行 / -27 行。
  ローカルのレビューは 6 周目に入った（周の数は担当のセッションの記録による。git の履歴には残っていない）
- feat/hook-require-pipefail（先端 2d05c00）: 14 コミット、10 ファイル、+981 行 / -40 行。コミットの件名に
  「3 周目の反例」がある

原因は、レビューのたびに、作為的な書き方での抜け道が「正しい反例」として指摘され、ADR-0025 の基準のもとでは
直す対象になったことにある。例: `push.default=upstream` や `remote.<名前>.push` で push の行き先を書き換える
設定（f18c131）、`set +o pipefail` を `||` や `{ …; }` の後ろに置いて効く範囲をずらす形（a0860b6）。どれも
直せば正しいが、モデルが手順に沿って作業していて書く形ではない。直すたびにテストと読み方が増え、次の周で
その増えた読み方の隙が新しい反例になった。

ユーザーの言葉（2026-10-21）: 「独自ルールを守らせること（WTを分けたり、no-ffでリベースし直すなど）、
うっかりミスやlint, fmtをしっかりかけるぐらいで、LLMの抜け道を塞ぐことではないです」「OpusやSonnetの判断は
ある程度信じることにしていた」。

## 決定の要因

- hook は、手順に沿って作業するモデルを、手順の側へ戻すためにある。モデルの判断はある程度信じる
- レビューの周が、指摘の内容で終わること（指摘ゼロを待たない運用と食い違わない基準）
- 止める側の誤判定は、そのまま作業を止めるので直す
- すでに入っているコードは、消す手間と壊す危険の方が大きい

## 検討した案

- 案 A: hook は、モデルが普通に書く形のコマンドで、独自の手順のルール、うっかりミス、lint と fmt を守らせる。
  作為的な書き方での抜け道は塞がない。hook は境界ではない
- 案 B: ADR-0020 と ADR-0025 の基準のまま、見つかった抜け道を直し続ける
- 案 C: 抜け道を塞ぐ範囲を、ルールごとの ADR で個別に決める

## 決定と理由

採用: 「案 A」。

### hook が止めるもの

- このリポジトリ独自の手順のルールを守らせる: worktree を分け、ブランチを既定ブランチから作る（`guard-branch-base`、`guard-git-stash`）、rebase したうえで
  no-ff でマージする（`guard-git-merge`、`pre-git-merge-check`）、main に直接コミットしない、PR の形
  （`pre-pr-create-check`、`pre-merge-check`）、重い計算を Slurm に流す（`guard-sbatch`）など
- うっかりミス: `git add -A`、秘密情報のコミットなど（大きすぎるコミットは止めずに知らせる。`warn-large-commit`）
- lint と fmt を確実にかける: git の hook（pre-commit）を飛ばさせない（`block-no-verify`）など

### 判定の対象

モデルが普通に書く形のコマンド。スキル、CLAUDE.md、ツールのヘルプに出る書き方と、それを `&&`、`;`、`|`、
`cd <dir> &&`、`git -C <dir>`、`VAR=value` の前置き、`env`・`timeout`・`nice`・`nohup`・`time`・`command` の
前置き、スキルにある `… | xargs -0 -r git add --`、サブシェル、2 段までの `bash -c '…'`（ADR-0025 の案 E の
記録で、Claude Code が書く入れ子は 2 段を超えない）でつないだものを指す。

### 止めないもの

作為的な書き方での抜け道。例:

- ラッパーで包む（`sudo`、`ssh`、`eval`、`flock -c`、`watch`、`script -c` など）、3 段以上の `bash -c` の入れ子
- 文字列にして実行させる（`$CMD`、`eval "$CMD"`、`printf %q` で包んだ文字列、標準入力から読ませる）
- 珍しい git の設定や全体オプションで行き先や挙動を変える（`push.default=upstream`、`remote.<名前>.push`、
  `url.<base>.insteadOf`、`git -c …`、`--git-dir`）

hook は境界ではない。これらを止めないことで生じる穴は、モデルの判断と人のレビューに任せる。

### 運用

- 新しいルールを足すときと判定を直すときは、普通に書く形で正しく動くことをテスト（`.claude/tests/hooks.sh`、
  単体テスト）で示す。それ以上の形は追わない
- レビュー（Copilot、/code-review）で出た「この形なら抜ける」という指摘は、普通に書く形でなければ直さず、
  この ADR を理由に閉じる（重大度によらない）
- 止める側の誤判定（普通の形を誤って止める）は直す
- すでに入っているコードは消さない。簡単にしてよい箇所の洗い出しは #405 に書く

### ADR-0020 と ADR-0025 との関係

次の部分を、今後の判断の基準にしない（この ADR で置き換える）。それに基づいて入ったコードとテストは残す:

- ADR-0020 の決定の要因「実際に Slurm へ投げるスクリプトは、どの書き方でも止める（ガードは、見落としたら通す側
  ではなく止める側に倒す）」と、決定と理由の「本物の書き方がどれだけあっても……見落としは止める側に倒れる」。
  決定そのもの（除くのは同名のテスト `.claude/tests/scripts/slurm-run.sh` だけ）と、案 A を捨てた理由
  （`scripts/slurm-run.sh` のような相対パスを通す）は変えない
- ADR-0025 の決定の要因「ガードは、見落としたら通す側ではなく止める側に倒す（ADR-0020）」
- ADR-0025 の案 A のうち、普通に書く形を超える部分: `bash -c` の文字列を 3 段以上（深さ 5 まで）読み、超えたら
  止める側に倒すこと（案 E を捨てた理由「深く包めば抜けられる」を含む）、包みの表に `sudo`、`flock`、`chrt`、
  `taskset`、`watch`、`script -c`、`ssh`、`eval` を足すこと、走らせるものが決まらない形を対象語があれば止める
  こと（`Cmd::opaque`、`Shell::runs_program`）。「足さなかった包み」の「要るときに足す」は、モデルが普通に書く形で
  使うようになったときだけ足す、と読む。帰結の「包みが受け付けるオプションが変わったら表を直す」は、普通に書く
  形の読み方が変わるときだけ直す

次の部分は、普通に書く形の範囲にあり、そのまま有効:

- ADR-0020 の決定（同名のテストだけを除く）と、その確認のテスト
- ADR-0025 の、`bash -x <script>` / `sh -eu <script>` のオプション付きの起動（#303）、2 段までの `bash -c '…'` を
  読むこと（案 D を捨てた理由「Claude Code が書く形」）、`xargs` の包み（スキルの `… | xargs -0 -r git add --`）、
  `cd x; (git commit)` の `cd` を効かせるスコープの読み方、
  `echo sbatch` のような引数に現れるだけの形を止めない（偽陽性を増やさない）こと、偽陽性による見直しの条件

置き換えは部分的なので、両 ADR は `status: accepted` のまま、補足に日付つきでこの ADR を指す。前付けの
`requires` に両 ADR を入れ、両 ADR を置き換えるときに `grep -l 'requires:.*ADR-NNNN' docs/adr` で引けるようにする。
`superseded-by` は付けない。`design-records check` は `superseded-by` を `status: superseded`（全体の置き換え）と
組で求め、全体を置き換えるなら ADR-0025 の読み方の表（今のコードの説明として有効）をこの ADR に書き直して
含めることになる（/adr の確定後の運用）。

### 採らなかった案

- 案 B: 背景の 2 つのブランチのとおり、抜け道を 1 つ塞ぐと読み方が増え、その隙が次の反例になる。作為的な形は
  数え上げられないので、レビューの周が終わらない。周を終える側の基準（指摘の内容で打ち切る）とも食い違う
- 案 C: ルールごとに範囲を決めると、レビューのたびに「このルールではどこまで塞ぐか」を決め直すことになり、
  周が終わらない原因が残る

### 帰結

- 良い点: hook のルールを直すブランチが、普通に書く形のテストで終わる。レビューの抜け道の指摘は、この ADR を
  理由に閉じられる
- 悪い点: 作為的な書き方をすれば、hook を通り抜けられる。それはモデルの判断と人のレビューに任せる
- 実装との差: 既存のコード（`unwrap.rs` の包みの表、`shell.rs` の `MAX_DEPTH` と `Cmd::opaque`、
  `Shell::runs_program`、ssh / `sudo -i` の中の場所の扱いなど）は、この ADR の範囲を超える読み方を含む。消す
  手間と壊す危険の方が大きいので残し、簡単にしてよい箇所の洗い出しは #405 に書く
- 背景の 2 つのブランチは、この ADR を元に最小の形で作り直す（作り直しは別の PR）
- レビューの打ち切りの基準（`.claude/skills/gh-pr-review/SKILL.md`、`.claude/skills/gh-pr-create/SKILL.md`、
  `.claude/skills/delegate/SKILL.md`、`.claude/skills/git-merge/SKILL.md`）から、この ADR を指す

### 確認

- hook のルールを足す・直す PR の `.claude/tests/hooks.sh` と単体テストが、普通に書く形を確かめている
- レビューの抜け道の指摘への返信と、対応しなかった指摘の報告が、この ADR を理由に挙げている
