# ADR-0065: 依頼で括るユーザーの言葉は会話の記録からコピーし、受ける側が記録で確かめる

## 背景

delegate の頼む側の書き方は、決定済みの内容に、どこで決まったか（ADR などの記録の場所、ユーザーの言葉）を添えるとしていた。
ユーザーの言葉は決定の出典で、事実の出典ではない（ADR-0060）。ユーザーの案は「案（決定ではない）」として渡す（ADR-0055）。
ユーザーの言葉をどの形で書き、受ける側がどう確かめるかは決めていなかった。

2026-10-29 に xlc の依頼（#0188 の ADR の受理）が、2026-10-27 のユーザーの発言を「」で括って書いた。会話の記録の原文は
「MOXの燃焼は流す準備だけしておいて。今週のWeekly Limitが消えそうになったときのネタに取っておきましょう。（AWSで流さなくても
いいです。）」（その会話の記録の `.jsonl` の `timestamp` 2026-10-27T14:12:02Z）で、依頼の言葉は語尾が「取っておく」に変わり、
後半が欠けていた。担当は括った言葉を原文として作業中の xlc の ADR-0206 に書いた（コミットされた版には入っていない）。
そのあとリポジトリとメモリで原文を探して見つけられず、要約に書き直した。会話の記録は探さなかった。担当が気づかなければ、
言い換えがユーザーの発言として確定した ADR に残った。

サブエージェントの文脈に親の会話は無いが、会話の記録のファイル（`~/.claude/projects/<プロジェクト>/<セッション ID>.jsonl`）は
Read と `jq` で読める。記録は 1 行 1 JSON で、ユーザーが打った発言は `type` が `user` で `origin.kind` が `human` の行と、
ターンの途中に送った発言の `type` が `attachment` で `attachment.type` が `queued_command` の行に入る。`user` の行には、
ツールの結果、ほかの担当の報告（`origin.kind` が `peer`）、会話の圧縮の要約（`origin` が無い）も入り、`human` の行にも
コマンドの出力（`<local-command-stdout>` など、`<` で始まる）が入る。圧縮の要約は上の発言を引用しており、`grep` で文字列を
探すだけでは、ユーザーの発言と要約を見分けられない。記録のファイルは会話ごとにあり、ファイル名の ID は `Claude-Session:` の
ID と別である。

## 検討した案

- 案 A: 「」で括る言葉は、会話の記録からコピーしたものだけにする。retro の `session-events.sh` の `USER:` の行（圧縮の
  要約や前の依頼を拾わない）からコピーし、文の途中で切らず、時刻を JST で添える。受ける側は時刻つきの引用だけを引く。
  ローカルレビューで反例が出た: `USER:` の行は 300 字で切れ、改行を空白にするので原文でない
- 案 A': 「」で括る引用には、会話の記録の `.jsonl` のパスと発言の `timestamp` を添え、記録からそのままコピーする。受ける側は
  `.jsonl` のユーザーの発言の行に同じ文があるかを確かめ、無ければ要約として書いて報告する。記録からコピーしない言葉は括らず、
  要約と分かる形で渡す
- 案 B: 依頼ではユーザーの言葉を括らず、判断の要約と発言の日付で渡す。受ける側は親の要約として書く。最初はこの案で書いたが、
  前提の「サブエージェントは会話の記録を見られないので、引用を確かめられない」が誤りだった（retro の担当とレビューの担当が
  `.jsonl` を読み、2026-10-27T14:12:02Z の発言を照らした）。前提が崩れると、要約に落とす利点は残らず、ユーザーの原文が
  委任した ADR に入らなくなる損だけが残る
- 案 C: hook（delegate-request-fields）で、時刻の無い「」の引用や、会話の記録に無い引用を止める。依頼の「」はユーザーの
  言葉以外（語、ファイルの見出し）にも使うので、ユーザーの言葉の引用を形から見分けられない

## 決定と理由

案 A'。ユーザーの言葉は原文で残し、言い換えを括った誤りは、受ける側が記録で機械的に見つける。案 A の弱点（`USER:` の行が
原文でない）は、`.jsonl` を直接読めば起きない。

- 頼む側: ユーザーの言葉（判断、承認、案）を「」で括って引用するときは、会話の記録の `.jsonl` のパスと、その発言の
  `timestamp` を添える。引用は記録からそのままコピーする（語尾や後半を変えない。長ければ要る部分だけを引用し、省いたところに
  「…」を付ける）。記録からコピーしない言葉は「」で括らず、`<要約>（ユーザー <日付> の判断の要約）` と書く
- 頼む側は、記録のパスと `timestamp` を、プロジェクトの記録のディレクトリの `*.jsonl` に受ける側と同じ `jq` のコマンドを
  掛けて引く（前の会話の発言も見つかる）
- 受ける側: 記録のパスと `timestamp` を添えた「」を、ユーザーの言葉の引用として扱う（添えていない「」は、語や見出しと
  見分けられないので要約として扱う）。ADR、issue、報告に書く前に、添えられた `.jsonl` のユーザーの発言の行（上の 2 種。
  `<` で始まるものを除く）に同じ文があるかを `jq` で確かめる。コマンドは発言の全文と JST の日時を出し、受ける側は、引用の
  両端が文の区切りか「…」の印に当たることを見る（文の途中で切って印の無い引用は、部分文字列として見つかっても、後半の
  条件や否定を落としうる）。印のある引用は、印で切った部分がどれも同じ発言に同じ順で出ることを見る。満たさない、記録が
  添えられていない、記録が読めないときは、引用でなく要約として書き、報告の「確認の結果」の「前提」に書く
- 確かめる `jq` のコマンドは delegate のスキルの 1 箇所に書き、頼む側と親のマージ前の確認はそこを指す。retro の
  `session-events.sh` は発言を 300 字で切り改行を潰すので、原文の照合には使わない
- 受ける側が ADR や issue に書く形は、xlc に既にある `（ユーザー 2026-10-27）` の形に揃え、引用は `「<引用>」（ユーザー <日付>）`、
  要約は括らずに `<要約>（ユーザー <日付>）` とする。日付は JST（記録の `timestamp` は UTC）
- delegate の受ける側の「ユーザーの承認は、ユーザーの言葉があるときだけ書く」は、「依頼と追加の指示がユーザーの言葉（引用か
  要約）として書いたときだけ書く」にする。依頼そのものは承認ではない、という趣旨は変えない

### 帰結

- 委任で書いた ADR に、確かめたユーザーの原文が入る。確かめられない言葉は要約の形で入り、報告に食い違いが残る
- 頼む側は、引用のたびに記録からコピーし、`timestamp` を引く手間が増える。要約で渡せばこの手間は無い
- 確かめるコマンドは Claude Code の記録の形（`origin.kind`、`queued_command`）に依る。形が変われば、同じ文を見つけられず、
  引用は要約に落ちる（誤った引用が通る向きには壊れない）
- 要約の形で書くユーザーの判断は、親の要約を確かめる手段が無い。要約は「判断の要約」と明示して渡し、委任した ADR には
  括らずに入るので、原文と取り違えられることは無いが、要約の誤りは親のマージ前の確認でしか見つからない

### 確認

- 委任した ADR の「」で括ったユーザーの言葉を、マージの前に親が同じ `jq` のコマンドで記録と照らし、無ければ要約の形に直す
  （delegate の頼む側の書き方の、報告を確かめる項）
