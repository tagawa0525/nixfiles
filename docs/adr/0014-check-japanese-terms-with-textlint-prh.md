# ADR-0014: 崩れた日本語の語を、textlint と prh の辞書で pre-commit と commit-msg に検査する

## 背景

どのプロジェクトのセッションでも、日本語が同じ型で崩れる（2026-10-11 に調べた。#290）。

- 動詞の連用形をそのまま名詞にする: `確かめ`、`比べ合わせ`、`効き`、`数え`（本来は 確認、比較、影響、計数）
- 英語の直訳の造語: `端のケース`（edge case）、`作業木`（worktree）、`点断面積`（pointwise）、`掃引`（sweep）

ユーザーの発言（全セッションの記録を検索）に、和語に寄せる指示は無かった。原因の候補は 2 つ。

- 文書の多くを Claude が書いていて（xlc は 1573 コミット中 1497、グローバルの CLAUDE.md は 20 回中 19 回が Claude
  との共著。2026-10-11）、和語の動詞の多い文体で毎セッション読み込まれる。次のセッションがそれに寄せて書き、また
  文書に残る
- 指摘はプロジェクトごとのメモリに入り（nixfiles: `端のケース`、`作業木`。xlc: `点断面積`、`確かめ`）、ほかのプロジェクトの
  セッションには届かない

## 決定の要因

- 一度指摘された崩れは、どのプロジェクトのコミットでも二度と通らない（グローバルの hook が走るプロジェクト）
- 新しい崩れを 1 か所に足せば、全てのプロジェクトに効く
- 動詞の「確かめる」と名詞の `確かめ` のように、前後の文字で見分けられる
- 既存の道具があれば、それを使う

## 検討した案

- 案 A: textlint と textlint-rule-prh。辞書は prh の YAML（誤り、正しい語、JavaScript の正規表現）
- 案 B: Vale（Go のシングルバイナリ）
- 案 C: 辞書を埋め込んだ Rust の CLI を作る
- 案 D: 検査せず、グローバルの CLAUDE.md とメモリだけで伝える

## 決定と理由

採用: 案 A。

- textlint と prh は、日本語の文書の検査の事実上の標準で、nixpkgs にある（textlint 15.7.1、textlint-rule-prh 6.0.0。
  `textlint.withPackages` で組む。2026-10-11）。Node.js の実行環境は Nix が持ち込む
- JavaScript の正規表現は先読みと後読みを書けるので、`確かめ(?=[のでをは…])` のように、名詞の用法だけを止められる
  （2026-10-11 に、名詞の `確かめ` を止め、「確かめる」「確かめにくい」を通すことを確かめた）
- 案 B は、正規表現が Go の RE2 で先読みと後読みが無く、名詞と動詞を前後の文字で見分けられない
- 案 C は、辞書の形式と照合を自分で決めて保守する。既存の道具があるので作らない（ユーザーの判断）
- 案 D は、プロジェクトごとのメモリが届かないという原因を残す

検査の範囲と置き場所:

- 辞書は `modules/home/parts/ja-terms/prh.yml`。textlint の設定（`@textlint/text` に足すコードの拡張子と、辞書の
  パス）は Nix で作り、hook は textlint と設定を Nix store のパスで呼ぶ
- 辞書に入れるのは、どの文脈でも 1 つの語に直せるものだけ（prh は 1 つの語にしか直せない）。`効き` は「影響」「効果」
  「効くか」のどれにもなり、nixfiles の ADR-0010 の「設定の効き」を「影響」にすると意味が変わるので入れない
- 崩れた語を例として書くときは、インラインのコードにする（textlint は Markdown のコードを検査しない）。崩れた語を
  わざと含むファイル（辞書のテストなど）は、リポジトリの `.textlintignore`（gitignore と同じ書き方）に挙げる。
  prh の辞書（`prh.yml`）は誤りを並べるので、どのリポジトリでも検査しない
- 名詞の用法を前後の文字で見分けるときは、名詞にしか続かない文字だけを使う。「に」「も」「は」、空白、行末は
  動詞にも続く（確かめにくい、確かめもせず、確かめはした、行の折り返しの `確かめ⏎る`）
- グローバルの pre-commit が、ステージしたファイルのうち Markdown、テキスト、コード（コメントと文字列の日本語を
  含めて、ファイルの全体）を検査する。対象の拡張子は `md`、`txt`、`rs`、`py`、`sh`、`nix`、`toml`、`yaml`、`yml`、
  `json`（大文字と小文字を問わない。自分のプロジェクトで日本語を書く言語。足すときは `git.nix` の一覧に足す）。
  シンボリックリンクは行き先が文章でないので外す
- 見るのはコミットに入る中身（ステージした版）。Markdown の自動修正は作業ツリーをステージし直す（#282）ので、
  既定の検査の最後に走らせる。手順は `modules/home/parts/ja-terms/staged.sh`。textlint は引数をグロブとして読み、
  エスケープも効かない（2026-10-11 に `[draft].md` で確かめた）ので、ブロブを番号の名前で書き出して検査し、
  出力を元のパスに戻す
- プロジェクトがローカルの pre-commit（`.git/hooks/pre-commit`）を持つときは、ほかの既定の検査と同じく走らない
- グローバルの commit-msg が、Claude Code のセッションのコミットの本文を検査する。除くのは `commit -v` の scissors の
  行から後だけ（`#` で始まる行は、`-m` や `-F` ではコミットに残る）。Merge、fixup、squash、Revert は、件名が元の
  コミットから写したもの（Merge は git が作るもの）なので、件名を除いた本文だけを見る。textlint の起動は重いので、
  Conventional Commits と件名の長さの検査の後に呼ぶ
- upstream リモートのある fork では、ほかの検査と同じく飛ばす（上流の文書はこちらの辞書の対象でない）
- グローバルの CLAUDE.md に、技術文書で定着した語で書くことを肯定の形で 1 行足す（辞書は既知の崩れしか止めない
  ので、新しい崩れを減らす指針は残す）
- 言葉づかいのプロジェクトごとのメモリは、中身を辞書に移して消す

### 帰結

- 良い点: 一度辞書に入れた崩れは、どのプロジェクトのコミットでも止まり、直す語が示される
- 悪い点: 辞書に無い新しい崩れは止まらない。見つけたら辞書に足す。文脈で直す語が変わる崩れも止まらない
- 悪い点: 辞書を厳しくすると、その語を含むファイルを触るコミットが止まる。今ある文書は、辞書を足したときに各リポジトリで
  一度掃除する
- 悪い点: Node.js の実行環境が依存に入る（Nix が持ち込むので、手で入れるものは無い）
- 実装が決定に追いついていない点: 各リポジトリの今の文書の掃除（2026-10-11 の検査で lsp-det 5 件、nucrawler 4 件。
  nixfiles と xlc は 0 件）と、言葉づかいのプロジェクトごとのメモリの整理は、この変更を rebuild で反映した後に行う（#290）

### 確認

- `modules/home/parts/tests/ja-terms.sh`: 辞書の各項目が名詞の用法を止め、動詞を通す。コードのコメント、ステージ
  した中身だけを見ること、空白を含むパス、辞書と `.textlintignore` のファイルを外すこと、fork で飛ばすこと、
  コミットの本文のコメントと scissors の後を見ないこと
- 辞書の各項目の `specs`（prh が辞書を読み込むときに確かめる）
