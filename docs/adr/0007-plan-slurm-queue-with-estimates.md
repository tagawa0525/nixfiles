# ADR-0007: r995 の Slurm の待ち行列を、見積もりの時間と利用者の並べ替えで組み替えられるようにする

## 背景

r995 の Slurm は、重い計算を `--exclusive` で 1 本ずつ流す（`modules/slurm/common.nix`）。投げるのは主に Claude Code の
エージェントで、複数のエージェントが同時に投げる。2026-10-11 の xlc の作業では、次のことが起きた。

- xlc の短い測定（数分）が、OpenMC の計算（1 本約 1 時間）2 本の後ろで待った。`scontrol top` で前に出そうとしたが、
  利用者には許されておらず `Access/permission denied` で断られた
- ジョブがどれくらいかかるかを、待ち行列からは知る手段が無く、いつ何が始まるかの見込みを立てられなかった
- `--wrap` で投げたジョブは名前がすべて `wrap` で、どのセッションのどの計算かが分からなかった

## 決定の要因

- 走っている計算は止めない（途中で止めると、それまでの計算が無駄になる。ユーザーの判断）
- 待っているジョブの順番を、投げた本人（エージェント）が変えられること
- 待ち行列から、何がいつ始まりいつ終わる見込みかと、誰に連絡すればよいかが読めること
- 利用者は 1 人なので、利用者どうしの公平さは要らない

## 検討した案

- 案 A（採用）: `SchedulerParameters=enable_user_top` で利用者に `scontrol top` を許し、`--time` を見積もりとして必ず付け、
  `OverTimeLimit=UNLIMITED` で超えても止めない。投げ方は `~/.claude/scripts/slurm-run.sh` に決める
- 案 B: 先に走らせたいジョブより前のジョブを `scontrol hold` し、走り始めたら `release` する
- 案 C: 優先度の高いパーティションか QOS を作り、急ぐジョブをそこに投げる
- 案 D: `--time` を本当の上限として付ける

## 決定と理由

採用: 「案 A」。走っている計算に触れずに、待っているジョブだけを並べ替えられる。見積もりは `squeue` の見込み（`%S`）に使われ、
上限としては効かないので、見積もりが外れても計算は失われない。

- `SchedulerParameters=enable_user_top` と `OverTimeLimit=UNLIMITED` を `modules/slurm/common.nix` に置く
- `squeue` の既定の表示（`SQUEUE_FORMAT`）に、名前、経過、見積もり（`%l`）、始まりの見込み（`%S`）、連絡先（`%k`）を出す
- `slurm-run.sh` は `-t <見積もり>` を必須にし、名前（`-J`）、ログ（r995 の `~/github/slurm-logs/<名前>-<番号>.out`）、
  連絡先（`--comment` に git のブランチ、投げた場所、`CLAUDE_CODE_SESSION_ID`）を付ける。`--top` で投げたジョブを先頭に移す

### 帰結

- 良い点: 短い計算を長い計算の前に出せる。`squeue` だけで、何がいつ終わる見込みで、どのセッションの計算かが分かる
- 悪い点: 見積もりを書く手間がかかる。見積もりが外れると、見込みの時刻もずれる（計算は止まらない）
- 見直す条件: 利用者が増えて公平さが要るようになったとき（`enable_user_top` は自分のジョブの中の順番しか変えないが、
  `OverTimeLimit=UNLIMITED` は他人の見込みを狂わせる）

### 確認

- `slurm-run.sh` の振る舞いは `.claude/tests/scripts/slurm-run.sh` で確かめる
- 反映後に、利用者のまま `scontrol top` で待っているジョブの順番が変わることを確かめる。今の設定は優先度の重みが
  すべて 0 で、全ジョブの優先度が 1 なので、nice の調整で順番が変わるかは試すまで分からない

## 各案の長所と短所

### 案 B（hold と release）

今の権限でできるが、待っているジョブを 1 本ずつ止めて戻す手間がかかり、戻し忘れるとそのジョブは走らない。
同じ優先度のジョブが投げた順に走るなら、release したジョブは元の位置に戻るので、hold を続けるジョブが増える。

### 案 C（優先度の高いパーティションか QOS）

順番の付け方は確実だが、どれを急ぐかを投げるときに決めなければならず、投げたあとの組み替えができない。
QOS は accounting のデータベース（slurmdbd）が要る。

### 案 D（`--time` を上限にする）

見込みは立つが、見積もりを超えた計算が止められ、それまでの計算が無駄になる。決定の要因の 1 つ目に反する。
