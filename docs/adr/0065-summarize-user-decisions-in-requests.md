# ADR-0065: 依頼のユーザーの判断は日付つきの要約で渡す

## 背景

delegate の頼む側の書き方は、決定済みの内容に、どこで決まったか（ADR などの記録の場所、ユーザーの言葉）を添えるとしていた。
ユーザーの言葉は決定の出典で、事実の出典ではない（ADR-0060）。ユーザーの案は「案（決定ではない）」として渡す（ADR-0055）。
ユーザーの言葉をどの形で書くかは決めていなかった。

2026-10-29 に xlc の依頼（#0188 の ADR の受理）が、2026-10-27 のユーザーの発言を「」で括って書いた。会話の記録の原文は
「MOXの燃焼は流す準備だけしておいて。今週のWeekly Limitが消えそうになったときのネタに取っておきましょう。（AWSで流さなくても
いいです。）」（その会話の記録の `.jsonl` の `timestamp` 2026-10-27T14:12:02Z）で、依頼の言葉は語尾が「取っておく」に変わり、後半が欠けていた。担当は会話を見られないので、括った言葉を原文と
して xlc の ADR-0206 にコピーし、そのあと原文をリポジトリとメモリで確かめられず、要約に書き直した。担当が気づかなければ、言い換えが
ユーザーの発言として確定した ADR に残った。

## 検討した案

- 案 A: 「」で括る言葉は、会話の記録からコピーしたものだけにする。retro の `session-events.sh` の `USER:` の行（圧縮の
  要約や前の依頼を拾わない）からコピーし、文の途中で切らず、時刻を JST で添える。受ける側は時刻つきの引用だけを引く。
  ローカルレビュー（2 周目）で反例が出た: `USER:` の行は 300 字で切れ、改行を空白にするので原文でない。全文を `.jsonl` から
  取り直す手順は手作業で、受ける側は会話の記録を開かないので確かめられない
- 案 B: 依頼ではユーザーの言葉を括らず、判断の要約と発言の日付で渡す。受ける側は親の要約として書く
- 案 C: hook（delegate-request-fields）で、時刻の無い「」の引用や、会話の記録に無い引用を止める。依頼の「」はユーザーの
  言葉以外（語、ファイルの見出し）にも使うので、ユーザーの言葉の引用を形から見分けられない

## 決定と理由

案 B。言い換えが原文として残る失敗は、原文を依頼に持ち込まなければ起きない。案 A は手作業の手順が増え、誤りが入っても
受ける側が止められない。

- 頼む側: 依頼と追加の指示に書くユーザーの言葉（判断、承認、案）は、要約にして発言の日付（JST。会話の記録の `timestamp` は
  UTC）を添える。日付が分からなければ「日付不明」と書く。確定した ADR や記録にある原文は、その場所を挙げて引く
- 受ける側: ユーザーの判断と承認は `（ユーザー <日付>、親の要約）<要約>`、案は `（ユーザーの案 <日付>、親の要約）<要約>` の形で
  書く。確定した ADR や記録を出典に挙げた原文は、その出典を開いて同じ文を引く。同じ文が無い、ほかの出典、出典の無い「」は、
  親の要約として書き、食い違いを報告する
- delegate の受ける側の「ユーザーの承認は、ユーザーの言葉があるときだけ書く」を置き換える。この条件は依頼の「」の言葉を確かめられないので、
  言い換えを防いでいなかった。承認は、親がユーザーの判断として書いたときだけ、親の要約と分かる形で書く

### 帰結

- 委任で書いた ADR の、ユーザーの判断の出典は、親の要約と日付になる。ユーザーの原文は委任した ADR に入らない
- 頼む側は、会話の記録の UTC の時刻を JST の日付に直す手間が残る

### 確認

- 委任した ADR のユーザーの判断が、親の要約の形か、出典を挙げた原文の引用かを、マージの前に親が見て、出典の無い「」は
  要約の形に直す（delegate の頼む側の書き方の、報告を確かめる項）
